# ADR-0017: Migrate to a Replacement Host and Admit the 7.0 Kernel Series

Status: accepted

Date: 2026-08-11

## Context

ADR-0007 requires the K3s deployment to stay compatible with the host kernel and cgroup
mode and states that an incompatibility "stops implementation and requires a new OS or VM
ADR". ADR-0016 discharged that clause for the 5.15 → 5.8 kernel change on the original
host. This ADR discharges it again, for a change of machine.

The original host (`pci`, i9-14900K) is gone. Its failure is recorded here, in this ADR,
which is the primary record; the audit note for G03 carries the operational consequence
rather than restating the evidence. In summary:

- `/var/lib/systemd/pstore/` held **3112 crash dumps** reaching back to 2025-06-26, with
  **95 distinct kernel RIPs** spread across unrelated subsystems (page-fault handling,
  buffer reclaim, IRET, path walking, rmap, memcg) and faults inside `swapper/9` and
  `kswapd0` — pure kernel context. Many unrelated RIPs indicate corrupted execution, not
  one software defect.
- Crashes occurred on **both** 5.15 and 5.8, so they were not kernel-specific.
- `mce_count: 0` with no EDAC driver loaded, and both DIMMs at their JEDEC-rated
  5600 MT/s with no XMP/EXPO, so neither ECC-visible memory failure nor an overclock
  explains it.
- The crash rate accelerated: 45 dumps in 2025-11 → 574 on 2026-08-11.
- The CPU ran microcode `0x123`. Intel's Raptor Lake Vmin-shift mitigation is `0x12B` or
  later. The installed `intel-microcode` package already carried `0x12F` but it had never
  been packed into an initramfs, so it never early-loaded.
- After `update-initramfs` the host booted with `microcode updated early to revision
  0x12f` — and then crashed twice more (21:18:08 and 21:19:49, boots lasting 1 and 6
  minutes). Microcode prevents *further* Vmin-shift degradation; it cannot repair silicon
  already degraded. The host subsequently stopped booting at all.

The replacement host is a 13th-gen i9-13900K / RTX 4090 on ASUS PRIME Z790-P, reachable
over LAN and through an frpc relay. Probing it produced four capability-contract failures
against the retained baseline: `kernel_release` (7.0.0-28 vs accepted `5.15.`/`5.8.`),
`cgroup_version` (2 vs required 1), `docker_available` (absent), and `protected_ports`
(80/443 unused).

Three of those four were environment gaps rather than incompatibilities and were simply
resolved: Docker was installed, the host boots the cgroup v1 legacy hierarchy with
`systemd.unified_cgroup_hierarchy=0`, and the 80/443 workload the fourth asserts was
provisioned on loopback (see Consequences). That was verified rather than assumed — kernel 7.0
still ships `CONFIG_MEMCG_V1=y`, `CONFIG_CPUSETS_V1=y`, and `CONFIG_CGROUP_FREEZER=y`, and
after the reboot `/sys/fs/cgroup` is a v1 hierarchy, `systemctl is-system-running` reports
`running` with 0 failed units, Docker reports `Cgroup Version: 1`, and the GPU still
initializes.

The replacement host has its own crash history, which was examined before committing to
it rather than after. It is materially different from the original:

- 33 crash events / 450 dump files, all between 2026-07-31 (the OS install date) and
  2026-08-10.
- Only **9 distinct RIPs**, and the population is explained: 24 faults in
  `Comm: stress-ng-cpu` from a deliberate `stress-ng --cpu 32` burn-in recorded in shell
  history, one `sysrq_handle_crash` (an operator-triggered panic), and a cluster in the
  NVIDIA GSP path (`r535_gsp_acpi_info`).
- The genuine faults all occurred at microcode `0x10e`, the factory revision.
  `0x133` — later than the `0x12B` fix threshold — was early-loaded on 2026-08-10 20:14,
  and no genuine kernel fault has been recorded since.
- Memory runs at its JEDEC-rated 4800 MT/s with no XMP/EXPO. `Tainted: 4097` decodes to
  proprietary + out-of-tree module, i.e. the NVIDIA driver, which is expected and benign.

So the original host degraded *under* a fixed microcode, while this host's faults were
recorded *before* its fix was applied. That is the distinction that makes the replacement
usable, and it is the claim to re-examine if instability reappears.

**Instability did reappear, on 2026-08-12, and the claim above is therefore qualified rather
than intact.** During a `fw-sut` lab deploy the host entered a crash-reboot loop: seven boots
between 22:08 and 22:14, each dying 8-30 seconds in, ending in a real `poweroff` that left the
machine down until it was physically power-cycled. The panic lands at roughly 21 s of uptime,
which is when k3s finishes starting and restores pods, so `cni0`/`veth` churn immediately
precedes it — that is *when* it dies, not *why*.

The signature is hardware-class by the same test this ADR applied to the original host. The
faulting RIP is frequently not a valid address at all (82 records at `0x0`, 28 at `0x1`, plus
`0xb8`, `0xa`, `0x9407c01`), i.e. corrupted control flow rather than a logic error, spread over
six CPUs (4, 5, 10, 12, 13, 20) and over unrelated contexts including `swapper`, `kworker`,
`runc`, `conda`, `pt_autograd_0`, `snapd`, and `systemd-udevd`. Memory exhaustion is excluded
(`oom_kills=0` with 122 GB of 131 GB free) and so is ECC-visible memory failure or an
overclock (`mce=0`; DIMMs at their JEDEC-rated speed).

Two facts distinguish this from the original host's decline, and neither is yet decisive.
First, microcode was `0x133` throughout — later than the `0x12B` threshold — so these faults
occurred *under* a fixed microcode, which is precisely the pattern this ADR used to condemn
the original machine. Second, the archive is cumulative across 36 boots, so most of its 1072
records predate that night and the per-boot rate has not been isolated. **CPU versus DIMM has
not been separated**: EDAC counters, `dmidecode` memory detail, and a memtest pass are all
still unrun, and bad RAM produces an identical scatter pattern.

What has accumulated since is evidence of stability rather than decline. The host booted
2026-08-25 and, as of 2026-09-03, had been up nine days continuously with `oops_this_boot=0`,
`mce_this_boot=0`, microcode still `0x133`, and 122 GB of 131 GB available. The original host's
defining trait was an accelerating crash rate that no fix arrested; this host has instead gone
from a crash loop to a nine-day uninterrupted run. That is not proof of soundness — a
Vmin-shift failure is intermittent and load-dependent, and the DIMM hypothesis remains
untested — but it is inconsistent with active, progressive degradation. The operating stance is
therefore: usable for evidence production, with the host recorded alongside the kernel for
every artifact, and with the CPU-versus-DIMM separation still owed before this host is called
sound.

## Decision

Admit `7.0.` as an accepted host kernel series, appended to `ACCEPTED_KERNEL_SERIES`
alongside `5.15.` and `5.8.`. `compatibility_profile` in `deploy/k3s/versions.lock.yaml`
becomes `ubuntu-5.15-or-5.8-or-7.0-cgroup-v1-amd64`.

Series are admitted additively, never replaced, for the reason ADR-0016 gave: removing an
accepted series would retroactively invalidate closed G01 capability evidence, which is
frozen historical record in the same category as `docs/gates/G02/REPORT.md`.

Run the replacement host in **cgroup v1**, so `cgroup_version == 1` continues to hold
unchanged rather than being weakened to accept v2. This keeps the fault-injection
environment comparable to the one G01 and G02 closed on. It is a deliberate choice to
adapt the host to the contract instead of the contract to the host, and it costs nothing
semantically: `cgroup_version` is only ever *recorded and asserted* in this codebase —
faults are injected through flagd feature flags in the OTel demo, not through cgroup
controllers — so no fault adapter depends on either mode.

Add `server.host` rotation as a first-class operation (`rotate-server-endpoint`). The
prior bootstrap had no path for a pinned host disappearing: `migrate_handoff` refuses to
overwrite an existing store, which is correct for its own job but left rebootstrapping
from scratch as the only option, discarding the Bailian and LangSmith keys and their
live-verification evidence for no reason — those credentials are host-independent.
Rotation therefore retains the API keys, replaces the four `server.*` values, and
**clears** `host_key_verified`, `ssh_key_verified`, and `capability_reprobe_match`, and
deletes the stale `known_hosts` entry. A new machine must re-earn trust rather than
inherit it; a stale pin is worse than no pin, because it would let a different machine at
the same address pass `BatchMode` checks.

Pull container images through a verified registry mirror. Docker Hub is unreachable from
this network — every advertised address blackholes on both IPv4 and IPv6 — while
`ghcr.io`, `nvcr.io`, and GitHub releases are reachable. This is a transport substitution
only: every image the project consumes is pinned by sha256 digest, so content is verified
against the pin regardless of which host served the bytes. This was confirmed rather than
assumed, by fetching the pinned `busybox` and `mirrored-pause` manifests through the
mirror and hashing them: both match their pinned digests byte-for-byte.

## Alternatives

- **Accept cgroup v2 and relax the assertion to `in {1, 2}`.** Rejected. The assertion is
  cheap to satisfy and expensive to loosen: v1 was part of the environment G01 and G02
  closed on, and relaxing it would make future readiness evidence silently
  non-comparable with closed evidence. Booting v1 costs one kernel flag.
- **Replace `5.15.`/`5.8.` with `7.0.` instead of appending.** Rejected for ADR-0016's
  reason: it would invalidate the closed G01 capability baseline.
- **Rebootstrap the secret store from a fresh handoff.** Rejected. It would discard the
  Bailian and LangSmith keys and their `verified_live_*` evidence, which have nothing to
  do with which machine the project runs on.
- **Keep the original host by replacing its CPU under Intel's extended 13/14th-gen
  warranty.** Still the correct action for that hardware and worth pursuing separately,
  but it is an RMA with a multi-week turnaround and the host no longer POSTs, so it
  cannot carry the current work.
- **Make `protected_ports` conditional on a pre-existing workload being present.**
  Rejected. It reads as the careful option but inverts the guarantee: the check would pass
  automatically on a bare host, which is precisely the host where re-enabled Traefik or
  ServiceLB could claim 80/443 unnoticed. Provisioning the subject keeps the assertion
  meaningful on every host instead of only on hosts that already satisfy it.
- **Pin a Docker Hub IP address in `/etc/hosts`.** Rejected: it rots the moment Docker
  rotates its fleet, and it does not actually work here — the advertised IPv4 address
  blackholes too.
- **Relay every image from the operator's VPN-connected PC.** Kept in reserve and used
  where a mirror cannot serve a needed artifact, but not adopted as the default: it makes
  every image pull depend on a workstation being online, whereas the digest pin already
  provides the integrity guarantee the relay was meant to protect.

## Consequences

`0x133` is current on the replacement host and must stay early-loaded. Because 13th-gen
i9 is affected by the same Vmin-shift defect that destroyed the original host, microcode
revision is now a thing to verify on this host rather than assume, and a regression to a
pre-`0x12B` revision should be treated as a stop condition, not a warning.

Because the 2026-08-12 crash loop occurred *at* `0x133`, microcode currency is no longer
sufficient evidence of host health, and long runs must be able to survive the host vanishing
mid-flight. Two consequences follow. Infrastructure bootstrap must be bounded: the lab
readiness waits in `render_k3s_bootstrap_script` previously looped unbounded and would block
forever on a wedged host, and now fail with `FW_G02_LAB_DEPLOYMENT_TIMEOUT` /
`FW_G02_LAB_STATEFULSET_TIMEOUT` naming the pending workload
(`LAB_READINESS_DEADLINE_SECONDS`, a bootstrap-only bound that is not one of the frozen metric
deadlines). And a host disappearance mid-run is an expected infrastructure failure to be
retried under AMD-0003, not a metric failure: pod restart reasons read `Unknown` after such an
event, which is power loss rather than an application defect. Separating CPU from DIMM on this
host remains open work and is the prerequisite for treating it as sound.

Readiness evidence produced on the original host **cannot be compared** with evidence from
this host, and evidence produced on a CPU that was silently corrupting execution should
not be used at all. In particular the best previous G03 preflight round (24 pass / 7
`infra_failed` / 1 `metric_fail`) is not a baseline to improve on; the 7 `infra_failed`
cases are now attributable to the failing host. ADR-0016's obligation to record which
kernel produced each piece of evidence extends to recording which **host**.

That obligation is discharged in the metric-v3 run manifest by `host_identity_v3()`, first
present in the r9 round (2026-09-05) and absent from every earlier manifest. It records two
fields: `host_key_digest`, a SHA-256 over the sorted keytype-plus-key fields of the pinned
`known_hosts` entries, and `runner_kernel`, the local kernel string. A host public key is
non-secret by construction -- it is what a client verifies a server against -- so hashing it
yields a stable, machine-unique fingerprint that survives reboots. The `known_hosts` line's
first field is the host **address** and is excluded from the digest deliberately, so the
artifact carries a machine fingerprint while address, port, username and all key material
stay out of the record. Unavailable input yields the literal `unavailable` rather than a
partial digest.

The field is deliberately **outside** the resume identity contract asserted by
`_assert_resume_identity_v3`. A host swap mid-run is a real hazard, but `runner_kernel` is
environmental, and comparing it on resume would refuse resumes for reasons unrelated to what
is being measured. The field exists so that two rounds from different machines are
distinguishable after the fact, which is the actual failure this ADR addresses.

G01 and G02 closed evidence is untouched by this ADR. `docs/gates/G02/REPORT.md` keeps its
0.500/0.000 values as honest historical record.

`protected_ports` (80/443 in use) is satisfied by provisioning the workload it asserts,
for the same reason the cgroup mode was adapted rather than relaxed. The original host
happened to run 26 unrelated containers on those ports, and the assertion exists so that
`disable: [traefik, servicelb]` in `deploy/k3s/versions.lock.yaml` has a live subject: with
nothing bound to 80/443, a k3s install that re-enabled either component would claim them
and no check would notice. A digest-pinned container bound to `127.0.0.1:80` and
`127.0.0.1:443` restores that subject. It is loopback-only, so it adds no public exposure
and `audit_runtime_coexistence` still sees zero non-loopback listeners; displacement of it
is caught by `compare_docker_baselines`, which compares the full container and network
inventory before and after install. The alternative — weakening the predicate to "80/443
are in use *or* nothing pre-existing is present" — was rejected because it would pass
vacuously on exactly the host where displacement is possible.

The same re-probe exposed a fail-open in `deploy/bootstrap/probe_host.py`: `docker_state()`
routed `docker ps` through a helper that maps any non-zero exit to an empty string, so a
`docker.sock` the probe user cannot read reported 0 running and 0 unhealthy containers —
and `docker_unhealthy_count == 0` therefore passed while measuring nothing. This host
reproduced it, because the probe runs unprivileged and the account was not in the `docker`
group. `docker_state()` now raises when the daemon is installed but unreachable, and
`docker_cidr_conflict()` reports a conflict when an installed daemon lists no networks at
all (Docker always owns `bridge`/`host`/`none`, so an empty list is a failed query, not a
clean reservation). Both are fail-closed directions: a check that cannot measure must not
report "clear".

## Migration and rollback

Rollback of the kernel-series change is removing `"7.0."` from `ACCEPTED_KERNEL_SERIES`
and reverting the `compatibility_profile` string; no evidence is rewritten in either
direction because the change is additive. Rollback of the cgroup mode is removing
`systemd.unified_cgroup_hierarchy=0` from `GRUB_CMDLINE_LINUX_DEFAULT` and rebooting;
`/etc/default/grub` is backed up on the host under `/root/fw-cgroup-*`. The Docker mirror
configuration is backed up under `/root/fw-mirror-*` and the DNS change under
`/root/fw-dns-*`. Rotation history accumulates in the private bootstrap metadata as
`server_endpoint_rotations`, recording endpoints as digests rather than addresses.

The coexistence workload is removable with `docker rm -f fw-coexistence`; its document root
is `/opt/fw-coexistence/html`. Removing it makes `protected_ports` fail again, which is the
intended coupling.

Tests pin the new behavior: `tests/infra/test_infra.py` covers acceptance of all three
series and rejection of unaccepted ones, `tests/security/test_bootstrap.py` covers
endpoint-handoff parsing, API-key retention across rotation, host-pin clearing, and the
refusal to write anything when round-trip verification fails, and
`tests/security/test_probe_host.py` covers both fail-closed probe directions plus the
running/unhealthy count it must still report correctly.
