# ADR-0016: Accept Both 5.15 and 5.8 Host Kernel Series After the 5.15 Boot Regression

Status: accepted

Date: 2026-08-11

## Context

ADR-0007 requires that the K3s deployment stay compatible with the host kernel and
cgroup mode, and it states that an incompatibility "stops implementation and requires a
new OS or VM ADR". This ADR discharges that clause.

G01 closed on `5.15.0-139-generic`, recorded in
`docs/evals/EVAL-G01-001/CAPABILITY_BASELINE.json`. Three guards enforced that series:
`bootstrap.py` (capability baseline), `infra.py` (pre-install baseline), and the
`infra.py` runtime-smoke kernel-identity check.

On 2026-08-11 the host stopped booting that kernel. The evidence, in order:

- `15:32:58` — the G03 readiness preflight lost the host on scenario 4 of 32
  (`remote script upload failed … exit=255`). Scenarios 1-3 had passed.
- `16:45:26` — `dpkg.log` records `upgrade linux-image-5.15.0-139-generic:amd64
  5.15.0-139.149~20.04.1`; `/boot/initrd.img-5.15.0-139-generic` was rewritten at
  `16:45:36`.
- `16:46:53` — the first boot after that package event lasted 11 seconds. Four
  consecutive 5.15 boots then failed, each booting and dying after 15-45 s, with
  `Kernel panic - not syncing: stack protector: Kernel stack is corrupted` while
  `systemd-udevd` probed modules.
- `17:01`-`17:28` — one 5.15 boot survived ~27 minutes and produced two survivable
  `Oops: 0011` events with `RIP == CR2 == RBX` pointing into the per-CPU/GS region
  inside `on_each_cpu_cond_mask → native_flush_tlb_multi → flush_tlb_mm_range`, i.e. a
  corrupt function pointer handed to a cross-CPU TLB flush. `mce_count: 0` — no
  machine-check or ECC error, so this is not attributable to failing memory.
- The DKMS module for 5.15 (`nvidia, 570.133.07`) was built `2025-06-26`, against the
  module tree that today's package event refreshed. Kernel taint on every 5.15 boot was
  `P OE` with `nvidia(POE)` loaded.
- `5.8.0-43-generic` has no recorded oops or panic in its journal history.

The long uptime before this is explained: the kernel and modules in RAM were untouched
by the on-disk package change, so the first reboot was the first execution of the new
initramfs.

The unexplained part is stated rather than hidden: the `15:32:58` failure precedes the
package event by 72 minutes, so the package event does not account for the host becoming
unstable in the first place. The two may share a cause; no evidence links them.

## Decision

Accept `5.15.` **and** `5.8.` as host kernel series for the frozen profile, via a single
`ACCEPTED_KERNEL_SERIES` constant and a `kernel_series_accepted()` helper in
`bootstrap.py`, used by all three previous guard sites. `compatibility_profile` in
`deploy/k3s/versions.lock.yaml` becomes `ubuntu-5.15-or-5.8-cgroup-v1-amd64`.

Both series are admitted rather than one replaced. Replacing `5.15.` would retroactively
invalidate the closed G01 capability baseline, which is frozen historical record in the
same category as `docs/gates/G02/REPORT.md`.

Every other capability assertion is unchanged and still enforced: `cgroup_version == 1`,
`cpu_count >= 32`, `memory_bytes >= 60 GiB`, `kvm_available`, `seccomp_available`,
`user_namespace_available`, `nvidia_available is True`, `"4090" in gpu_model`,
`gpu_memory_bytes >= 23 GiB`. Kernels outside both accepted series are still rejected.

## Alternatives

- **Repair 5.15 and keep a single accepted series.** The likely fix is a DKMS rebuild for
  5.15 plus `update-initramfs -c`. Not selected as the immediate path because each
  attempt costs a reboot, this consumer board (ASUS TUF GAMING Z790-PLUS WIFI) has no
  BMC/IPMI, the panic occurs before sshd and frpc start, and GRUB selection requires
  physical presence. 5.15 remains repairable and this ADR does not preclude returning to
  it.
- **Blacklist `nvidia` on 5.15.** A useful diagnostic, but it violates the
  `nvidia_available is True` capability assertion, so it cannot be a run configuration.
- **Nested VM or OS replacement.** Disproportionate to a kernel-selection problem and it
  would invalidate the G01 coexistence evidence.
- **Weaken or remove the kernel guard entirely.** Rejected: the guard is what prevents
  evidence being produced on an unverified host profile.

## Consequences

`5.8.0-43-generic` is an EOL HWE kernel on a 13th/14th-gen Intel board, so this is a
downgrade in supported-lifetime terms, accepted because it is the only kernel on which
this host stays up. The reason of record is "5.15 panics here", not "5.8 is better".

Two consequences are concrete and were discovered, not predicted:

1. **The onboard NIC `eno1` does not exist on 5.8** — its driver is absent from that
   kernel. Only `enp7s0` (`atlantic`) comes up. The host therefore holds a different
   address on 5.8, and K3s assets that pin an address (`bind-address`, `tls-san`,
   `node-ip`, kubeconfig `server`) plus the etcd member peer URL must all follow the
   kernel choice. This is a documented cost of the decision.
2. **The NVIDIA DKMS module must be built for 5.8** — it existed only for 5.15, so
   `nvidia_available` is False until that build completes. Until it does, the capability
   baseline fails on the GPU assertion rather than on the kernel.

Any G03 readiness or reference evidence must record which accepted kernel produced it, so
runs are not silently compared across kernels.

## Migration and rollback

Rollback is reverting `ACCEPTED_KERNEL_SERIES` to `("5.15.",)` and the
`compatibility_profile` string; no evidence is rewritten by either direction, because the
change is additive. Tests pin both accepted series and the rejection of unaccepted ones
(`tests/infra/test_infra.py`). Returning to 5.15 requires no ADR supersession, since
5.15 was never removed from the accepted set.
