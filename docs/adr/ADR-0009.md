# ADR-0009: Separate Behavior Candidate and Evidence Head Revisions

Status: accepted

Date: 2026-07-23

## Context

G01 used one Git SHA for behavior, runtime artifacts, Eval manifests, evidence reports, and Gate
closure. A test fixture or evidence-only synchronization changed HEAD and made every exact-SHA
manifest stale. Updating those manifests changed HEAD again. This created repeated deployment
binding, evidence rebinding, and a self-referential close-readiness cycle even when runtime image,
Chart, configuration, and environment were unchanged.

Commit `2e82126` allowed a narrowly defined evidence-only descendant for G01 close readiness, but
that local correction did not define a reusable identity model for later Gates.

## Decision

Candidate-bound evaluation has two explicit Git identities:

- `candidate_sha` is the immutable behavior revision. It identifies source, behavior-affecting
  tests, schemas, thresholds, workflows, lockfiles, deployment templates, and runtime artifacts.
- `evidence_head_sha` is either `candidate_sha` or a descendant containing only an approved
  evidence/status asset set. It identifies reports, manifests, claims, lifecycle state, and the
  final closure record without pretending those files changed the evaluated runtime.

Every evidence result also records the relevant runtime image, Chart, configuration, evaluator,
dataset, and environment-fingerprint digests. Git ancestry and changed paths between the two SHAs
are machine checked and fail closed.

A change to product behavior, test semantics, thresholds, locked fixtures, workflow behavior,
dependencies, deployment templates, evaluator semantics, or runtime artifact digest creates a new
`candidate_sha` and reruns every affected phase. An allowlisted evidence-only change advances only
`evidence_head_sha`. The Gate report names both; the Gate tag targets the closure/evidence head while
preserving the evaluated `candidate_sha` as the runtime claim.

## Original alternative and failure mechanism

The rejected model required every manifest and close check to equal current HEAD. It failed because
the act of recording a result changed HEAD. Rebinding all evidence to the documentation SHA was also
incorrect because deployed artifacts still came from the earlier behavior candidate.

## Boundaries

- The two-SHA model never declares semantic equivalence across source, test-semantic, evaluator,
  threshold, workflow, dependency, deployment, dataset, or runtime-artifact changes.
- Environment-bound live evidence is reusable only while its recorded environment fingerprint and
  required external-service identities remain valid.
- Ancestry alone is insufficient; every intervening path must be allowlisted and content rules may
  impose narrower constraints.
- Security findings, secret exposure, Ground Truth leakage, waiver changes, and locked-test changes
  always invalidate the affected evidence regardless of path name.
- This ADR accepts the model but does not implement phase caching, resume, or manifest migration in
  the G01 retrospective maintenance change. A future authorized Iteration owns that tooling.

## Consequences

Evidence synchronization and Gate closure no longer force runtime redeployment solely because their
own documentation changed. Reports become more precise about what was executed versus what recorded
the result. Tooling and schemas must eventually carry both SHAs and artifact/environment bindings,
and negative tests must reject non-evidence descendants or digest drift.

## Operational clarification (2026-07-24)

G02 exposed three remaining ambiguities in the accepted model. They are resolved as follows:

1. `candidate_sha` is supplied explicitly and remains the business/runtime identity until a
   behavior-affecting subject changes. Current checkout HEAD is not an implicit replacement. When a
   runner executes from an allowlisted evidence-only descendant, it validates candidate ancestry,
   the complete changed-path allowlist, and all declared subject digests. Exact
   `HEAD == candidate_sha` is therefore not a general Gate invariant and must not trigger a
   redeployment by itself.
2. A Git-tracked artifact cannot name the SHA of the commit that contains itself. Consequently,
   `evidence_head_sha` inside a runner-produced binding or manifest names the pre-existing execution
   checkpoint observed before output was produced. A later evidence or closure commit is identified
   externally by Git ancestry and the Gate tag. It never rewrites `evaluated_revision` or a phase's
   producing identity merely to point at itself.
3. A completed Iteration is an immutable audit record. A defect found later creates a new,
   monotonically numbered corrective Iteration with an explicit `corrects` link. The corrective
   Iteration may block the next planned work, but governance does not reopen the completed record or
   move the project lifecycle backward.

These clarifications change provenance and orchestration only. They do not reduce sample counts,
locked-test or Ground Truth isolation, quality/performance thresholds, health-oracle windows,
token/cost ceilings, or any phase pass/fail rule.
