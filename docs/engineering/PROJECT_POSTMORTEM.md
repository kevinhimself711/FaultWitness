# FaultWitness 项目复盘

## 0. 结论先行

**本项目终止，未达成任何原定目标。**

这句话此前不存在于仓库任何位置。`PROJECT_STATE.yaml` 的终态是
`active_gate: G03 / active_gate_status: not_started`，`PLAN.md` 最后一条写的是
"3b 取消 …… 不是项目终结"。本文档是这个失败声明的第一次落地。

原定目标是"做一个能在大厂 Agent 岗面试上讲清楚的项目"。终态：

| 维度 | 计划 | 实际 |
| --- | --- | --- |
| 周期 | 8–10 周做到 phase 0–7 | 52 天，G00–G02 关闭，G03 未启动 |
| Agent 能力 | 工具调用 + 多轮诊断 + 受控修复 | `/v1/tools` 与 `/v1/skills` 都 `return []`，`src/` 下无 `agent/`、无 `tools/` 包 |
| 面试就绪 | 150+ 案例、1000+ 轨迹、88 道答辩题有据可答 | 0 条真实 Agent 轨迹；1,284 个 docs 文件，读不完自己写的东西 |
| 产品 / 工装比 | 未设定 | 产品 5,819 行 : 工装 19,254 行 = 1 : 3.3 |

**一句话归因**：这个项目从第一天起衡量的是"治理动作是否合规"，
而不是"Agent 会不会诊断故障"。它在治理层面执行得非常严格，
而严格执行一个错误的度量标准，只会更快地到达一个错误的地方。

失败**不是**因为技术难度、不是因为宿主机崩溃、也不是因为模型能力不够。
上述都发生了，但它们只是把一个已经注定的结果提前暴露出来。

## 3. 教训

11 条，按"下一个项目开工前就能落地"排序。每条给症状、可数代价、成因、反做法。
标注区分**实测**（有命令或文件可查）、**推断**（从证据推出）、**未验证**（判断，无证据）。

### L1 从 JD 反推需求，而不是在成熟开源项目上做二次开发

**症状**：立项报告的输入是 22 份 JD + 84 份面经，输出是 57 条需求。
需求的合法性依据是"某份 JD 提到过"，不是"某个真实用户需要"。
于是需求集合等于**招聘市场的词表并集**，而词表并集必然自相矛盾且无法排序。

**可数代价（实测）**：57 条需求 → 审计重评只有 21 条 T1。也就是说 **63% 的需求
从一开始就不该进来**，而它们全程占用设计、评审、冻结、修正案的成本。

**成因（推断）**：JD 是一份职位的**能力清单**，不是一个产品的**问题陈述**。
把清单当需求，会得到一个没有主线的功能矩阵。更关键的是，JD 描述的是
"在已有系统上工作的能力"，而从零搭一个同等复杂度的系统，是完全不同、
且大得多的一件事——JD 里没有任何一条要求你**造**那个系统。

**下一个项目怎么做**：
- 选一个**已经跑得起来、有真实 issue 列表**的开源项目做二次开发。
  起点是别人的 CI 是绿的，而不是你的 `docs/` 是齐的。
- 需求来自那个项目的 issue / PR / 邮件列表，而不是 JD。JD 只用来**筛选**
  ——"这个 issue 修完之后，我能不能对着 JD 的某一条讲 15 分钟"。
- 把 JD 用在最后一步（讲什么），不是第一步（做什么）。顺序反了，
  整个项目就是为了覆盖名词而存在。

### L2 体量对一人开发根本不可行，而这一点从未被算过

**症状**：G00–G10 共 11 个 Gate，每个 Gate 要求一份决策完备的 Master Plan
加一组冻结的数值 exit criteria。11 个 Gate、57 条需求、5 个数据后端、
一套 K8s 故障环境、一个前端、一个训练栈——这是团队规模的分解，交给一个人。

**可数代价（实测）**：52 天走完 G00–G02（3/11），G03 未启动。
按这个速率推完 G10 需要约 **190 天**，且不含 G04+ 明显更重的内容。
原计划 8–10 周。**实际速率与计划差约一个数量级。**

**成因（推断）**：立项报告 §22.2 做过一次范围选择（8–10 周 → phase 0–7、
不做训练、K8s 只用于故障环境），**但那次选择没有换算成人日，也没有约束后续的 Gate 设计**。
`FINAL_PLAN.md` 定义 Gate 时把范围又放回去了。一次没有算术的范围收缩，等于没收缩。

**下一个项目怎么做**：
- 开工前写一张**人日表**：每个模块估人日，加总，除以你每天真实能投入的小时数。
  如果总数超过你敢投入的天数的 50%，砍到过。**先砍，再冻结。**
- 单人项目的硬上限：**一条主链路 + 两个可选侧枝**。超过这个数就不是"雄心"，
  是"没有做选择"。
- 每周核对一次实际速率对计划速率。第一次出现 2 倍偏差就重新规划范围，
  不要靠加班把偏差吸收掉——本项目的 44 天空洞就是吸收失败的样子。

### L3 项目脱离了找实习导向，交付物变成了治理记录

**症状**：项目的真实产出是 1,284 个 docs 文件、19 份 ADR、7 份修正案、
667 个诊断文件。而面试要用的东西——能跑的 Agent、能讲的轨迹、能画的架构图——
一个都没有。写完之后，**连作者自己都无法在合理时间内读清自己的架构**。

**可数代价（实测）**：0 条真实 Agent 轨迹（计划 1000+）；0 个案例（计划 150+）；
`/v1/tools` 与 `/v1/skills` 都 `return []`；`src/` 无 `agent/`、无 `tools/` 包。
88 道预备答辩题中，涉及 Agent 行为的部分**无实测数据可答**。

**成因（推断）**：目标函数被悄悄替换了。原目标是"面试上讲得清楚"，
执行中变成"Gate 能不能合规关闭"。后者可以每天产出可见进展（提交、文档、
修正案），前者要等很久才有第一个信号，于是注意力全被前者吸走。
**当一个代理指标比真目标更容易推进时，它一定会取代真目标。**

**下一个项目怎么做**：
- 开工第一天写一份**面试演示脚本**：15 分钟里点开哪几个界面、跑哪条命令、
  展示哪张图、讲哪三个技术决策。这份脚本就是验收标准，它先于任何架构文档。
- 每周问一次："如果面试是下周，我今天能讲什么？"如果答案里没有新东西，
  这一周就是白干的，不管提交了多少次。
- **可讲性优先于完备性**：一条端到端跑通、有真实数据、能当场演示的窄链路，
  在面试里完胜 11 个 Gate 的治理体系。后者甚至无法在 15 分钟内介绍完。
- 代码要能被**别人**在 30 分钟内读懂主链路。做不到，就等于你自己在面试前
  也要花几天重读——本项目正是如此。

### L4 技术栈是堆砌，不是有机组合

**症状**：`FINAL_PLAN.md` §4 一次性钉入 Python/FastAPI/Pydantic/LangGraph、
React/TS/Vite、PostgreSQL/Redis/Qdrant/MinIO/DVC、Keycloak-OIDC/OPA-Rego、
K3s/Helm/NetworkPolicy/ResourceQuota、OpenTelemetry/Prometheus/Loki/Tempo/Grafana、
LangSmith（硬依赖）、SOPS+Age、TRL/PEFT/bitsandbytes/Accelerate。
**没有一层写明"为什么是它，不是更简单的那个"。**

**可数代价（实测）**：langgraph / rego / peft / bitsandbytes / accelerate 在 `src/`
命中 **0** 个文件；qdrant 5、dvc 4、trl 5。也就是说声明的栈里有一半从未落地，
另一部分只有引入的代价没有产出。而每一项都进入了 Gate 的 exit criteria、
镜像清单、依赖锁与安全评审——**成本先付，收益从未到账**。

立项报告 §21.1 明确把"为了名词覆盖而堆组件"列为反模式，§21.8 明确禁止"提前做训练"。
**项目违反了自己第一天就写下的两条禁令。**这不是失误，是"反模式清单"被当成了
文档章节而不是检查项——它没有对应任何一道 Gate 检查。

**成因（推断）**：栈是从 JD 词频反推的（见 L1）。每个名词都有 JD 依据，
所以每个都"必要"；而"要不要"的判断本该来自架构约束，那一层从未存在。
审计报告 `FINAL_PLAN_REVIEW.md` 缺陷 1 的原话就是：**没有权衡层，范围只增不减。**

**下一个项目怎么做**：
- 每引入一个组件，写**一行**：它解决哪个具体问题，不用它的最简替代是什么，
  为什么替代不够。写不出来就不引入。这一行比一页架构图有用。
- 默认用**最少的后端**：一个关系库能撑住就不要向量库；文件系统能撑住就不要对象存储。
  数据库数量是运维复杂度的乘数，不是能力的加数。
- **重点只能有一个**。选一项深挖到能讲出取舍、失败尝试与实测数据，
  其余全部用最平庸可靠的方案。面试考的是深度，广度靠一句话带过就够了。
- 技术选型评审至少有一次是**削减评审**，会议目标是删东西，不是加东西。

### L5 需求始终无法确定

**症状**：57 条需求（41 条 mandatory）从 07-17 定稿到项目终止，
**从未有过一次收敛**。07-28 审计把它们重评为 T1/T2/T3/T4 = 21/17/12/7，
清楚指出多数不该做；这份审计 21 个文件、5,054 行，全部标 `authoritative: false`，
**没有触发任何一次计划变更**。需求没有被改，只是被审计了。

**可数代价（实测）**：7 份修正案、19 份 ADR（其中 3 份撤回自己冻结的数值）、
AMD-0007 膨胀到 753 行含 8 个事后补丁段。这些全是"需求没定但又必须冻结"
所产生的机械成本。

**成因（推断）**：需求同时具备两个互斥属性——**已冻结**（改动需走修正案）
和**未验证**（没有任何实测支撑它值得做）。冻结让它改不动，未验证让它站不住，
两者叠加的唯一出路就是不断打补丁。审计之所以标 `authoritative: false`，
也是因为治理层没有为"审计结论推翻已冻结需求"留任何通路。

**下一个项目怎么做**：
- 需求分两类：**接口/安全/失败语义**可以早冻；**功能范围**必须保持可删，
  直到有一次真实使用或真实测量。
- 给需求集合设**总量上限**（例如 15 条），新增必须删除等量的旧条目。
  上限会强迫排序，没有上限就永远不会有优先级。
- 审计如果没有权力改计划，就不要做审计——5,054 行的结论如果注定
  `authoritative: false`，那它的全部成本都是浪费。**先给通路，再做评审。**
- 每条需求写一条**放弃条件**："如果 X 没发生，就删掉它"。
  没有放弃条件的需求会一直活着。

### L6 治理无限膨胀

**症状**：治理 v1 要求每个 Iteration/Corrective/Gate attempt 都走
plan → activate → candidate → evidence → close 的提交序列，
带 candidate SHA / evidence SHA / governance HEAD 三元身份、绑定 ConfigMap、
manifest 耦合。**治理动作本身成了主要工作量。**

**可数代价（实测）**：
- G02 期间 119/174 次提交不触碰 `src/` 或 `tests/`；1,111/1,616 次文件触碰属非实现类。
- `access-58`：运行时 **+12/-7 行**，代价 7 次提交、59 次触碰、**+1,593 行**。
  治理开销与产出之比约 **80 : 1**。
- `C-G02-012`：一个 **27 秒**的真实测试，周边产生 **6 小时零实验**。
- 全项目 212/356 次提交（60%）不触碰代码。

**成因（实测，`G02_GOVERNANCE_RETROSPECTIVE.md` 列了 10 条系统性根因）**：
治理设计的目标是"任何状态都可追溯、任何变更都可审计"，这在多人长周期项目里是对的。
单人项目里，追溯的收益接近零（唯一的读者就是作者本人），而成本按变更次数线性增长。
更糟的是它**惩罚小改动**：改 12 行和改 1200 行要付同样的治理税，
于是理性反应变成"攒着一起改"——而攒批改动又让归因失效。

**下一个项目怎么做**：
- 治理 v2 已经给出了正确形态，直接沿用：**单一机器状态源**
  （`PROJECT_STATE.yaml`）+ 一本日志里的直接调试循环。
- **死锁规则**（本项目最有价值的一条产出，照抄）：
  *连续两次治理动作而没有产生任何运行时观测 = 死锁，删掉那个阻塞者。*
- 治理税必须与改动大小成比例。改 12 行就该是一次提交，没有前置仪式。
- 任何流程规则上线前问一句："它挡住的错误，历史上真的发生过吗？"
  没发生过就不要加。**本项目大部分治理机制防的是从未发生的问题，
  而真正发生的失败（仪器泄漏、门槛不可能、宿主报废）它一条也没挡住。**

### L7 在任何有效测量之前就冻结了数值目标

> 完整版：`docs/engineering/POSTMORTEM_MEASURE_BEFORE_FREEZE.md`。此处只留结论与代价。

**症状**：`+5pp` 的提升门槛钉在 G02 实测的 `deterministic 0.500` 与 live `0.000` 上。
后来查明 `0.500` 来自规则表缺陷、`0.000` 是标签格式 artifact——**门槛被钉在两个仪器故障读数上**。
治理层的"已冻结，只能提高"把一个经验猜测变成了不可下调的规则。
终局是 `max(0.70, best+0.10)` 要求 `core_e2e >= 1.0167`：**在单位区间上无解**。

**可数代价（实测）**：3 个 metric 版本、7 份修正案、AMD-0007 的 8 个补丁段、
8 个 `-invalidated-*` 目录、r1–r9 中 3 轮作废。全部花在修同一个东西上。

**下一个项目怎么做**：
- **冻结定义，不冻结未知数。** 程序、安全边界、失败语义、`diagnostic_only`
  这类定义早冻是对的。**引用某个实测量的数值目标**在拿到一次可信测量之前
  写成"待定，由第一次通过有效性检查的运行确定"。
- 上线前顺序：**泄漏探针 → 分化度 → 披露对称性 → 才买 trial。**
  本项目最有效的诊断是零模型成本的单特征多数投票分类器，
  它本该在第一轮之前跑，而不是第五轮之后。
- **冻结的目标变成数学上不可能，是设计缺陷的信号，不是待满足的指标。**
  出现就停下报告，不要去凑。
- 预登记预期，然后如实记录被否证。**重算不等于实测**——把这句写进预登记，
  事后就无法重新解释。

### L8 仪器在测量自己，而失效方式是让门"通过"

**症状**：三代泄漏。v1 无条件写入 `working_set` 键；v2 六个证据组的**存在性签名**
本身就编码了答案；v3 去掉泄漏后任务饱和——数值通道退化成一张六路查找表。
09-11 加宽观测域后 D1 从 0.9062 升到 **1.0000**：改动让任务**更容易**，不是更难。

**披露不对称（本项目最危险的一条）**：对照臂按构造直接拿到答案，
被测臂必须自己推断。这个比较是无效的，**而它的失效方式是让门 PASS，不是 FAIL**。
r8 的"ready"就是这样产出的——制造那个"显著"的，恰是它本该检出的缺陷。

**可数代价（实测）**：整个 44 天空洞期基本都在这上面。3 代 metric、3 轮作废、
8 个失效目录，约 6.36 CNY 模型花费里有超过一半买的是无效对比。

**下一个项目怎么做**：
- **评测器先于被评测者。** 写完 metric 立刻问：如果被测对象是一个只会
  猜最频繁标签的常量函数，这个 metric 给它多少分？给高分就说明 metric 坏了。
- **披露对称性作为硬检查项**，每次改 metric 都重跑：所有被比较的臂拿到的
  信息必须等价。
- **任何让指标变好的改动都要先当成泄漏来查**，而不是先当成进展来庆祝。
  "加宽观测域后分数上升"的第一解释永远是仪器，不是能力。
- 零成本探针（泄漏、分化度、级联）在花任何模型预算之前跑完。

### L9 证据活在 gitignored 目录里，于是历史上出现了一个 44 天的空洞

**症状**：`.audit/**` 是 gitignored。r1–r9、metric v2/v3、ADR-0016/0017/0018、
宿主报废与更换、8 个失效运行——**项目中最贵的诊断工作全部发生在
git 历史看不见的地方**。`git log` 在 07-27 到 09-08 之间是一片空白。

这直接违反项目自己的规则。`AGENTS.md` 原文：*eval 产物必须入 git……
产物不入库 = 证据不存在。*

**可数代价（实测）**：44 天工作在版本历史中不可见。61 个 `EVAL-*` 目录里
只有 44 个有 `artifacts/`——**17 个目录的产物已经无法核对**。
复盘时这段只能靠 `.audit/` 的本地残留重建，而 `.audit/` 一旦丢失就不可恢复。

**成因（推断）**：`.audit/` 被 gitignore 是为了避免仓库膨胀，
这个理由本身合理。错在没有配套的**摘要入库**通路：大产物不入库，
但每轮的结论、digest、样本数、区间必须入库。两者被当成一个决定处理了。

**下一个项目怎么做**：
- 大产物可以不入库，**每轮的结论摘要必须入库**：样本数、digest、
  关键指标、置信区间、是否作废及原因。一个文件、几十行，成本极低。
- 每天至少一次提交，即使只是一行日志。**版本历史的连续性本身就是资产**——
  它是你复盘时唯一不会撒谎的东西。
- 失效证据用 `-invalidated-*` 重命名 + `INVALIDATION.md`，**不要删**。
  这条本项目做对了，8 个目录都还在，是这次复盘能做的原因。

### L10 硬件与基础设施风险被吸收进了关键路径

**症状**：宿主机（13/14 代 i9）出现硬件级 kernel panic——RIP 散落数十处、
出现在 `swapper`/`kswapd` 纯内核上下文。ADR-0016 记录内核从 5.15 回退到 5.8，
ADR-0017 记录整台宿主报废更换，**旧宿主产出的全部 readiness 证据不可与新宿主比较**。

**可数代价（实测）**：一次完整的证据基线作废。加上 ADR-0018 撤回 `+0.10` margin
（锚定读数全部无效），意味着**换机之前的所有 readiness 测量都白做了**。

**成因（推断）**：项目把"自建 K3s 集群 + 30 个 digest 钉死的镜像 + 单台物理机"
放在了关键路径上，且没有第二条路。单机就是单点，而这个单点恰好是一颗
有已知 Vmin-shift 退化问题的 CPU。

**下一个项目怎么做**：
- 关键路径上**不要放你自己维护的物理机**。托管服务贵一点，但它的故障
  不会消耗你的项目周期。
- 如果必须自建：装机时就确认微码版本（本项目的教训是 i9 需 ≥ `0x12F`），
  并且**准备第二套可运行环境**，哪怕能力打折。
- 基础设施故障可重试，metric failure 是阻塞的——**两者别混**。
  本项目一度把宿主崩溃当成实验失败来分析，浪费了归因。
- 让实验设计对**换机**免疫：每轮记录环境指纹，跨环境比较必须显式声明并重测基线。

### L11 工装长成了产品的 3.3 倍，而产品的核心能力一行没写

**症状**：`src/faultwitness_dev/`（实验工装）19,254 行，
`src/faultwitness/`（产品）5,819 行。同时 `/v1/tools` 与 `/v1/skills` 都 `return []`，
`src/` 下**没有 `agent/` 包，也没有 `tools/` 包**。

也就是说：一个"故障诊断 Agent 平台"，写了两万行代码来测量它的 Agent，
而那个 Agent 从未存在。

**可数代价（实测）**：19,254 行工装是纯沉没成本——没有 Agent，
测量工具没有对象。667 个诊断文件同理。

**成因（推断）**：这是 L3（代理指标取代真目标）与 L7（先冻数值）的合成结果。
因为门槛先被冻结，注意力被迫转向"如何测出达标"；
而测量比实现更容易产生可见进展，于是工装持续增长，产品停滞。
**没有人在某一天决定不写 Agent，它是被一系列局部合理的决策挤掉的。**

**下一个项目怎么做**：
- **产品先于工装。** 第一版评测就用最粗的手段（人眼看 10 条、
  一个 20 行脚本），直到产品能跑通端到端。
- 设一条**硬比例**：工装代码不得超过产品代码的 50%。超了就停下来写产品。
  这条比例是本次复盘唯一一条我会写进下个项目 CI 的规则。
- 每周检查最核心的那个能力是否**存在**（不是是否完善）。
  `return []` 存在了 52 天没有人拦住它，因为没有任何检查项在问这个问题。

## 4. 下一个项目的开工检查表

按顺序，全部在写第一行代码**之前**完成。任何一项答不出来就不要开工。

**方向**
1. 我要二次开发的开源项目是哪个？它的 CI 现在是绿的吗？我能跑通它的测试吗？
2. 我要解决的具体问题来自哪个 issue / PR / 真实使用场景？（不接受"某份 JD 提到"）
3. 15 分钟面试演示脚本写好了吗？点哪几下、跑哪条命令、讲哪三个决策？

**范围**
4. 人日表加总是多少？除以每天真实可投入小时数，得到几天？
   超过我敢投入天数的 50% 了吗？（超了就现在砍）
5. 主链路是哪一条？侧枝不超过两个吗？
6. 需求总量 ≤ 15 条吗？每条有放弃条件吗？

**技术**
7. 每个组件都能用一行说清"不用它的最简替代是什么、为什么不够"吗？
8. 深挖的那一项是哪个？其余是否都用了最平庸可靠的方案？
9. 数据后端能不能再少一个？

**度量**
10. metric 写完了吗？对一个只猜最频繁标签的常量函数，它给多少分？
11. 泄漏探针、分化度、披露对称性三项零成本检查跑过了吗？
12. 有任何数值门槛引用了尚未实测的量吗？（有就改成"待定"）

**工程纪律**
13. 每轮实验的摘要入库通路建好了吗？（大产物可不入库，结论必须入库）
14. 工装/产品行数比的检查加进 CI 了吗？（上限 50%）
15. 关键路径上有我自己维护的物理机吗？有备用环境吗？
16. 治理规则每一条都对应过一个**真实发生过**的错误吗？

## 5. 尾注：这个项目做对的事

复盘不该只留下否定，有三件事下个项目要照抄：

1. **失效证据不删，改名加 `INVALIDATION.md`。** 8 个 `-invalidated-*` 目录还在，
   这是本次复盘唯一可靠的事实来源。
2. **假设被证伪就明确写下来。** `PLAN.md` 的"已知坑"段落记录了每一个被推翻的假设
   （XMP 超频、5.15 专属回归、stale `nvidia.ko`、"baseline 太强"）。
   留着错误假设比承认它更贵——这条判断是对的。
3. **死锁规则。** *连续两次治理动作而没有产生任何运行时观测 = 死锁，删掉那个阻塞者。*
   这是从 174 次提交里榨出来的一句话，也是整个治理体系唯一值得带走的产物。

最后一句留给整个项目：**它没有失败在难度上，而是失败在从未验证"我在做的事
是否通向我想要的结果"。** 52 天里没有一次检查问过这个问题，
所有检查问的都是"我做的事是否符合我自己定的流程"。
下一个项目的第一条规则就是这个：**每周问一次目标，不只问流程。**
