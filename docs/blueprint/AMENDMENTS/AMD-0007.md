# AMD-0007 — Freeze G03 readiness metric v3

Status: accepted

Date: 2026-07-28

## Decision

Metric v3 is the forward-only G03 readiness instrument. Metric v1, metric v2, AMD-0006, the
seven Gate threshold values, all closed G02 `PLAN`/`REPORT`/`VALIDATIONS` and `EVAL-G02-*`
assets, and historical scores `0.500`/`0.000` and `1.000`/`1.05` remain reproducible and are not
reinterpreted.

This amendment authorizes changes only to:

- `config/g03/baselines-v3.yaml`;
- `src/faultwitness_dev/g03_readiness.py`;
- the explicit v3 route in `src/faultwitness_dev/cli.py`;
- the label-blind readiness collector in `src/faultwitness_dev/g02_lab.py`;
- fail-closed version dispatch in `src/faultwitness_dev/g02_baselines.py`;
- `tests/g03/**` and relevant G02 regression tests;
- `docs/gates/G03/PLAN.md`; and
- `docs/runbooks/G03_BASELINE_READINESS.md`.

It does not start G03. G03 remains `not_started` until a separate decision-complete Master Plan is
frozen.

## Dataset and packet

Every run begins with a fresh replay of all 32 cases. Each case collects five healthy and two fault
windows. Injection, the sealed oracle, and recovery thresholds remain unchanged. The public
collector always queries the same six candidate services and never selects a trace service from the
sealed label.

Every public packet contains the same six non-empty groups:

1. `journey_window`;
2. `trace_activity`;
3. `trace_errors`;
4. `cpu_window`;
5. `memory_window`; and
6. `queue_window`.

The seven window phases and timestamps are recorded once in a packet-level registry. Every evidence
sample refers to a fixed window index. No service, sample, field, or measured value may be removed
to meet a token budget. Evidence IDs are the first 24 hexadecimal characters of
`SHA-256(case_id + NUL + metric_version + NUL + kind)` and contain no label ordinal.

Required evidence is frozen as follows:

- catalog and both payment labels require `trace_activity + trace_errors`;
- CPU requires `trace_activity + cpu_window`;
- memory requires `trace_activity + memory_window`; and
- Kafka requires `trace_activity + queue_window`.

Required and distractor groups are disjoint and cover all six groups. Every case must contain a
source-traceable non-zero distractor. A distractor that meets another root cause's support rule
makes the case ambiguous. Ambiguous case IDs remain in the summary; they are never silently removed.
Any result with `N < 32` is `diagnostic_only`.

Public packets contain no truth, fault stimulus, oracle/evaluator boolean, or label index. Missing
groups, empty groups, fewer than seven samples, and field drift are `dataset_incomplete`.

## Wire and result schemas

Metric version and wire schema version are independent:

- metric 1 uses wire `1.0.0`;
- metric 2 uses wire `2.0.0`; and
- metric 3 uses wire `2.0.0`.

Unknown versions fail before credential reads, network calls, bootstrap, statistics, result
construction, or journal writes. Metric-v3 results are validated against the strict
`RESULT_SCHEMA_V3`, require `metric_version: 3`, a typed root-cause claim, and
`additionalProperties: false`.

## Deterministic definition

The deterministic baseline uses two observable features for each candidate: target-service trace
activity and the candidate's root signal. For the current case, thresholds are derived from the
other 31 cases. Each contributes four consecutive healthy positive drifts, for 124 values per
feature. The threshold is the nearest-rank P99 plus the measurement quantum.

The quanta are:

- count: `1`;
- CPU: `0.000001` cores;
- memory: `4096` bytes (one page); and
- lag: `0.001` seconds.

For a root signal whose healthy baseline is a large non-zero level rather than a floor at zero, the
threshold is `max(healthy_p99 + quantum, relative_floor)`, where `relative_floor` is a registered
fraction of that case's own healthy median. `emailMemoryLeak` is the only such label, at `0.05`.
The fraction is recorded per case in the frozen registry.

Incident excess is `max(two fault windows) - median(five healthy windows)`. Both features must
reach their threshold (`>=`). Candidates are ranked by the weaker standardized excess, then by
lexical label as the fixed tie-break. No candidate yields `unknown`.

### Amendment of 2026-09-05 — deterministic discrimination correction

r5 was the first run to complete the 32-case replay, so the deterministic estimator had never
before run on a complete dataset. It exposed two defects that had never been observable:

1. **Memory had no usable absolute threshold.** 127 of 128 healthy single-step drifts for
   `working_set_bytes` are exactly zero, so the threshold collapsed to the quantum and was then
   compared against an excess accumulated over seven windows. `email` and `fraud-detection` are
   both Kafka consumers, so a queue fault genuinely grows email's working set; four
   `kafkaQueueProblems` cases were therefore flagged ambiguous. The cross-talk is not stable in
   sign — case `SEED-G02-0028` measured `-1,085,440` B on 2026-07-29 and `+135,168` B in r5 — so no
   byte-valued cutoff can work. All 224 memory samples are exact multiples of 4096 with a GCD of
   one page, so the declared `1` byte quantum also overstated the counter's resolution by 4096x.
2. **The candidate rule charged the quantum twice.** `healthy_p99 + quantum` already means "exceeds
   observed healthy noise by at least one minimum resolvable unit"; requiring a strict `>` on top
   demanded a second unit. On an integer counter this discarded genuine signal: of the 15 cases
   whose own true label failed to qualify, 9 failed because the excess exactly equalled its cutoff
   (2 vs 2.0, 1 vs 1.0). All four true `emailMemoryLeak` cases scored `unknown`, so the estimator
   had never once detected a real memory leak.

Both corrections increase discrimination rather than relax the gate, which is the test that
distinguishes a fix from a weakening. On r5, true-label qualifications rise from 17 to 26 of 32
while false-label qualifications fall from 4 to **0** of the 160 non-truth pairs. On the
independent 2026-07-29 diagnostic scan the same change gives 14 -> 19 of 24 true with 6 -> 0 false.
A relaxed threshold would have raised the false count, not zeroed it. The `0.05` fraction was
calibrated on 56 case-measurements pooled from those two runs, where true leaks are `>= 10.39%` of
the healthy median and every non-leak case is `<= 3.87%`; every value in `[0.04, 0.10]` yields zero
false qualifications and zero missed leaks.

Consequences. The deterministic point estimate moves from `0.500` (on 28 scoreable rows) to
`0.8125` with 95% CI `[0.656, 0.938]`. This is a **more capable** deterministic baseline, so it
raises the bar the live arms must clear; `best_baseline <= 0.90` and the `> 0.90`
`task_rule_solvable` mapping are unchanged and are still evaluated on point estimates. Packet bytes
are untouched: `dataset_digest` remains `8f5a628ab1eb5e87fd5846194b8d6792` and both
checkpoint-pinned collector/observer digests are unchanged, so r5's 32 measured trials stay
inheritable and no re-measurement is required. `metric_definition_digest` necessarily changes,
which invalidates resume and requires a fresh preflight directory.

This supersedes the quanta list and the strict-inequality candidate rule above, and closes the
second form of the defect AMD-0006 first recorded as "the ambient `working_set` field intercepted
three unrelated fault classes": metric v2 removed the presence shortcut but left the same ambient
signal able to intercept through a magnitude cutoff.

This formula may not read injection-oracle constants, truth, a label index, or an evidence suffix.
Its canonical definition and `RESULT_SCHEMA_V3` digest are hashed into
`metric_definition_digest` during preflight. Live resume recomputes the definition from current
code and configuration and rejects any mismatch before model use.

## Live arms and budgets

The registered arms are:

- deterministic: once per case;
- `no_rag`: one turn; and
- `naive_react`: two to four turns, stopping after two consecutive canonical diagnoses match.

`naive_react_single` runs as an unregistered ablation with the same prompt and packet. It never
participates in `best_baseline` or readiness.

Every live arm uses cumulative input budget `65,536`, cumulative output budget `8,192`, and maximum
completion output `2,048`. These are trial budgets, not per-call budgets. `max_tool_calls: 6`
remains an explicit G03 `tool_contract_matrix` obligation and is not implemented here.

Preflight calculates a conservative four-turn input upper bound for every real packet. UTF-8 bytes
upper-bound static content; every message adds 64 tokens; every request adds 256 tokens; and each
prior assistant draft contributes the full 2,048-token maximum to every later request. The sum must
not exceed `58,982`, retaining at least `6,554` tokens of headroom. A failure blocks live. The only
permitted correction is removing repeated representation metadata without removing measurements;
the budget may not be raised.

`budget_exhausted`, `output_truncated`, and `malformed` are distinct scored failures.
`budget_exhausted` remains in the denominator and is not retried. Transport, fallback, route, and
abnormal termination failures are not valid denominator entries and must be resumed.

## Statistical acceptance

All intervals use 2,000 percentile bootstrap samples clustered by `case_id`; paired intervals align
on `case_id + repetition`.

Readiness requires all of:

1. `best_baseline <= 0.90`;
2. complete six-group packets, presence-only Top-1 exactly `8/32`, and Top-3 at most `20/32`;
3. the paired difference between deterministic and at least one registered live arm excludes zero,
   in either direction;
4. every registered baseline has a non-zero-width interval, complete trial counts, and no
   arm-wide configuration or budget failure; and
5. the three registered point estimates are not exactly equal.

Live-live ordering, `naive_react - no_rag`, the observed baseline ordering, and the multi-turn delta
are findings only.

The initial live run is three repetitions per case. Repetitions four and five are authorized only
when every other hard condition passes and deterministic-vs-live significance is the sole blocker.
Five repetitions are final.

Blocked reasons short-circuit in this order:

1. residual presence leakage: `leak_not_eliminated`;
2. incomplete execution/data or exact equality: `unclassified`;
3. `no_rag > 0.90`: `dataset_too_easy`;
4. `deterministic > 0.90`: `task_rule_solvable`;
5. significance alone: `instrument_underpowered`; and
6. any other condition: `unclassified`.

`task_rule_solvable` is a finding, not permission to weaken deterministic. It requires a G03 scope
decision about where an Agent adds value. `dataset_too_easy` points forward to the G07 160-case
adversarial and time-split dataset. Neither condition authorizes case tuning.

## Execution boundary

`--skip-live` and live use one target directory. Preflight performs the only privileged replay,
writes scenarios, configuration/AMD/source/checkpoint identities, metric definition, deterministic
results, presence and ambiguity diagnostics, and token headroom, then stops without model calls.

Live can enter only through `--resume` in the same directory. It must verify the exact scenarios
artifact, dataset/config/AMD/source/metric-definition digests, and producer/SUT/checkpoint
identities. An `invalidated/` path, including link or `..` resolution into that tree, is never a
resume source.

Any code, configuration, AMD, packet, or metric-definition change after preflight requires a new
empty directory and a new fresh replay. Execution, preflight, readiness, and blocked reason are
separate fields. Evidence is atomically saved before a blocked command exits non-zero.

## 2026-07-29 collector pod-pinning defect appendix

This appendix freezes the correction of a metric-v3 implementation defect discovered before the
32-case frozen replay completed. It does not create metric v4, alter any of the seven Gate
thresholds, change an injection oracle, remove a case, or relax a fault-state predicate.

### Decisive diagnosis

After `_reset_email_runtime()` recreated pod `email-846bdcbfb9-wtmzz`, the readiness poll observed:

| Poll | Wildcard memory | Exact-pod memory | Matching series |
|---|---:|---:|---:|
| 1 | 45,985,792 bytes | unavailable | 1 |
| 2 | 45,985,792 bytes | unavailable | 1 |
| 3 | 45,985,792 bytes | 3,911,680 bytes | 2 |

The first two polls therefore had a wildcard value while the current pod had no cAdvisor sample.
At the third poll and the first two 30-second samples, the wildcard remained 45,985,792 bytes while
the exact current pod was 3,911,680 bytes. At the third sample the wildcard was still 45,985,792
bytes while the exact pod had reached 44,498,944 bytes; two series remained. This confirms that the
wildcard `max` could select a stale pod series and mask the current pod's memory growth. The
diagnostic, including its readiness-poll trace, is stored as non-Gate evidence under
`.audit/g03-readiness/diagnostic-collector-pod-pinning-readywait-20260729T111227Z/`.

### Collector correction and sampling decision

The metric-v3 collector now resolves the current non-terminating `email-` and `ad-` pod on every
sample for every fault class. Exactly one pod must resolve for each workload; zero or multiple pods
fail closed. CPU and memory queries use exact pod equality and never fall back to a wildcard. Pod
resolution and the six-service trace query shape are independent of the sealed fault label.

Sampling option A is preregistered: the interval between the two fault windows is 65 seconds for
all six fault classes, which is at least two 30-second scrape periods. The 90-second activation
deadline, the email memory minimum growth of 1 MiB and 5%, all other injection-oracle thresholds,
and the two-conjunct email fault-state rule are unchanged.

The collector checkpoint advances from
`g03-readiness-v3-label-blind-six-group-collector-v1` to
`g03-readiness-v3-label-blind-six-group-collector-v2`. Its semantic cache key is bound to a
source-validated collector contract rather than a manually copied version string. A journal from
the prior checkpoint cannot be inherited by the corrected collector.

### Exhaustive v1/v2-to-v3 difference review

The review classified these intentional v3 changes: a fixed six-service trace query instead of a
fault-selected service; six service maps instead of scalar trace counts; unconditional fraud-log
collection; service-scoped public trace-error groups with normalized connection phrases; and five
healthy windows. It identified the lost exact-email-pod selector as the confirmed defect and the
analogous ad CPU wildcard as the same latent defect.

It also found that the private oracle path had loosened whole-trace semantics: selected-service
descriptions/error spans were aggregated differently, and `paymentUnreachable` no longer required
the checkout error, `Payment Charge`, and connection marker in one trace. The corrected collector
keeps its public six-group output service-scoped but separately computes those private oracle
signals with the v1/v2 whole-trace correlation. The stimuli, email reset, first fault sample,
fault/recovery sleeps, deadline, and recovery checks remained inherited and were not lost.

The machine-readable classification and the reviewed commit list are stored beside the decisive
diagnostic as `COLLECTOR_DIFFERENCES.json`.

### Digest freeze

The prior incomplete run used metric-definition digest
`e32eee324a262eded7a3edfc04eb5efaf529d779f82359f2432e3d586c517594`.
That definition did not bind collector source semantics. The corrected definition includes a
source-validated collector contract, its 65-second fault-sample interval, and the exact-pod
selection contract. Its frozen metric-definition digest is
`359908105c3ea78a3882eeb1a3a61ee51161470f7c2a91c8e1edf6933d295abe`.

The prior run is invalidated in place and may not support a Gate conclusion. Its seven completed
packets retain only the narrow structural use recorded in their invalidation notice: confirming

truth mapping. The corrected frozen replay must start in a new empty directory and collect all 32
cases.

## 2026-07-29 runner false-negative and failure-attribution appendix

The two preceding appendices each corrected one instrument defect. This appendix records that the
remaining blocker is not a third instrument defect but a property of the runner itself: the fault
window never drove the workload it measured, so activation depended on whether ambient
load-generator traffic happened to arrive inside the deadline. It corrects that, plus the four
structural gaps that made each failure cost an entire round to explain.

Metric version remains 3. No Gate threshold value, adapter, `fault_state` predicate,
`recovery_state` predicate, the 90-second activation deadline, the 65-second fault-window interval,
or the 32-case denominator changes.

### Decisive diagnosis

The frozen collector-v3 replay (`b45ddadb…`) failed at `SEED-G02-0001` (`kafkaQueueProblems`) at
12:55:30. An isolated diagnostic re-run of that same case at 12:57, under the same
metric-definition digest, **passed** (consumer lag 27.0 then 87.0, `kafka_error` true in both
windows). `SEED-G02-0015` (`adHighCpu`) and `SEED-G02-0008` (`emailMemoryLeak`) likewise passed on
isolated re-runs. A case that passes on re-execution under an unchanged definition is a runner
false negative, not a candidate failure.

The repository had already reached this conclusion twice. `docs/evals/EVAL-G02-036/REPORT.md`
records that consumer lag "remained zero during the frozen 90-second deadline and became positive
only after incidental load-generator checkout traffic arrived. The runner did not create a
deterministic Kafka workload after injection. This is a runner-control defect, not an
infrastructure failure." `EVAL-G02-042` attributes both payment branches to the same cause and
identifies the single ambient load user as the exposing condition.

The code confirms it. The 90-second fault poll loop never re-drove the workload it measured:
`adHighCpu` and `emailMemoryLeak` stimulated once per fault *call*; `kafkaQueueProblems`,
`paymentFailure`, `paymentUnreachable`, and `productCatalogFailure` stimulated once per *case*, in
the `fault_started is None` branch only. No class re-stimulated on a poll tick.

Two mechanisms follow, both false negatives:

- **A — the fault window carried no load.** `SEED-G02-0001` (kafka poll staleness never rose),
  `SEED-G02-0015` (ad CPU never lifted inside a two-minute rate window).
- **B — the recovery predicate was unsatisfiable inside 90 seconds.** `SEED-G02-0008` was first
  blocked with `recovery oracle did not reach HEALTHY` and passed on the second attempt: the email
  process does not return memory to the OS immediately after the flag resets, while
  `signal_not_worsening` requires growth below tolerance.

### Correction 1: the fault window drives its own workload

Metric v3 now issues exactly one candidate-bound request for the sealed label on every poll tick of
both the fault and recovery windows, symmetric across all six classes. The v1/v2 observer keeps its
prior behaviour through a class-level contract (`restimulate_each_poll`).

**This strengthens rather than relaxes the oracle.** All six `fault_state` predicates and all three
`recovery_state` conjuncts are byte-for-byte unchanged. Repeated stimulus can only remove false
negatives: with the flag off, checkout succeeds, no error span is recorded, fraud-detection keeps
polling, and the ad service does not spin, so no additional request can make a predicate true. This
is asserted mechanically, per label, in
`tests/g02/test_g02_lab.py::test_repeated_fault_stimulus_cannot_manufacture_a_false_positive`: the
window polls and re-stimulates repeatedly with the flag off and the oracle must stay non-active for
all six classes.

This is the second half of a correction already accepted under `EVAL-G02-036`/`EVAL-G02-042`, which
classified the same phenomenon as a runner-control defect and added explicit `_stimulate_checkout`
calls for kafka and payment. Those calls fired once per case; this completes them to once per poll.
It also removes the implicit dependence on `LOCUST_USERS=1` without changing any environment load
setting.

### Correction 2: a failed case explains itself

The failure path recorded only `{scenario_id, fault_class, reason}`, so every failure required a
separate live diagnostic run — and a re-run is a different sample, which means the original failure
could not be explained at all. The runner now attaches to the raised error, and persists into the
journal payload, the healthy windows, whichever fault and recovery observations were obtained, and
the per-observation truth of every predicate term for that label (for kafka: `consumer_lag`,
`baseline_lag`, `kafka_error`, `kafka_log_error`, `kafka_fault_log`, `error_spans`). The diagnostic
`RecordingObserver` under `.audit/g03-readiness/` had already proved these values were obtainable;
the official path simply discarded them.

### Correction 3: the primary cause is no longer masked by cleanup

Cleanup errors were raised ahead of the primary error, so a fault-oracle failure combined with
recovery flapping reported only the recovery symptom — the exact shape of `SEED-G02-0008`. The
primary error is now reported first, with the cleanup failure carried alongside it in the same
message and in the persisted diagnostics.

### Correction 4: absent series are infrastructure, not observed zeros

The v3 collector coerced an empty PromQL result to `0.0`, feeding a synthetic zero into a
fault-state predicate and producing a non-retryable `metric_fail`. It now reports an absent series
as null and names it in `absent_series`. A null in a series the sealed label actually reads raises
`InfrastructureFailure`, which AMD-0003 already authorises for unlimited attributable retries;
metric failures remain blocking, and no retry budget is added. During the control phase an absent
series is treated as the expected post-restart transient and polled for, not failed closed. Because
all six evidence groups must be present for every label, a null can never be projected into a
packet: doing so only for the labels whose series happened to be absent would itself leak the
label.

A probe confirmed the direction of this change is safe: `kafka_consumer_records_lag` and
`kafka_consumer_last_poll_seconds_ago` both return real series with full label sets and value `0`,
so the pervasive zeros in the frozen evidence are genuine measurements, not absent series.

The mirror defect is corrected in the same pass. `LiveReadinessObserverV3._sample` rewrapped **all**
`GovernanceError` as `InfrastructureFailure`, laundering the deliberately fail-closed
`FW_G03_COLLECTOR_POD_CARDINALITY` refusal into the unlimited-retry class. Markers prefixed
`FW_G03_COLLECTOR_` now propagate as `GovernanceError`, following the existing
`FW_G02_STIMULUS_HTTP_ERROR` exemption.

### Correction 5: the recovery deadline is named and pre-registered

The 90-second **activation** deadline frozen by this AMD is unchanged. The recovery observation
deadline and the spacing between the two recovery samples were never pre-registered: the spacing
was a hardcoded 30 seconds, inconsistent with the pre-registered 65-second fault spacing. Both are
now named constants bound into the collector contract: a 240-second recovery observation deadline
and 65-second recovery spacing. The three `recovery_state` conjuncts are byte-for-byte unchanged —
what changes is how long the runner waits before declaring cleanup unprovable, not what counts as
clean. Mechanism B closes here.

### Diagnostic scan mode

`--continue-on-case-failure` is added for diagnosis only and requires `--skip-live`. Default
behaviour is unchanged: readiness evidence still requires abort-on-first-failure and a single clean
32-case replay. Under the flag, failing cases are recorded and skipped, the remaining cases still
run, and every case's outcome is written to the journal. Products are stamped
`diagnostic_only: true` and `promotable_to_gate_evidence: false`, and are refused as a `--resume`
source. This AMD already declares that "Any result with `N < 32` is `diagnostic_only`"; the flag
only makes such a result something the runner can deliberately produce. **A diagnostic-mode product
may never be promoted to readiness evidence.**

### Correction 6: an absent series is waited out, not failed on first sight

Correction 4 classified an absent series as infrastructure rather than an observed `0.0`, which is
right, but the first implementation raised on the **first** incomplete sample. The diagnostic scan
immediately produced a fifth false negative from that choice: `SEED-G02-0001`
(`kafkaQueueProblems`) failed with `absent Prometheus series: cpu_rate`, a series that label's
predicate never reads. A read-only probe taken minutes later showed the series present and healthy
(`sum(rate(container_cpu_usage_seconds_total{pod="ad-68d778b69-pp57j"}[2m]))` → one series, value
`0.00146`; the pod Running since 2026-07-25; 79 cAdvisor CPU series in the namespace). The absence
was a transient scrape gap, and failing the case on it is the same class of defect this round exists
to remove: a runner-manufactured failure on a case that would otherwise have passed.

The corrected rule separates *unscoreable* from *failed*. Because the packet must carry all six
evidence groups for every label, the wait is deliberately **label-blind**: a window is unscoreable
until every series is present, regardless of which one the sealed predicate reads. Waiting on the
sealed label's own series instead would make the poll count a function of the label. Each phase
polls at the existing five-second interval, re-driving its workload per tick, and only raises
`InfrastructureFailure` for a series still absent at that phase's already pre-registered observation
deadline. No predicate, deadline, interval, or floor value changes; the fault, recovery, and healthy
windows all follow the rule the control phase already followed. `_public_window`'s null check is
retained as a residual invariant behind that wait, not as the live failure path.

This correction can only remove false negatives. A series that is genuinely missing still fails as
`InfrastructureFailure` at the deadline, which AMD-0003 authorises for unlimited attributable
retries; nothing converts a metric failure into a pass, and a synthetic `0.0` is still never scored.

## 2026-07-29 ad-baseline quiescence appendix

The first complete 32-case diagnostic scan under metric-definition digest
`0e6e7565ec2f44d657012d9ab2712b2abff1fce5e42921bcbf36bea6965d82c5` returned 24 `pass`,
7 `infra_failed`, and exactly 1 `metric_fail`. All seven infrastructure failures were SSH transport
(`connection_refused` on `SEED-G02-0023` through `SEED-G02-0027`, `connection_timeout` on
`SEED-G02-0008` and `SEED-G02-0030`) in two outage windows; the host was confirmed reachable
afterwards with all 25 pods present. AMD-0003 authorises unlimited attributable retries for that
class, so they require re-execution, not a correction. This appendix addresses the single metric
failure.

### Correction 7: the ad baseline is measured on a quiesced pod

`SEED-G02-0015` (`adHighCpu`) recorded `baseline_cpu_max = 2.243332663338218` and then failed with
`fault oracle did not reach FAULT_ACTIVE` against fault readings of 4.0013 and 4.0011 cores. That
baseline is byte-identical to the final recovery sample of `SEED-G02-0014`, taken 34 seconds
earlier. The ad CPU query is a 2-minute `rate()`, so case 14's burn was still inside case 15's
baseline lookback. Against the frozen `AD_CPU_ACTIVE_MULTIPLIER` of 5.0 the activation bar became
11.2 cores, which the pod cannot reach — it saturates near 4.

The exposure is structural, not incidental. `recovery_state` requires only that the signal is not
worsening, never that it returned to rest, so **every** `adHighCpu` case ends with the pod mid-decay
at roughly 2.24–2.45 cores. Whether the next `adHighCpu` case fails then depends only on the gap
between them: 25 minutes (case 3 → 11) and 12 minutes (11 → 14) were clean, 6 minutes (14 → 15) was
not. With a two-minute lookback, anything under about three minutes of quiet is unsafe. This is
deterministic and will recur whenever two `adHighCpu` cases land close together. `emailMemoryLeak`
is immune because it deletes and recreates its pod before sampling; `kafkaQueueProblems` is far less
exposed because its predicate compares against the baseline without multiplying it. `adHighCpu` is
the only label that combines an unreset baseline with a multiplier, which is exactly why it is the
only label that failed.

The correction requires the metric-v3 control phase to observe a quiescent ad pod before sampling
the baseline: CPU at or below `0.25` cores, polled at the existing five-second interval, with a
240-second deadline. Idle was measured at `0.002` cores in every passing case, so the ceiling sits
far above rest and far below any contaminated reading. A pod that never settles raises
`InfrastructureFailure`, a lab condition rather than a candidate verdict.

Waiting can only remove false negatives: a quiesced baseline is a *lower* baseline, so it can never
make an inactive fault appear active. `AD_CPU_ACTIVE_MIN_CORES`, `AD_CPU_ACTIVE_MULTIPLIER`, every
`fault_state` and `recovery_state` predicate, all seven quality-floor values, the six adapters, the
90-second activation deadline, the 65-second spacing, and the 32-case denominator are unchanged.
Capping the multiplier or lowering the floor to make this case pass would be the unauthorised
weakening that `docs/runbooks/G03_BASELINE_READINESS.md` forbids, and was not done. Metric v1/v2
keep their recorded behaviour: the wait is opt-in via `require_ad_cpu_quiescent_baseline`, false on
`LiveScenarioObserver`.

## Amendment of 2026-09-05 (second) — the live prompt must state the evidence contract it is scored against

### The defect

`core_e2e` requires a diagnosis to name the correct root cause **and** cite every required
evidence ID **and** cite no distractor. `REQUIRED_KINDS` pairs `trace_activity` with a
label-specific kind for all six labels, so `trace_activity` is required in all 32 cases and
`|required_evidence|` is exactly 2 everywhere.

`build_baseline_prompt_v3` never stated that the evidence set must be **complete**. It asked for
IDs that "directly support" the diagnosis, and its only concrete shape example carried a single ID
(`"evidence_refs":["<supporting evidence ID>"]`). `RESULT_SCHEMA_V3` permits `minItems: 1` on both
`evidence` and `evidence_refs`. The four-turn recheck prompt adds no evidence guidance either.

r8 measured the cost. All three live arms cited `trace_activity` in a small minority of trials
(`naive_react` 16/96, `no_rag` 18/96, `naive_react_single` 13/96) while naming the correct root
cause in 94.8-96.9% of trials. `missing_required_evidence` accounted for 77% of scored failures.
Turn telemetry shows the multi-turn arm cannot recover: all 96 `naive_react` trials terminated
`stable_diagnosis`, 95 of them after exactly two drafts with **identical digests** — the recheck
turn restates rather than revises, because it supplies no criterion to revise against.

The asymmetry is what makes the comparison unsound. `deterministic_baseline_v3` builds its evidence
list as `sorted(evidence_id_v3(case_id, kind) for kind in REQUIRED_KINDS[root])` — it receives the
required set **by construction** and never infers it. The live arms were scored against a convention
only the comparison arm was exempt from having to discover. `trace_activity` is never any case's
distractor and carries data in 32/32 cases, so citing it is risk-free: this was not a
precision/recall trade the arms were navigating but a rule they were never told.

### The correction

`build_baseline_prompt_v3` now states that `evidence` must be complete as well as correct, that it
must include the trace observation localising the failing service, that a right-cause diagnosis with
an incomplete evidence set is scored as a failure, and that most incidents require more than one
observation ID. The shape example becomes `"evidence_refs":["<ID>","<ID>",...]`.

**Not changed:** `REQUIRED_KINDS`, `score_result_v3`, the `minItems` bounds, any threshold, any
quality-floor value. The rubric is unchanged; only its disclosure changes.

**Deliberately not done:** the prompt does not name `trace_activity` or any evidence kind. Naming
the required kinds would hand the live arms the same answer key `deterministic_baseline_v3` holds and
destroy the inference the metric exists to measure. A regression test asserts no `EVIDENCE_KINDS`
member appears in the prompt.

### Why this is a correction and not a weakening

The rubric is defensible on its own terms: an SRE who names the smoking gun without localising the
failing service has given an incomplete diagnosis. What was not defensible was scoring against a
rubric the prompt withheld while exempting the comparison arm from inferring it. The fix discloses
the requirement; it does not relax the scorer, and every previously-scored trial would score
identically under the unchanged scoring code.

### Cost against the token bound

The four-turn upper bound counts `system_bytes` once per request, so added prompt length costs
roughly 4x itself. The correction adds 346 bytes. Recomputed over all 32 packets:
`status pass`, `max 57778` against `FOUR_TURN_INPUT_LIMIT 58982`, `p95 56494`,
`headroom_at_max 7758` against `REQUIRED_INPUT_HEADROOM 6554`, `blocked_case_ids []`.
No token constant was touched.

### Pre-registered expectation, recorded before the measurement

Recomputing r8's existing answers with the required ID added scores the three live arms at
0.9688 / 0.9479 / 0.9583 — all **above 0.90**. The judgement chain therefore predicts
`best_baseline_above_0_90` and `blocked_reason: dataset_too_easy` on the corrected round. This is
recorded in advance so the outcome cannot be reinterpreted after the fact.

That prediction is a **recomputation, not a measurement**. Being told to cite completely raises the
chance of citing a distractor, which is a hard failure (r8 already had 3/74), so the measured values
may fall below the recomputed ones and cannot be assumed to stay above 0.90. Only the corrected live
round settles it.

If `dataset_too_easy` is confirmed, the honest reading is that the packet-fed six-way classification
task is saturated — not that the instrument failed. Remedies belong to a future amendment and must
change the task, not the thresholds: text-blinded packet variants, agent-collected rather than
pre-assembled evidence, an open label set, or a redesigned distractor construction. Capping the
target, excluding the winning baseline, or lowering a floor remains prohibited.
