# AMD-0004 — Remove Preset Execution Kill Timeouts

Status: accepted

Date: 2026-07-23

Owner: project owner

## Context

I-0017 used a 900-second Kubernetes rollout deadline and an outer 1,200-second process deadline. A
workload that legitimately needs longer can never pass under that protocol, regardless of how many
attributable retries AMD-0003 permits. Repeating a prematurely killed run does not create better
evidence and can misclassify normal progress as infrastructure failure.

## Amendment

- Normally progressing fetch, transfer, import, infrastructure, rollout, Iteration Eval, Gate
  phase, and external-tool execution has no preset wall-clock kill timeout.
- Duration estimates and phase start/progress timestamps remain mandatory observability and budget
  reconciliation data. Exceeding an estimate is not a failure or cancellation condition.
- A run ends only on pass, an explicit terminal failure, a verified no-progress condition with the
  last observed progress retained, or project-owner cancellation. A deterministic failure is fixed
  before retry; an unexplained long duration is not itself a deterministic failure.
- Future Iteration and Gate plans may declare expected duration but must not turn it into a process
  kill deadline or an implicit quality threshold.

## Metric isolation

This amendment changes orchestration only. It does not change validation sample counts, statistical
methods, the 95% bootstrap CI, Scenario DSL detection/recovery windows, latency or performance
metrics, seven frozen quality floors, paid-model token/cost ceilings, trial-internal retry counts,
fallback adjudication, cleanup semantics, zero-tolerance criteria, or any Gate pass criterion. A
metric or policy failure remains blocking even when the process that produced it was allowed to run
without a wall-clock kill timer.

## Impact

G02 rollout and evaluation runners wait while work is progressing, even when actual duration exceeds
the plan estimate. Operators diagnose explicit terminal states or verified no-progress evidence
instead of repeatedly changing arbitrary timeout values. Closed G01 evidence and historical runner
behavior are not rewritten; this protocol governs active G02 and later Iteration/Gate execution.
