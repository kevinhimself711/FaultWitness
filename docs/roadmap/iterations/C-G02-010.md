## Root cause

Candidate deployment reapplied the pinned manifest over one long-lived `fw-sut` namespace. The
upstream ten-user load had already produced fleet-wide POST 504 traces, persistent Kafka/PostgreSQL
work, and 62 `accounting` OOM restarts. Kubernetes still reported all Deployments Ready and the node
had no MemoryPressure. Reducing the load to one user did not repair that retained state: the first
C-G02-010 candidate-bound checkout still returned 504.

## Scope

Recreate the disposable `fw-sut` namespace for each candidate without a timeout, rewrite the
dedicated manifest to the minimum nonzero ambient load of one user, retain all candidate/image
checks, and prove the clean setting plus one real candidate-bound checkout with no OOM restart.
This corrective runs no Gate scenario matrix, baseline, or model call.

- Increasing service resource limits or changing pinned images.
- Treating an explicit HTTP failure as resumable infrastructure evidence.

Because namespace recreation and ambient load affect every live surface, the next Gate attempt
preserves only deterministic manifest/G01 debt and reruns 60/6/22 plus all 32 scenario seeds.

## Result

The first candidate-bound seam proved that one user alone did not repair the retained namespace:
24/24 Deployments were Ready, but the single checkout still returned 504. After adding clean
`fw-sut` recreation, the exact candidate deployed 24/24 Ready with one ambient user, flag `off`, and
accounting restart count zero. The one cart and one checkout both returned 200; restart count stayed
zero and the flag stayed `off`. Gate L2 phases, scenario trials, model calls, fallback, threshold
changes, and open evidence are all zero.
