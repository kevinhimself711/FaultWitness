# G00 回顾审查：蓝图、架构与治理基线

## 结论

**关闭有效，但 G00 证明的是"文档自洽"，不是"设计正确"。** 全部退出标准都是文档、schema
与图检查，没有任何一条需要代码运行产生观测。这在 G00 的定位下是合理的——它是立项 Gate。

真实问题不在于它做了什么，而在于它**开销过大且遗留了两处误导**：`REQ-DEV-001` 声称的
八类测试自动化实际是 manifest 声明；14 份 walkthrough 是设计追踪而不是执行证据。

## 一、Master plan 设计评价

### 合理的部分

G00 把"先冻结判据再实施"作为项目第一原则，这一条是对的，而且在后续 Gate 里真实起作用了：
G02 的 7 个 quality floor 数值从冻结到关闭没有漂移过（`validate_threshold_registry` 有相等性检查）。
立项报告 §21.4 点名的失败路径是"先编指标再补实验"，G00 的设计从结构上排除了它。

`REQ-DEV-002`（ADR）落地质量高。`docs/adr/INDEX.yaml` 是真实索引，
change policy 会拒绝没有治理资产的行为变更。这直接对应立项报告 §19.1 的 ADR 清单要求，
也是面试中"你的取舍记录在哪"这一追问的现成答案。

### 过度的部分

G00 建立的 I/C/A 三命名空间 + Eval 生命周期 + candidate binding，是 G02 治理过载的**源头**。
详细成本量化见 [GOVERNANCE_REVIEW.md](../GOVERNANCE_REVIEW.md)：G02 的 46 个 Eval 里
56.5% 被治理与传输机械消耗，12 次 Gate attempt 死于治理管道而只有 7 次死于真实被测对象。

判断：**G00 的治理设计在 G00 自身范围内是自洽的，但它没有对"治理成本随 Gate 复杂度增长"
做任何预算**。这是设计缺陷，不是执行缺陷。现已由 `GOVERNANCE_V2.md` 修正，
G00–G02 归入只读遗留 epoch（`PHASES.md:25-26`）。

## 二、Iteration 划分评价

G00 的 iteration 划分本身没有问题——文档类工作天然可并行、可分块。

但有一个结构性观察：**G00 没有产出任何可执行产物**，因此它的 iteration 划分无法验证
"划分是否得当"这个问题。iteration 边界的价值在于隔离失败影响面，而文档工作的失败影响面
接近于零。这意味着 G00 的划分经验**不能外推**到 G03 及以后。

## 三、退出标准松紧评价

| 退出标准类型 | 数量 | 评价 |
|---|---|---|
| 文档存在性与 front-matter 一致性 | 多数 | 过松，可被"写一份文档"满足 |
| schema 校验 | 若干 | 合适，机器可检 |
| 图检查（依赖/引用闭合） | 若干 | 合适 |
| 需要运行时观测的 | **0** | — |

`REQ-DEV-001`（八类测试自动化）是最松的一条。它的 verification 写的是
"CI manifests prove each test class exists, owns a trigger, and cannot be silently skipped"——
即证明 manifest 里声明了八类，不是证明八类真的会跑。G00 REPORT 记录的三个 CI job
现已缩减为 1 个 advisory job（见 [GOVERNANCE_REVIEW.md](../GOVERNANCE_REVIEW.md) 第二节），
其中 `audit.py` 的 secret 扫描与 GitHub Action SHA-pin 检查失去了前门，
只能通过 `tests/audit/test_audit.py:78` 间接触发。

**这曾是 G00 遗留的唯一真实安全回退。已于 2026-07-28 修复**：`audit.py` 已接回
`verify-fast`（349 tests passed），修法正是在 `verify_fast` 里加一行调用，
没有新建审计生命周期。下面第 1 项补救建议因此已关闭。

## 四、14 份 walkthrough 的性质

G00 的 14 份 gate walkthrough 是本次审查里最需要澄清的一项。

它们是**设计追踪**：逐条走查"如果发生 X，系统会怎样"，产物是推理链而不是执行记录。
这类文档在面试中的价值是真实的——它能回答"你考虑过哪些失败模式"。但它**不能**用来主张
"系统在 X 情况下正确"，因为没有运行过。

G00 REPORT 没有把它们误称为测试证据，措辞是准确的。但 `schemas/governance/gate-walkthroughs.schema.json`
现在是孤儿 schema（`_check_gate_walkthroughs` 在 `schemas.py:270` 定义后从未被调用），
这会让后续读者误以为 walkthrough 仍在被校验。属可选清理。

## 五、需求落点

按 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md) 的分级，G00 承接：

- T2 支撑：`REQ-DEV-002`（ADR）— 已达成，质量好
- T4 绕过：`REQ-DEV-001`（八类测试）— 建议不追求八类齐全，保证 Unit/Contract/Eval/Chaos 四类真实可跑

**G00 没有承接任何 T1 核心需求。** 这是正常的，但也意味着 G00 的通过对"项目是否达到 L3"
没有直接贡献。它的价值是间接的：为后续 Gate 提供判据冻结机制。

## 六、补救建议

按成本排序，只有第一项是必须的：

1. ~~**`audit.py` 接回前门**（S，0.5d）~~ —— **已完成**（2026-07-28）。已接进
   `verify-fast`，349 tests passed，`test_verify_fast_invokes_only_active_local_checks`
   按新的活跃检查集更新而非绕过。
2. **清理 7 个孤儿 schema**（可选）。`schemas/governance/` 下 `carry-in-registry`、
   `claim-registry`、`eval-manifest`、`gate-walkthroughs`、`gate`、`iteration`、
   `validation-registry` 不被任何 active 代码引用，且仍留有已废弃概念的字面定义
   （`iteration.schema.json` 的 `"iteration_type": {"enum": [..., "corrective", "gate_attempt"]}`、
   `eval-manifest.schema.json` 仍 require `candidate_sha`）。它们是"治理已简化"这一事实的反证物。
3. **删除 `_check_gate_walkthroughs` 死代码**（可选）。

不建议做的：重新审查或补强 G00 的文档退出标准。G00 已关闭，且立项报告 §21 没有任何一条
失败路径指向"蓝图文档不够详细"。把精力放在 G03 上收益高得多。
