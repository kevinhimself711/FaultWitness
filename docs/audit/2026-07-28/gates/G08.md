# G08 设计：模型、架构与性能消融

## 本 Gate 是全项目最应瘦身的

按 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md)，G08 有
**1 条 T1 + 2 条 T2 + 6 条 T3**——T3（可降级）密度全项目最高。

`FINAL_PLAN.md:316-326` 列了 **5 组对照**：
deterministic/naive-ReAct/最终 Agent、单 Agent vs Planner-Investigator-Verifier、
静态 vs 动态 Tool/Skill、GLM/DeepSeek/Qwen、RAG/Memory/Reranker/Cache/Batch/Routing。

最后一组本身就是 6 个子对照。全部做完是 13+ 次预注册实验,每次都要求
"至少三次并报告 95% CI"（`FINAL_PLAN.md:365`）。这个规模不现实,而且**大部分是重复劳动**。

## 核心瘦身策略：不重跑前序 Gate 已做的消融

这是本 Gate 设计的关键洞察：**G04 已经做了 RAG、Memory、Reranker、动态 Tool 四个消融**
（见 [G04.md](G04.md) 的 I-02、I-03、I-12、I-14）。如果它们按预注册规范做,
**G08 直接引用其数据,不重跑**。

| 原 G08 对照项 | 处理 |
|---|---|
| RAG 消融 | **引用 G04-I-03**，不重跑 |
| Memory 消融 | **引用 G04-I-08 的 on/off arm**，不重跑 |
| Reranker 消融 | **引用 G04-I-03 的分段增量收益**，不重跑 |
| 静态 vs 动态 Tool | **引用 G04-I-12**，不重跑 |
| Chunk 策略 | **引用 G04-I-02**，不重跑 |
| 压缩 | **引用 G04-I-14**，不重跑 |
| Cache | 保留（G08 新做） |
| Batch | **舍弃**，理由见下 |
| Routing | **保留（按任务路由）**，判断已修正，见下 |
| 三条 baseline vs 最终 Agent | 保留（**核心**） |
| 单 Agent vs 多 Agent | 保留但收窄（见下） |
| GLM/DeepSeek/Qwen | 保留但降级（见下） |

**Batch 的舍弃理由是结构性的**：批处理的收益取决于上游是否支持 continuous batching，
而模型网关只有一个真实上游（Bailian）且不暴露该能力。在单上游下这个对照测不出真实效果，
做了只能得到"无显著差异"，而这个结论无法讲述。
**应显式记录为"因单上游架构不可测量，主动排除"**，这比强行做一个无意义的对照更能体现判断力。

**Routing 的判断已修正为保留。** 第一轮把它与 Batch 一并舍弃，理由是"单上游下
无多 provider 价格/延迟差异"——这个理由只对"按 provider 容灾路由"成立，
对立项报告 §6.5 `:457` 实际要求的**按任务路由**不成立：

> 根据任务路由模型：确定性分类优先规则/小模型，复杂规划和验证才用强模型。

同一个 Bailian upstream 下，`qwen3.7-plus` / `deepseek-v3.2` / `glm-5.2`
三个模型族的**能力与价格本身不同**，所以"确定性分类用小模型、复杂规划用强模型"
这个对照在单上游内完全可测，且它产出的是一个**成本数字**，不是"无显著差异"。

现状是 `RoutePolicy.routes` 的类型为 `dict[ModelFamily, tuple[str, ...]]`
（`models/catalog.py:31`），**只有模型族维度，没有任务维度**——所以这一项是真实增补，
不是已有能力的重复测量。详见 [MODEL_LAYER_REVIEW.md](../MODEL_LAYER_REVIEW.md) 缺口 3。

这处修正使本 Gate 的规模从第一轮的 16-20 天变为 17-22 天（按任务路由 +1-2d），
再加 I-04 的模型族切换演练后为 **18-23 天**。

## 冻结的退出标准（只能提高）

`FINAL_PLAN.md:326` 只冻结了一条,是关于 Multi-Agent 准入的：

> Multi-Agent 进入默认架构必须满足质量提高至少 **5pp**、**95% CI 不跨 0**,
> 且成本和延迟增加不超过 **30%**；或危险建议下降至少 **50%** 且质量不退化。

**这条门槛很可能达不到,而这是预期结果而非失败。** 理由：单机环境 + 160 case + 三次重复,
统计功效有限；5pp 的差异要在 95% CI 不跨 0 的前提下检出,需要的样本量可能超出预算。

`PHASES.md:23` 已明确"负向 baseline 结果可以通过 Gate,前提是实验预注册、执行完整、结论真实"。
**因此 G08 的计划里应当预先声明这个可能性**,而不是到时候被动接受。

预先声明的价值不只是防御性的：立项报告 §0.1 有一条一票否决项是
"使用多 Agent 但说不清为什么单 Agent 不够,也没有单 Agent 对照实验"。
**一个诚实的负结果完全满足这一条**——它证明的是"我做了对照,数据不支持,所以我没用多 Agent"。
这比强行上多 Agent 然后讲不清收益要好得多。§21.7 点名的失败路径正是"为了多 Agent 强行拆分职责"。

## Iteration 划分

### I-G08-01：三条 baseline vs 最终 Agent（M，3-4d）

**T1 核心**（`REQ-BUS-002` 的最终形态）。这是 G08 唯一不可省的对照。

**Eval 与通过标准**：
- deterministic / naive_react / 最终 Agent 在同一 160 case、同一 split 上对照
- 至少三次重复,报告 95% CI（`FINAL_PLAN.md:365`）
- 报告结果、延迟、成本、失败分布四维（`REQ-BUS-002` 的 verification 要求）
- **baseline 必须是去泄漏并已分化后的值**——metric v2 的复测让三条 baseline 同分 1.000，
  那批数不能用作 G08 的对照参照物（见 [EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md) 第 0 节）

### I-G08-02：单 Agent vs 多 Agent（M，3-4d）

**T3 降级**（`REQ-AGT-004`）：按立项报告 §22.2 的口径,
**多 Agent 只保留并行取证与独立验证两种形态**,不做完整 Planner/Investigator/Verifier 编排。

理由：`multi_agent` 主题 JD 64% / 面经 **24%**,且面经里问的主要是
"为什么需要多 Agent"而不是"你的多 Agent 怎么编排的"。两种形态足以回答这个问题。

**Eval 与通过标准**：
- 预注册,同一 case 集,报告负结果（`REQ-AGT-004` 的 verification 明确要求）
- 质量、延迟、成本、无效调用、失败模式五维
- 按冻结门槛判定是否进入默认架构；**不满足则如实记录不进入**

### I-G08-03：独立 Verifier（S，2-3d）

**T2 支撑**（`REQ-AGT-005`，跨 G03/G08）。

**这一项比多 Agent 编排更有价值**,因为它测的是**确认偏误**——
Verifier 不继承 Planner 结论,这是一个具体的、可度量的设计决定。

**Eval 与通过标准**：
- 测量确认偏误、Verifier 假接受率与假拒绝率
- 对抗 case：Planner 给出错误结论,Verifier 是否能独立否决

**依赖 G03**：接口位必须在 G03 预留（见 [G03.md](G03.md) 联动表）。

### I-G08-04：模型族对照（S，2d）

**T3 降级**：`qwen3.7-plus-2026-05-26` / `deepseek-v3.2` / `glm-5.2` 三族对照,
但**必须声明它们共享同一个上游网关（Bailian）**,不是三个独立 provider。

这个声明是本 iteration 最重要的产物。假装有三个独立 provider 会在面试中被问出来
（"你怎么处理不同 provider 的限流差异"),而诚实声明反而展示了对真实约束的理解。

**Eval 与通过标准**：
- 三族在同一 case 集上的质量、延迟、成本对照
- 显式说明单上游架构对该对照的限制
- **附一次模型族切换演练**（第二轮增补，+0.5d）：把默认族换掉，跑一遍 locked 回归。
  §20 Q81 问"旧模型下线如何保证稳定"——升级侧已有真实机制
  （`REQ-EVAL-005` 在 model behavior 变化后触发 locked 回归，G10 I-08 建门），
  但**下线侧只有 ADR-0008 的 "retain a NewAPI-compatible channel" 一句声明，无演练**。
  这一次演练同时给 Q81 与 ADR-0008 提供执行证据，
  见 [INTERVIEW_DEFENSE_COVERAGE.md](../INTERVIEW_DEFENSE_COVERAGE.md)

### I-G08-05：Cache、上下文缩减与按任务路由（S→M，3-4d）

**T3 降级**（`REQ-PERF-004`）：做缓存 + 上下文缩减 + **按任务路由**三项，舍弃 Batch。

**缓存的关键不是命中率，是 Key 的组成。** 立项报告 `:460` 要求
Key 含模型版本、Prompt 版本、输入哈希与**权限范围**。第四维是一条真实的安全边界——
它防止跨租户缓存命中，直接关联 G06 的"跨租户泄漏 0"零容忍标准。
现状 `models/` 目录下 `cache` 零命中，是从零实现。

**Eval 与通过标准**：
- 缓存仅用于纯函数步骤，**一个跨租户缓存命中被拒的负例测试** — 零容忍
- 按任务路由报告成本差异的绝对值与样本数（确定性分类走小模型 vs 全程强模型）
- 上下文缩减报告压缩比与质量变化，质量下降超过阈值即判定该机制不进默认架构

**Eval 与通过标准**：
- 每项优化有 no-optimization 基线和含回退的 Pareto 报告
- 报告 quality/latency/cost 三维,**包含回退**（`REQ-PERF-004` 的 verification 要求）

### I-G08-06：性能与成本对账（S，2d）

**T2 支撑**（`REQ-PERF-001` + `REQ-PERF-003` 的 G08 段）。

**Eval 与通过标准**：
- Trace 导出的瀑布图总和与端到端延迟对账,暴露缺失 span — 零容忍
- 成本报告与 provider usage 对账 — 差异 <1%
- **偿还 DEBT-G01-004** 的最终形态（若 G03 已接走,此处只做验证）
- 报告硬件、并发、数据集、模型、成本、失败分布（`FINAL_PLAN.md:369`）

### I-G08-07：Gate 评测与架构决定（S，2d）

**交付**：每个机制的"是否进入默认架构"判定记录。

**Eval 与通过标准**：
- 每个对照有明确的进入/不进入判定及依据
- **失败 Gate、负实验、rejected architecture 全部保留**（`FINAL_PLAN.md:368`）
- 引用 G04 消融数据的项标明来源,不重跑

## 规模

七个 iteration,约 **18-23 天**（含按任务路由的 +1-2d 修正与 I-04 模型族切换演练的 +0.5d）。

原设计（13+ 次独立预注册实验,各三次重复）估计需 35-45 天。
瘦身的主要来源是**不重跑 G04 的消融**——这要求 G04 的消融从一开始就按 G08 的预注册规范做,
是一个跨 Gate 的设计决定,必须写进 G04 计划。

## 明确不做

- **Batch 对照**。单上游不暴露 continuous batching,不可测量,显式记录排除理由。
- **按 provider 容灾路由**。单 live upstream,不得表述为跨供应商容灾。
  （**按任务路由已改为保留**,两者不是同一件事,见上文）
- **本地推理、Continuous Batching、Prefix/KV Cache**。立项报告 `:839` 写的是
  "根据数据决定是否引入"——条件句,不是要求。单机 K3s + 单张 4090 已被 G09 训练 smoke 占用,
  没有硬件余量。
- **完整 Planner/Investigator/Verifier 编排**。按 §22.2 收窄为并行取证 + 独立验证。
- **重跑 G04 已完成的消融**。引用其数据。
- **超过三次的重复实验**。`FINAL_PLAN.md:365` 要求"至少三次",三次即可。
