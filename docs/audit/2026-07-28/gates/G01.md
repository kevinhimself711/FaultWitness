# G01 回顾审查：平台、契约与 Trace 地基

## 结论

**关闭有效，且这是三个已完成 Gate 中工程含量最高的一个。** G01 测的是真实的平台管道：
OIDC 认证、tenant 边界、Outbox、checkpoint、SSE 续传、span 导出、脱敏。这些都需要代码跑起来
才能产生观测，不是文档检查。

两个问题：**2 条 pass 条件是关于报告措辞而不是系统行为**；**4 笔债务被推给 G02，
其中 1 笔至今无归属**。

## 一、Master plan 设计评价

### 设计正确的关键决定

G01 把 Trace 放在 Agent 之前建。这个顺序是对的，而且是立项报告 §24 明确推荐的顺序
（"建立评测与 Trace；再引入 Agent 决策"）。反过来做——先写 Agent 再补 Trace——会导致
badcase 无法归因，正是 §0.1 的一票否决项。

`TraceSanitizer` 的设计值得单独肯定。`_DENIED_KEY_PARTS` 对 casefold 后的 key 做**子串**匹配
且包含 `token`，因此 `model.tokens.input` 这类命名会被拒。这个严格性在后续会造成摩擦
（指标命名必须迁就它，用 `model.usage.input_units`），但方向是对的：
**宁可让指标改名，不要为迁就指标而放宽 denylist。**

`REQ-OBS-002`（流式）实现完整：SSE 带 `Last-Event-ID` 续传、retention gap 控制事件、
slow consumer 检测（`src/faultwitness/api/app.py:235-297`）。按
[REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md)，streaming 在 JD 与面经的覆盖率
都 ≤5%，是全项目最低——所以这项**已完成即冻结，不再加深**。

### 设计的边界声明是诚实的

G01 明确声明它不测量产品能力。这一点在 REPORT 里写清楚了，没有把平台管道通过
包装成"Agent 能力已验证"。这种边界诚实度在个人项目里不常见，是可以在面试中主动讲的点。

## 二、退出标准松紧评价

G01 的多数退出标准是真实的运行时断言。但有 2 条例外，它们是关于**报告是否包含某段陈述**，
而不是关于系统行为。这类条件的问题是：写下那段话就能通过，与系统状态无关。

这不是伪造——G01 的报告陈述是真的。但作为**退出标准**它是空的，因为它无法失败。
建议在 G03 及以后的 Gate 设计中排除这一形态：**每条 pass 条件必须能被一次代码运行反驳。**

## 三、Carry-in 债务：本 Gate 最重要的审查发现

`docs/gates/G02/CARRY_IN.yaml` 记录 4 笔 G01 债务：

| 债务 | 内容 | 覆盖状态 |
|---|---|---|
| DEBT-G01-001 | 未授权 schema object-prefix 与 observability 访问缺完整可独立复核矩阵 | `covered_by_target_gate`（I-0024 / V-G02-009） |
| DEBT-G01-002 | 六个必需阶段（API/persistence/Outbox/checkpoint/model-stub/export）缺完整 span 矩阵 | `covered_by_target_gate`（I-0024 / V-G02-010） |
| DEBT-G01-003 | Secret 与 PII canary 缺跨全部持久化与出口面的完整可复核证据 | `covered_by_target_gate`（I-0024 / V-G02-011） |
| DEBT-G01-004 | 生产阶段 wall-time 对账缺完整可独立复核执行证据 | **`not_covered`，`owning_iteration: null`** |

关键点：**前三笔债务对应的正是 G01 报告声称已满足的判据。** 也就是说 G01 的通过条件在
"矩阵完整性"这一维度上是有缺口的，缺口被显式记录并推给 G02。G02 确实关闭了这三笔
（`docs/gates/G02/REPORT.md:58-61` 声明 forward closure 且未修改 G01 审计资产），
这个处理方式是正确的——**记录债务并前向关闭，好于假装没有缺口**。

DEBT-G01-004 是唯一至今无归属的。理由写得成立："G02 记录 baseline 客户端 wall-time 与
phase timestamp，但不执行生产 Agent 阶段瀑布图；该主张必须由更晚的 Agent-runtime Gate 拥有。"
G02 REPORT 也没有把 phase timestamp 冒充为该证据。

**但它现在没有 owner。** 它对应 `REQ-PERF-001`（分段延迟，跨 G01/G08）。
如果 G03 计划不显式接走它，它会一直悬空到 G08——而 G08 是按
[REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md) 判断最应瘦身的 Gate，
届时很可能被顺手砍掉。

**补救建议：G03 计划中显式接走 DEBT-G01-004。** G03 是第一个存在真实 Agent 阶段的 Gate，
一旦有 Agent loop，stage-level 瀑布图对账就是自然产物，成本极低。

## 四、需求落点

- T1 核心：`REQ-OBS-001`（Trace 可追溯，跨 G01/G03）— G01 建成地基，G03 才产生可追溯的结论
- T2 支撑：`REQ-SEC-003`（脱敏，跨 G01/G06/G10）、`REQ-PERF-001`（分段延迟，跨 G01/G08）
- T4 冻结：`REQ-OBS-002`（流式）— 已完成，不再加深

`REQ-OBS-001` 是 G01 唯一的 T1 落点，但它在 G01 只完成了一半：**Trace 基础设施存在，
但没有"最终结论"可供追溯**，因为还没有 Agent。L3 门槛第 9 条要求"一次请求能从最终结果
追溯到所有模型、检索、工具和状态更新"——这条要到 G03 才可能真正满足。

## 五、执行到位程度

到位。G01 的问题是**判据设计**（2 条措辞类条件、矩阵完整性缺口），不是执行。
`src/faultwitness/` 现有 5,819 行里，`api / identity / observability / persistence / runtime / state`
六个包都是 G01 产物，且都有真实实现而非骨架。

## 六、补救建议

1. **G03 计划显式接走 DEBT-G01-004**（成本≈0，只需在 G03 的 validation registry 加一项）。
2. **G03 起禁止"报告措辞类"pass 条件**。每条退出标准必须能被一次代码运行反驳。
3. **不要回补 G01 的矩阵完整性**。三笔债务已由 G02 前向关闭，重开会重新引入
   [GOVERNANCE_REVIEW.md](../GOVERNANCE_REVIEW.md) 里量化过的那种治理成本，而系统行为不会变。
