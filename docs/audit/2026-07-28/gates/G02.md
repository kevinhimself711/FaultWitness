# G02 回顾审查：故障实验室与基线

## 结论

**关闭有效。被测对象是故障实验室，实验室确实建成了。** 32 个 case、6 个根因家族、
flagd 注入、digest 钉住的 OpenTelemetry Demo、192 次真实模型 trial、95% 聚类 bootstrap——
这套东西是真的，而且是全项目目前唯一的可信度量地基。

三个问题，严重性递减：**记录的两个分数是 artifact 不是能力信号**（详见
[EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md)）；**VALIDATIONS.yaml 的 artifact 路径
仍指向失败的 EVAL-028**；**PLAN 的 iteration 枚举停在 A-G02-003 从未补齐**。

治理过载成本已单独量化，见 [GOVERNANCE_REVIEW.md](../GOVERNANCE_REVIEW.md)。

## 一、Master plan 设计评价

### 设计正确的核心决定

**先建确定性 baseline，再谈 Agent。** 这是立项报告 §21.2 点名失败路径
（"未建 Baseline 就断定 Agent"）的正面对策，也是 §3.1 门槛 4 的要求。G02 建了三条 baseline
（deterministic / naive_react / no_rag），这个结构让 G03 的"Agent 比什么更好"有了参照物。
面试中"你怎么证明 Agent 是必要的"这个问题，只有做过 baseline 的项目答得上。

**Ground Truth 与 locked test 对 Agent runtime 不可达。** 这条隔离在 G02 有 60 格
access matrix 实测支撑。它防止的是评测自证——立项报告 §0.1 里"拿不出测试集、公式、样本数"
的反面不只是"有测试集"，而是"测试集不能被被测者看到"。

**负结果诚实保留。** `docs/gates/G02/REPORT.md:47-49` 明确写 Root-cause Top-3 = 0.000
是"retained honestly; it is a comparison baseline for later Agent Gates, not a
G02 quality-floor waiver"。这个处理是对的，不应改动。

### 设计偏松的部分

`docs/gates/G02/VALIDATIONS.yaml` 17 项里有若干 `n_unit` 极小（如 V-G02-001 的
"five fixtures"、V-G02-002 的 "one candidate-bound bootstrap action"）。这些项自带
`small_n_audit` 字段说明为何可以缩减，形式上是自觉的。但 `zero_tolerance: true` 且
`n=1` 的项（V-G02-002）实际上只是"做过一次且没报错"，谈不上验证。

不建议回补。这类项测的是治理机制本身，而治理机制已被 v2 大幅简化，回补等于验证已删除的东西。

## 二、Iteration 划分评价：这是 G02 的结构性缺陷

`governance/policies/iteration-lifecycle-v1.yaml:10-11` 把 `corrective` 与 `gate_attempt`
声明为可直接激活的类型，并强制 `corrective_link_direction: lower_iteration_id`。
后果是 EVAL-023 之后出现完美的奇偶结构：**奇数号 = C- seam 证明（pass），
偶数号 = A- Gate attempt（fail）**。

24 个 work item（12 C- + 12 A-）产生 24 个 YAML + 24 个 Markdown + 24 个 Eval 目录。
而 C- 被禁止运行 Gate（`gate_l2_execution: 0`），A- 被禁止修改 `src/`。
**一次修复被强制拆成两个不能互相验证的记录。**

这是 G02 时长的结构性来源，不是执行者的问题。12 次 Gate attempt 中有 12 次死于治理与传输管道
（`mc stat` 权限、Windows `CreateProcess` WinError 206、Python 3.8 缺 `datetime.UTC`、
`index.docker.io` 别名、`minio/mc` ImagePullBackOff、LF→CRLF），只有 7 次死于真实被测对象。

最极端的单点：EVAL-G02-012 因 LF→CRLF 转换 blocked，**十四个 Gate phase 中没有任何一个
进入其 runner**（`docs/evals/EVAL-G02-012/REPORT.md:3-5`）。一次换行符问题吃掉一整个 Eval 编号。

已由 governance v2 修正。**外推到 G03 的教训：iteration 边界应按语义失效范围划分，
不按治理动作类型划分。**

## 三、Eval 标准评价：数字对了，定义错了

7 个 quality floor 数值从冻结到关闭没有漂移（`validate_threshold_registry` 有相等性检查）。
这一点是真的做到了。

但 7 条里 5 条从未真正生效，`deterministic 0.500` 是签名表缺陷造成的巧合，
`0.000` Top-3 约 99% 是标签格式 artifact（重打分得 148/192 = 0.771）。
完整推导见 [EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md)。

**这不使 G02 的关闭无效**，因为 G02 的被测对象是实验室而不是诊断能力。
但它有一个直接的前向后果：`docs/gates/G03/PLAN.md` 冻结的
"validation E2E ≥ best G02 baseline + 5pp"这条门槛，其比较基准
（`best_baseline` = deterministic 0.500）是错的。

**修复状态（2026-07-28 晚）**：以上三项已由 metric v2（`AMD-0006`）修复——
封闭标签集已披露、签名表已改为读值、floor 覆盖已硬化为 5 条 measured + 2 条 N/A
（带 G03 证明义务）。`docs/gates/G02/REPORT.md` 未被修改，`0.500` / `0.000`
作为诚实历史记录原样保留；重测产物在 `.audit/g03-readiness/baseline-v2/`
并显式标注 `non_gate_evidence: true`。

**但比较基准仍然无效**：v2 下三条 baseline 全部得 1.000、CI 宽度为 0，
`best_baseline + 5pp = 1.05` 不可达。这是一处新的构造性泄漏（组存在性签名可在
不读任何数值的情况下拿到 Top-3 = 32/32），不是基线变强。
G03 的准入前提相应改为"先去泄漏使三条基线分化，再重跑"，
见 [EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md) 第 0 节与 [G03.md](G03.md) 前置依赖。

另需修正本文件原稿的一处判断：148/192 = 0.771 的重打分**只是启发式历史解释**，
它不能修复 resource case，也不适合作为新的 G03 基准。实际采用的是完整 fresh v2 复测。

## 四、关闭证据链的一处不一致

`docs/gates/G02/VALIDATIONS.yaml` 的 17 个 validation 里，**11 个的 `artifact_paths`
指向 `docs/evals/EVAL-G02-028/`**，零个指向 `EVAL-G02-046/`。

而实际状态是：

- `EVAL-G02-028`：`Result: fail`。`trace-six-stage-matrix` 返回
  `remote_command_or_transport_failed; exit=1`，未写入 trace phase record。
- `EVAL-G02-046`：`Result: pass`。十四个 frozen phase 全通过。

同时 `docs/gates/G02/REPORT.md:53-56` 声明"All seventeen items ... passed"。

这不是伪造：EVAL-028 确实通过了四个 preflight、`lab-deploy-and-bind` 与全部 60 格
isolation matrix，那些 phase record 是 immutable 且各执行一次的（028 REPORT 自己写明）。
所以指向 028 的那些 artifact 对**它们各自的 validation** 是有效证据。

**但证据链的可读性坏了。** 一个外部复核者按 VALIDATIONS.yaml 追踪，会落到一份标着
`Result: fail` 的 Eval 报告里，而 Gate REPORT 说全部通过。这需要读完两份报告才能理解。

**补救建议**（低成本，非阻塞）：在 `docs/audit/` 或 G02 的 handoff 里加一份指针说明
"哪些 validation 的证据在 028、哪些在 046，以及为什么 028 的 fail 不影响那些 artifact 的有效性"。
**不要修改 VALIDATIONS.yaml 或 REPORT.md**——它们是已关闭 Gate 的冻结资产，
改动会触发 [GOVERNANCE_REVIEW.md](../GOVERNANCE_REVIEW.md) 里量化过的那类成本而不改变任何事实。

## 五、PLAN 与实际执行的偏离

`docs/gates/G02/PLAN.md` 的 §1 与 §10 的 iteration 枚举停在 **A-G02-003**，
从未扩展到 A-004…A-012。实际执行到了 A-G02-012。

这是 plan-drift：计划文档没有跟上执行。但在 governance v2 的口径下这**不应该补**——
补齐 9 个 iteration 条目属于纯治理写作，没有新的 runtime observation，
正是 `AGENTS.md:23-25` 反死锁规则要拒绝的动作类型。

**记录为已知偏离即可。** 真实的执行记录在 46 个 Eval 目录里，比 PLAN 的枚举更权威。

## 八、被 G02 掩盖的仪器缺陷（2026-07-29 补记）

这是本次审查**在 G02 关闭后才发现**的一类问题，写在这里是因为它的根因属于 G02 建成的实验室，
而不是 G03 的设计。为在 metric v3 下重测 baseline，32-case 重放先后暴露**六个缺陷**，
完整清单与判定证据见 [G03.md](G03.md)。这里只记录对 G02 结论的影响。

**G02 的关闭依然有效**，理由与第三节一致：G02 的被测对象是故障实验室本身，实验室确实建成了。
但需要如实记录：**六个缺陷里有三个是 runner 自己制造的假阴性**——
fault 窗口从不驱动它所测量的负载、瞬时 scrape 缺口被首见即判败、
以及前一个 `adHighCpu` case 的 burn 留在 2 分钟 `rate()` 回溯窗内污染后一个 case 的 baseline。
判定证据都是同一 case 在同一 metric-definition digest 下重跑即通过。

**其中两个在 G02 期间就已被独立诊断过两次**（`EVAL-G02-036`、`EVAL-G02-042`
均归类为 "runner-control defect, not an infrastructure failure"），
但当时的处置只到"每 case 激励一次"，没有推进到"每轮询激励一次"，
也没有把结论写进实验室的不变量。**这是第二节所述 iteration 划分缺陷的实际代价**：
按治理动作类型而非语义失效范围划分，使得同一个根因可以被诊断两次而仍然存活。

对 G02 评级不构成翻案，但对"实验室已建成"这一结论应加一句限定：
**实验室建成了，其自身的测量可靠性当时未被证明**。
真正的证明发生在 metric v3 首次跑完 32 个 case 时——
24 pass / 7 infra_failed / 1 metric_fail，且八个失败全部可从 journal 单独归因。

不建议做的：补齐 PLAN 的 iteration 枚举；回补小 N validation；重开三笔已前向关闭的 G01 债务。
这三项都是纯治理动作，会重新引入已被量化证明为浪费的成本。
