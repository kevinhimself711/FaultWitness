# G04 设计：RAG、Memory 与 Skills

## 本 Gate 的核心问题：它太宽了

G04 承接 **5 条 T1 + 6 条 T2 + 4 条 T3**，是全项目最宽的 Gate。
`FINAL_PLAN.md:252-265` 把 RAG、Memory、Skills、动态检索、多模态全部塞进一个 Gate。

按 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md) 的主题覆盖率，这几块的价值差异极大：

| 块 | JD | 面经 | 判断 |
|---|---:|---:|---|
| RAG 与检索 | 82% | 69% | **两侧都高，做深** |
| Memory 与上下文 | 68% | 64% | **两侧都高，做深** |
| Tools/MCP/Skills | 91% | 65% | 高，但 Skills 只是其一部分 |
| 多模态 | 77% | **25%** | **舍弃** |

**结论：G04 应拆成两个阶段，多模态从交付中移除。**

多模态的舍弃理由必须写清楚，因为它是 `FINAL_PLAN.md` 的既有交付项：FaultWitness 的证据是
指标、日志、Trace、配置、变更记录，**全部是结构化文本**。为覆盖关键词而引入图表 OCR，
正是立项报告 §1.3 明令禁止的"不为关键词覆盖强行加入"。`REQ-MM-001` 本身已是 P2 且
verification 要求"against OCR"的对照——做一个必然无收益的对照实验，投入换来的是一个负结果，
而这个负结果在简历上无法讲述。

**主动排除并说明理由，比勉强实现更能体现判断力。** 这一点应写进 FINAL_PLAN 修正案，
见 [FINAL_PLAN_REVIEW.md](../FINAL_PLAN_REVIEW.md)。

## 冻结的退出标准（只能提高）

`FINAL_PLAN.md:261-265`：

1. Recall@10 不低于 **85%**，Citation precision 不低于 **90%**。
2. 无收益机制不得进入默认架构。
3. Memory 和动态 Skill 通过独立消融和安全回归。

第 2 条是本 Gate 最有价值的一条，也是立项报告 §21.7 反模式（"为了多 Agent 强行拆分职责"）
在 RAG 侧的对应物。它要求每个机制自带"它有没有用"的证据——这直接对应面试追问
"你为什么用 rerank / 你怎么知道它有效"。

## 阶段 A：RAG（约 14-19 天）

### I-G04-01：摄取与格式路由（M，3d）

**交付**：文档、代码、配置、事故记录摄取；低质量 PDF 隔离；provenance 记录。

**Eval 与通过标准**：
- 版本化 fixture 覆盖格式路由、质量检查、抽取、隔离、provenance — 各有正负例
- 低质量输入进入隔离区而非静默降级 — 零容忍
- 每个 chunk 可追溯到 source/version/section — 100%

**降级说明**：`REQ-RAG-001` 属 T2 支撑。做到"有版本化 fixture、有隔离路径、有 provenance"即可，
不追求格式覆盖广度。数据量与文档类型能讲清楚就满足了 §0.1 的 RAG 条。

### I-G04-02：Chunk 策略对照（M，3d）

**交付**：structure-aware、parent-child、fixed-chunk 三种切分在同一批 case 上的预注册对照。

**为什么是 T1 核心**：`REQ-RAG-002`。§0.1 一票否决项含"使用 RAG 但说不清切分"。
parent-child 是面经里的高频具体追问（`SRC-INT-XHS-004` 的父子文档追问）。

**Eval 与通过标准**：
- 三种策略在同一 case 集、同一 embedding、同一 TopK 下对照 — 预注册
- 报告 Recall@10、Citation precision、端任务成功率、token 用量、延迟五个维度
- **必须报告负结果**：如果 parent-child 不优于 fixed，如实记录并说明为什么不进默认架构

### I-G04-03：检索管道与可归因（M，4d）

**交付**：dense、sparse、fusion、rerank 四段，各段独立可追溯。

**为什么是 T1 核心**：`REQ-RAG-003`。这是 RAG 追问的主战场——候选集、分数、参数、延迟、
增量收益五项是面试官会逐个问的。

**Eval 与通过标准**：
- Trace 中每段的候选集、分数、参数、延迟可读 — 零容忍缺失
- 每段的增量收益单独报告（消融）— 四段各有一次 ablation
- Recall@10 ≥ **85%** — 冻结标准
- 无收益段不得进入默认架构 — 冻结标准，需显式判定记录

### I-G04-04：引用可核验（M，3d）

**交付**：每个受支持结论携带 source/version/section/chunk/evidence 五级引用。

**为什么是 T1 核心**：`REQ-RAG-004`，直接对抗幻觉追问。

**依赖 G03**：EvidenceRef 结构必须在 G03 就预留四级定位（见 [G03.md](G03.md) 联动表第三行）。
如果 G03 只做了 observation 一级，这里需要返工改 G03 的核心结构。

**Eval 与通过标准**：
- Citation precision ≥ **90%** — 冻结标准
- 程序化打分 + 人工抽样双轨（`REQ-RAG-004` 的 verification 明确要求两者）
- 引用不存在的 chunk / 版本错配 — 零容忍

### I-G04-05：增量、删除与回滚（S，2d）

**交付**：增量更新、tombstone 删除、版本冲突、错误摄取回滚。

**T2 支撑**，做到有集成测试即可。但 §0.1 的 RAG 条明确点了"更新、冲突"，所以不能没有。

**Eval 与通过标准**：
- 变更、删除、冲突、回滚四类集成测试，无 stale 静默召回 — 零容忍
- 删除后的文档不出现在任何召回结果中 — 零容忍

### I-G04-06：ACL 与新鲜度前置过滤（S，2d）

**交付**：按认证 ACL 与新鲜度在**排序前**过滤。

**T2 支撑**，但有一个零容忍点：`REQ-RAG-006` 要求跨租户、已撤销权限、过期版本三类测试
返回**零**未授权证据。过滤必须在 ranking 之前——排序后过滤会泄漏"存在性"信息。

### I-G04-06b：RAG 路线 ADR（S，1d）

**第二轮增补**（[INTERVIEW_DEFENSE_COVERAGE.md](../INTERVIEW_DEFENSE_COVERAGE.md) 采纳 1）。
§19.1 清单里两条属于阶段 A：**RAG / 长上下文 / SQL / 知识图谱的选择**与
**Dense / Sparse / Rerank**。前者的对照数据由 I-G04-14 的长上下文 arm 提供，
后者由 I-G04-03 的四段消融提供——**ADR 写的是决策与被否决备选，数据引用这两个 iteration，
不新增实验**。

Embedding 选型的理由也写在这里。`gates/G04.md` 把 embedding 显式设为**控制变量**
（I-G04-02/03 都是"同一 embedding"），这是正确的实验设计，
所以 Q38 不采纳为实验，只采纳为 ADR 的一节。

## 阶段 B：Memory 与 Skills（约 13-17 天）

### I-G04-07：三类记忆分库（S，2d）

**交付**：runtime state、durable knowledge、learned memory 按 owner、storage、lifetime 分离。

**T2 支撑**。`REQ-MEM-001` 的价值在于能回答"你的 memory 和 state 有什么区别"——
这是面经高频问题，而多数项目答不上来因为它们混在一起。

**Eval 与通过标准**：
- 架构测试拒绝跨库所有权与无界 transcript 复用 — 零容忍

### I-G04-08：Memory harness（M，4-5d）

**这一项是 G04 里技术难度最高的，且当前完全不存在。**

`src/faultwitness/` 下没有 `memory/` 包。更关键的是**现有 harness 是单发的、trial 互相独立**，
而立项报告 §9/§12.2 要求的六个指标里至少四个需要跨 episode 顺序依赖。
完整分析见 [EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md) 第六节。

**四个设计决定必须在本 iteration 冻结**：

1. **memory state 作为内容寻址的派生产物**，从 `memory_ops` 日志重放得出，
   而非活的可变外部状态——只有这样它才能进 journal 的 artifact digest。
   `experiment.py` 的 `depends_on` + `dependency_artifacts` 已能表达顺序依赖失效传播，
   `ExperimentUnit` 与 cache-key 语义**不需要改**。
2. **逻辑时钟**，不用 wall-clock。过期记忆误用率必须可确定性复现。
3. **配对 `memory_mode` on/off arm**，同 case 同 seed。这是唯一能回答"记忆到底有没有用"
   的形态，也直接对应 §21.5 点名的失败路径"把整段历史塞进 Memory"。
4. **bootstrap `cluster_key` 从 `case_id` 改为 `sequence_id`**
   （现为 `g02_baselines.py:104`）。跨 episode 后同一序列内 trial 不再独立，
   按 case 聚类会低估方差。**这一改动需要单独一条修正案。**

### I-G04-09：写入门控（S，2-3d）

**T1 核心**（`REQ-MEM-002`）。重复、失败、低置信、敏感 episode 不得成为记忆。

**Eval 与通过标准**：
- 写入 Precision（正负 fixture 双轨）— 报告数值
- 敏感数据拒绝率 — **零容忍**，与 `REQ-SEC-003` 的 canary 复用同一套探针

### I-G04-10：冲突与过期（M，3d）

**T1 核心**（`REQ-MEM-003`），且是 Memory 追问里最难的部分。

**Eval 与通过标准**：
- 确定性排序、显式不确定性、有效期强制 — 冲突 case 全通过
- 冲突检测率与过期记忆误用率 — 报告数值（依赖 I-08 的逻辑时钟）

**第二轮增补：本 iteration 同时产出 Memory 写入与冲突 ADR（+1d）。**
§19.1 清单的第九条。这份 ADR 的被否决备选很具体：
无门控全量写入、LLM 判定冲突、wall-clock 过期——
三者都是本 iteration 明确不采用的做法（门控见 I-09、逻辑时钟见 I-08），
所以决策记录的成本只是写下来。

### I-G04-11：Skills 最小集（S，2-3d）

**T3 降级**：2-3 个 Skill + trigger 精确率/召回率，**不建完整 Skill 生态**。

理由：完整 Skill 生态是平台级工作，而 Skills 只是 `tools_mcp_skills` 主题的一部分，
该主题的高分主要由 tools 与 MCP 贡献。`REQ-SKILL-001` 本身是 P1。

**Eval 与通过标准**：
- trigger 精确率与召回率、任务成功率、token 开销、冲突、越界 — 报告五项
- Skill 不得绕过工具权限边界 — 零容忍

### I-G04-12：动态工具检索对照（S，2d）

**T3 降级**：保留一次 A/B，**不建动态加载子系统**。

理由：工具只有 6-8 个，动态检索的收益接近 0。但"我做了对照，证明在这个规模下不需要"
是一个比"我实现了动态加载"更好的面试答案——它展示的是判断力而不是堆砌。
这正是 `REQ-TOOL-004` 的 verification 要求的（recall、选择准确率、成功率、token、延迟同 case 对照）。

### I-G04-13：MCP 只读子集（S，2d）

**T3 降级**：只暴露 MCP 只读子集 + 一致性契约测试，**不做 SDK/MCP 双向等价实现**。

理由：MCP 是 JD 91% 的关键词，不能没有；但双接口完全等价的实现成本高、可讲述性低。
只读子集足以回答"你怎么把能力暴露给外部 Agent"和"MCP 的鉴权怎么做"。

**Eval 与通过标准**：
- 跨接口契约测试比较授权、schema、错误、结果行为 — 一致
- MCP 接口不得绕过 tenant 边界 — 零容忍

### I-G04-14：压缩与长上下文消融（S，2-3d）

**T3 降级**：只报压缩比 + 约束保持率两个指标，不做完整 Pareto。

`REQ-MEM-004` 的 verification 要求 no-compression baseline，这条必须保留——
否则又是"没有基线就断定有效"。

**第二轮增补：从两 arm 扩为三 arm。** 原设计的两 arm（压缩 on / 压缩 off）
都在同一上下文窗口内，它证明的是"压缩有没有损失"，
**答不了"为什么要做 Memory 和压缩，而不是把窗口开大"**——
`长上下文` / `context window` 全仓库 0 命中，这个判断从未被写下来。

第三个 arm：**长上下文（不做 Memory 检索，全量塞入窗口）**。
缺了它，阶段 B 的 I-07…I-10 与本 iteration 五个 iteration 全都少一个对照基线，
面试官一句"你为什么不直接用 128k 窗口"就能把整块 Memory 工作问空。

**Eval 与通过标准**：
- 三 arm 在同一 case 集、同一模型上对照，报告质量、成本、延迟三维
- 长上下文 arm 若在质量上不差而成本显著更高，这是本 iteration 的**主要产物**——
  一个可讲述的成本数字，而不是"无显著差异"
- 若长上下文 arm 质量也不差且成本可接受，则如实结论"本项目规模下 Memory 收益不成立"，
  按 `FINAL_PLAN.md` "无收益机制不得进入默认架构"处理。**这个负结果同样是合格产物**

## 明确不做

- **多模态**（`REQ-MM-001`）。理由见开头。应在修正案中记录为"已评估并主动排除"。
- **容量曲线**（`REQ-RAG-007` 的 20k-100k 扫描）。降为单点容量报告。
  个人项目的容量曲线不可信，报了反而是风险。
- **完整 Skill 生态**、**动态加载子系统**、**SDK/MCP 双向等价**。见上。
- **embedding 选型对照实验**（§20 Q38）。embedding 是 I-02/I-03 的**控制变量**，
  再加一个对照会稀释 chunk 与检索分段两个真正想测的因子。选型理由进 I-06b 的 ADR。
- **BM25 vs 学习式稀疏向量对照**（§20 Q37 后半）。`REQ-RAG-003` 只要求 "sparse retrieval"，
  未指定实现；这是检索方向的专精题，不落在本项目三个目标岗位族的核心素养上。
- **百万/千万级容量迁移**（§20 Q42）。与已排除的 25/50 并发同构——
  单机 K3s 上的迁移数字不可信，报了是负资产。
- **并发上传与索引更新一致性**（§20 Q63）。I-05 的增量/删除/冲突/回滚是**串行**集成测试，
  这是恰当范围：本项目知识库是运维文档与 Runbook，写入方是单一 dogfooding 用户，
  并发写入不是真实场景。为不存在的场景建并发一致性测试属于过度设计。

后四条来自 §20 追问清单的反向检索，经判据筛选后**驳回**，
理由见 [INTERVIEW_DEFENSE_COVERAGE.md](../INTERVIEW_DEFENSE_COVERAGE.md)。
按本审查一贯做法，驳回项也必须留下记录，不得静默省略。

## 与其他 Gate 的联动

| 联动 | 依赖方向 | 关键点 |
|---|---|---|
| `REQ-OBS-001` G01→G03→G04 | G03 提供结构 | EvidenceRef 必须已支持四级定位，否则返工 |
| `REQ-SEC-002` G04→G05→G07 | G04 起头 | 检索文档与工具结果视为不可信数据，此处建立注入防御基线 |
| `REQ-RAG-006` G04→G06 | G04 起头 | ACL 过滤在 G06 扩展为 RLS + Qdrant ACL |
| `REQ-ENV-003` G04→G07 | G04 起头 | 冲突/过期证据的对抗 case 在 G07 扩展到 24 个误导性变更 |
| `REQ-MEM-002` G04→G07 | G04 起头 | 写入 Precision 在 G07 进入完整指标体系 |
| `REQ-TOOL-004`/`REQ-RAG-002`/`REQ-MEM-004` G04→G08 | G04 产出 | 三个消融的对照数据直接进 G08，不重跑 |

最后一行是本 Gate 与 G08 关系的关键：**G04 的三个消融如果按预注册规范做，G08 就不需要重跑它们**。
这能显著压缩 G08 的规模——而 G08 是按分级最应瘦身的 Gate。

## 规模

阶段 A 约 14-19 天（含 RAG 路线 ADR +1d），阶段 B 约 13-17 天
（含 Memory 冲突 ADR +1d、长上下文 arm +0-1d），合计 **27-36 天**。
这仍是全项目最长的 Gate，但已从原设计（含多模态与完整 Skill 生态）压缩了约三分之一。

建议按阶段 A / 阶段 B 分两次 Gate 评估，而不是一次巨型评估。理由见
[G02.md](G02.md) 第二节：G02 的 12 次 attempt 全部死于管道，
单次评估的表面积越大，非语义失败的概率越高。
