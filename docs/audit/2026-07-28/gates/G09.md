# G09 设计：训练就绪与真实 Smoke

## 本 Gate 的取舍是全项目最微妙的

`training_optimization` 主题的两侧数字冲突最大：**JD 82% / 面经 33%**。

- JD 82% 是**不能完全放弃**的理由。这是三个目标岗位族之一（AI 算法岗）的核心,
  17/22 份 JD 明确写了后训练、SFT、DPO、RL。完全没有训练内容,这个岗位方向就断了。
- 面经 33% 与立项报告 §22.2 的"**不做模型训练**"是**不能做深**的理由。
  §21.8 更把"过早做训练"列为具名失败路径。

`REQ-ALG-001` 本身是 **P2、非 mandatory**,且其 statement 写得很清楚：
"Implement SFT, preference, or RL optimization **only after badcase attribution** and prove reliability."

**结论：保留但只做 smoke,且把"为什么现在不该真正训练"的归因报告作为主要交付物。**
这份报告比 loss 曲线更有说服力——它证明的是判断力,而 loss 曲线只证明会调 API。

## 冻结的退出标准（只能提高）

> 本节的**定性**条款（安全边界、失败语义、零容忍项）保持冻结。
> 其中**引用实测量的数值目标**在该 Gate 首次通过有效性检查的测量之前视为待定，
> 依据 ADR-0018 的同一原则：冻结定义，不冻结未知数。

`FINAL_PLAN.md:336-342`：

1. SFT、DPO 各至少 **20 个 optimizer step**。
2. GRPO 至少 **10 个 optimizer update**。
3. 三条路径均完成 checkpoint 保存、恢复、加载和推理。
4. **不使用 validation、locked test 或外部 benchmark。**
5. **不把 smoke loss/reward 包装为质量提升。**

这五条冻结标准的设计质量很高,尤其是第 4、5 条。它们把 G09 的性质定义得毫无歧义：
**这是"我能跑通训练管线"的证明,不是"训练提升了质量"的主张。**

第 4 条防止训练数据污染评测集;第 5 条防止把 20 步的 loss 下降说成模型变好了。
这两条正是 §0.1 里"简历写准确率 90% 却拿不出实验报告"的预防机制。

`FINAL_PLAN.md:359` 另有 G10 的最终退出条件："三条训练管线有真实 4090 smoke 证据"——
硬件是单张 4090,这也是"只做 smoke"的物理约束。

## 硬依赖：G07 的轨迹

**G09 没有 G07 的 1000+ 条 TrajectoryIR 就无法开始。** `REQ-EVAL-006` 跨 G07/G09,
其 verification 要求轨迹 manifest 证明"count, split isolation, lineage, privacy,
replay compatibility"——其中 **split isolation** 直接支撑 G09 的冻结标准第 4 条。

这是 G09 不能提前的结构性原因,也应该是它排在 G08 之后的理由（而不是"训练比较难所以放最后"）。

## Iteration 划分

### I-G09-01：训练数据准备与血缘（S，2-3d）

**交付**：从 G07 轨迹构造三类训练数据,全程可追溯。

**Eval 与通过标准**：
- 数据血缘：每条训练样本可追溯到原始 trajectory 与 case
- **split 隔离验证**：训练数据中**零**条来自 validation 或 locked split — 零容忍
- 隐私：无 secret 无 PII（复用 G06 的 canary 探针）

第二条是冻结标准第 4 条的机器化验证。它必须是零容忍的自动检查,
不能靠"我注意了"——这正是 G07-I-02 重设计 split 的下游价值。

### I-G09-02：SFT smoke（S，2-3d）

**交付**：State + Tools → Structured Next Action 的 SFT 管线。

**Eval 与通过标准**：
- ≥ **20 个 optimizer step** — 冻结标准
- checkpoint 保存 → 恢复 → 加载 → 推理全链路通过 — 冻结标准
- 报告数据血缘、算力、消融、安全、回归（`REQ-ALG-001` 的 verification 要求五项）
- **不得声称质量提升** — 冻结标准

任务形态选择理由：`State + Tools → Structured Next Action` 是三条路径里最贴合本项目的,
因为它的训练信号直接来自 Agent loop 的真实决策点,不需要额外标注。

### I-G09-03：DPO smoke（S，2-3d）

**交付**：Chosen/Rejected 计划或轨迹的偏好优化管线。

**Eval 与通过标准**：
- ≥ **20 个 optimizer step** — 冻结标准
- checkpoint 全链路 — 冻结标准
- **偏好对的来源必须是 G07 的 badcase 归因**,不是人工臆造

最后一条把 DPO 与 G07 的 badcase 工作连起来：chosen/rejected 对应
"深度报告里定位到的正确路径 vs 实际错误路径"。这个连接是本项目做 DPO 的合法性来源——
否则就是 §21.8 的"过早做训练"。

### I-G09-04：GRPO smoke（M，3-4d）

**交付**：环境、规则 Reward、轨迹采样。

**Eval 与通过标准**：
- ≥ **10 个 optimizer update** — 冻结标准
- checkpoint 全链路 — 冻结标准
- **Reward 必须是规则化的**,不用 LLM 打分

最后一条很关键：本项目的 Ground Truth 是客观可验证的（根因标签 + 证据 ID),
所以规则 Reward 是可行的。用 LLM 做 Reward 会引入
`FINAL_PLAN.md:364`（同一模型不得同时生成测试、答案并作 Judge）的问题。

GRPO 是三条里工程量最大的,因为需要环境交互采样。这也是它只要求 10 个 update 而非 20 的原因。

### I-G09-05：归因报告与训练决策（S，2d）

**这是本 Gate 的主要面试资产,不是附属品。**

**交付**：一份说明"为什么现在不该真正训练"的归因报告。

内容应包含：
- G07 的 badcase 13 类分布（口径见 [BADCASE_TAXONOMY.md](../BADCASE_TAXONOMY.md)）
  —— 哪些是模型能力问题,哪些是检索/工具/状态问题
- 只有模型能力类 badcase 才是训练的合法目标；其余应通过工程修复
- 当前 badcase 中模型能力类的占比,以及在这个占比下训练的期望收益
- 数据量、算力（单张 4090）、评测成本三个约束下的可行性判断

**Eval 与通过标准**：
- 报告的每个结论引用 G07 的具体 badcase 编号
- 明确给出"在什么条件下应该开始真正训练"的触发条件

这份报告直接回答面试问题"你为什么不做 SFT",而答案"我做了归因,发现 80% 的失败是
检索和工具问题,训练解决不了"比"我做了 SFT,loss 从 2.1 降到 1.8"有价值得多。

## 与其他 Gate 的联动

| 联动 | 方向 | 关键点 |
|---|---|---|
| `REQ-EVAL-006` G07→G09 | **硬依赖** | 1000+ 轨迹 + split isolation |
| G07 badcase 归因 → I-03/I-05 | 硬依赖 | DPO 偏好对与归因报告的来源 |

## 规模

五个 iteration,约 **12-16 天**（含 I-05 归因报告内 Reward Hacking 排除记录的 +0.5d）。

这是全项目最短的产品 Gate,符合它的定位：**证明管线可跑通,不追求训练效果。**

## 明确不做

- **真正的训练**。不追求任何质量提升主张,冻结标准第 5 条明确禁止。
- **使用 validation / locked test / 外部 benchmark**。冻结标准第 4 条明确禁止。
- **LLM-as-Reward**。用规则 Reward,理由见 I-04。
- **多卡或云端训练**。单张 4090 是硬约束,也是"只做 smoke"的物理依据。
- **超过冻结要求的 step 数**。20/20/10 即可,多跑不增加可讲述性。
- **Reward Hacking 探测实验**。10 个 GRPO update 的规模下测不出来,硬做属于过度设计。
  但**判断必须留下记录**（见 [INTERVIEW_DEFENSE_COVERAGE.md](../INTERVIEW_DEFENSE_COVERAGE.md) 采纳 4）：
  本项目的规则 Reward 基于根因标签 + 证据 ID 匹配,两个可预见的 hack 面是
  **多引用证据以提高命中率**与**输出全部候选标签**;
  真正开始训练时的第一道防线是 **Reward 与 eval 指标不得同源**——
  否则 hack 会同时提高两者而无法察觉。这三点写入 I-05 的归因报告,不单独立项。
