# G05 设计：受控修复与动作事务

## 本 Gate 的定位

G05 是**一票否决项最密集的 Gate**。立项报告 §0.1 十条里有两条直接指向它：

- "工具有写操作，却没有风险分级、人工审批、审计和回滚"
- "没有失败注入、超时、重试、降级、幂等、断点恢复和死循环控制"（后半由 G03 承担，
  幂等与降级在此完成）

它承接 **5 条 T1 + 5 条 T2**，T1 密度仅次于 G03。而且它是 L3 门槛 3（"至少 2 个有副作用工具，
所有副作用受控"）和门槛 8（"风险分级、最小权限、审批、审计、脱敏、回滚齐全"）**唯一**的落点。

一个反直觉的判断：按 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md)，
`security_governance` 主题 JD 覆盖 100% 但面经只有 **13%**。这说明安全治理
**必须存在且可演示，但不值得做到企业 IAM 深度**。G05 的正确投入水位是
"每条安全边界有一个能失败的负例测试"，不是"完整的策略引擎生态"。

## 冻结的退出标准（只能提高）

`FINAL_PLAN.md:274-278`：

1. 未授权写、审批绕过、Digest 篡改接受、重复外部副作用均为 **0**。
2. 后置验证成功率不低于 **95%**。
3. 失败进入补偿或人工升级为 **100%**。

`FINAL_PLAN.md:280` 另有一条门：通过来源、License 与 Secret 审计后，仓库可首次公开。
这一条与 [G00.md](G00.md) 的补救建议直接相关——`audit.py` 的 secret 扫描与
GitHub Action SHA-pin 检查曾只能通过 `tests/audit/test_audit.py:78` 间接触发。
**该前置已于 2026-07-28 满足**：`audit.py` 已接回 `verify-fast`，
公开决定不再建立在无 CI 保障的检查上。G05 只需验证该前门仍在，不需重建。

## Iteration 划分

### I-G05-01：R0-R3 风险策略（M，3d）

**交付**：四级风险分级，R2 需审批，R3 禁止执行。

**T1 核心**（`REQ-SEC-001`）。

**Eval 与通过标准**：
- R2 绕过 **0**，R3 执行 **0** — 冻结标准，零容忍
- 每一级各有一个负例测试尝试越级并被拒
- 策略判定发生在 dispatch **之前**，不是执行后回滚

**设计约束**：风险级别必须由动作类型 + 目标 + 范围共同决定，不能只看动作名。
否则"重启一个 pod"和"重启全部 pod"会同级——这是面试中很容易被问出来的漏洞。

### I-G05-02：四种类型化写动作（M，4d）

**交付**：`FINAL_PLAN.md:271` 要求四种类型化写动作，每种带 dry-run、审批、幂等、验证、补偿。

**T1 核心**（`REQ-TOOL-002`）。L3 门槛 3 只要求 ≥2 个，冻结计划要求 4 个——**保持 4 个**，
因为四种覆盖了不同的补偿语义（可逆/需补偿/需人工/不可逆但可验证），这个分类本身是讲述点。

**Eval 与通过标准**：
- 无审批绕过、无重复副作用、UNCERTAIN 状态不盲重试 — 零容忍
- dry-run 与真实执行的差异可解释
- 每种动作的补偿路径各有一次真实执行

**UNCERTAIN 是这一项的核心**。动作返回"不确定是否生效"时盲目重试是真实系统里最常见的
数据损坏来源，而多数个人项目连这个状态都没建模。

### I-G05-03：Action Digest 与幂等（M，3d）

**T1 核心**（`REQ-REL-002`，跨 G05/G06）。

**Eval 与通过标准**：
- at-least-once 投递下重复命令只产生**一次**外部副作用 — 冻结标准，零容忍
- Digest 篡改被拒 — 冻结标准，零容忍
- 重复请求可取回原结果而非重新执行

**依赖 G03**：checkpoint 恢复的幂等语义在 G03 已建立（只读范围），此处扩展到外部副作用。
如果 G03 的 checkpoint 设计没有区分"已提交"与"已计划"，此处需返工。

### I-G05-04：最小权限（S，2-3d）

**T1 核心**（`REQ-TOOL-003`，跨 G05/G06）。

**Eval 与通过标准**：
- 跨租户与超范围调用在 dispatch **前**被拒，且留下不可变审计证据 — 零容忍
- 权限维度覆盖 tool scope、认证 tenant、环境、目标、时间窗五项

### I-G05-05：后置验证与补偿（M，3-4d）

**T2 支撑但含冻结标准**（`REQ-REL-004`）。

这是 G05 最有面试价值的一项：**动作技术上成功但世界状态没恢复**，这个区分是
"你怎么知道修好了"的答案。多数项目只检查 API 返回 200。

**Eval 与通过标准**：
- 后置验证成功率 ≥ **95%** — 冻结标准
- 失败进入补偿或人工升级 **100%** — 冻结标准，零容忍
- E2E case 覆盖假成功、补偿失败、UNCERTAIN、人工对账四类

第三条"补偿失败"是最容易漏的：补偿动作本身也可能失败，此时必须升级到人工而不是循环重试。

### I-G05-06：审计链重建（S，2-3d）

**T2 支撑**（`REQ-SEC-004`，跨 G05/G06）。

**Eval 与通过标准**：
- 从不可变事件完整重建决策与动作链 — 100%
- 审计记录含审批者、执行者、时间、范围、参数、版本
- 审计写入失败时动作**不得执行**（fail-closed）

fail-closed 这一条是零容忍。审计与执行的顺序关系是面试可深挖点。

### I-G05-07：注入防御基线（S，2-3d）

**T2 支撑，建议上调投入**（`REQ-SEC-002`，跨 G04/G05/G07）。

理由见 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md)：这是唯一同时触及 RAG、
动作与评测的安全项，且攻击成功率是一个能直接写进简历的数字。

**Eval 与通过标准**：
- 注入套件测量攻击成功率、工具暴露、策略篡改、数据泄漏四项
- 检索文档与工具结果**不得**改变策略或角色 — 零容忍
- 攻击成功率报告绝对值与样本数（不报"很低"）

### I-G05-08：失败分类与降级（S，2d）

**T1 核心**（`REQ-REL-001`，跨 G03/G05）。

G03 已建立 typed error 分类体系，此处扩展到写路径：速率限制、5xx、超时、空结果、
重试耗尽、显式拒绝六类各有降级路径。

### I-G05-09：Gate 评测与公开审计（S，2d）

**交付**：完整 E2E 闭环演示 + 来源/License/Secret 审计。

**Eval 与通过标准**：
- 一条 E2E case 从 intake 走到验证后的最终外部状态（`REQ-BUS-003`，T1 核心，L3 门槛 2）
- `audit.py` 的完整审计通过，且**该检查已有 CI 前门**
- 无 secret、无绝对本地路径、License 合规

## 与其他 Gate 的联动

| 联动 | 方向 | 关键点 |
|---|---|---|
| `REQ-AGT-003` G03→G05→G06 | G03 起 | checkpoint 幂等从只读扩到外部副作用，再到多 Worker |
| `REQ-REL-001` G03→G05 | G03 起 | typed error 分类复用，不新建体系 |
| `REQ-TOOL-003` G05→G06 | G05 起 | 最小权限在 G06 扩展为 RLS + Keycloak 四角色 |
| `REQ-REL-002` G05→G06 | G05 起 | 幂等在 G06 面对并发 Worker 重新验证 |
| `REQ-SEC-004` G05→G06 | G05 起 | 审计在 G06 扩展到跨租户视图 |
| `REQ-SEC-002` G04→G05→G07 | G04 起 | 注入防御的攻击成功率在 G07 进入完整指标 |
| `REQ-BUS-003` G05→G10 | G05 起 | 完整闭环在 G10 成为 dogfooding 的基础 |

**G05→G06 有四条联动**，是全项目最强的 Gate 耦合。这意味着 G06 不应被大幅推迟——
G05 建立的四个机制（权限、幂等、审计、补偿）都需要在多 Worker 下重新验证，
拖得越久返工面越大。

## 规模

九个 iteration，约 **24-30 天**。

顺序约束：I-01（风险策略）必须最先，因为 I-02 的每个动作都要挂风险级别。
I-03（幂等）与 I-04（权限）可并行。I-05（后置验证）依赖 I-02。I-09 最后。

## 明确不做

- **完整策略引擎生态**。OPA 用来做策略判定即可，不建策略管理界面、版本发布流程、
  策略测试框架。`security_governance` 面经覆盖率 13%，投入产出比低。
- **企业 IAM**。`FINAL_PLAN.md` 自己在 §3 就把"完整企业 IAM"列为非目标。
- **不可逆动作**。所有写动作必须可逆或可补偿。这不是能力限制，是设计决定——
  它让"所有副作用受控"这个主张可证明。
