# G03 设计：只读 Agent 纵切

## 为什么 G03 是全项目最重要的 Gate

按 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md)，G03 承接 **6 条 T1 核心需求**，
是所有未开始 Gate 中密度最高的。它同时是第一个让四条 L3 门槛从"不可能满足"变成"可满足"的 Gate：

| L3 门槛 | G02 结束时状态 | G03 后 |
|---|---|---|
| 2 完整闭环（≥5 个有意义步骤） | 不可能——无 Agent loop | 可满足 |
| 3 真实工具（≥6 个） | 0 个 | 6 个只读工具 |
| 6 分层评测（轨迹维度） | 只有结果维度 | 轨迹可度量 |
| 9 可观测（结论→模型/证据/工具） | Trace 存在但无结论可追溯 | 首次真正满足 |

而 G03 当前只有一份 30 行 placeholder（`docs/gates/G03/PLAN.md`，`status: placeholder`）。
**这是项目当前最大的设计缺口。**

产品侧现状核对：`src/faultwitness/` 5,819 行，包名为
`api / contracts / identity / models / observability / persistence / runtime / state`。
**不存在 `agent/`、`tools/` 任何一个包**，`/v1/tools` 硬编码 `return []`
（`src/faultwitness/api/app.py:223-233`）。G03 是从零开始写产品逻辑。

## 冻结的退出标准（只能提高）

`docs/gates/G03/PLAN.md` 与 `FINAL_PLAN.md:246-250` 已冻结三条：

1. Validation E2E 比最佳基线提高至少 **5pp**。
2. 关键结论 **100%** 回溯到 EvidenceRef。
3. Worker 和 SSE 恢复不丢失或重复状态。

**前置阻塞：第 1 条的比较基准仍然无效，但原因已变。**

- **原诊断（已修复）**：`best_baseline` = deterministic 0.500，是签名表按 key 存在性匹配
  造成的巧合（16/32 误判）。metric v2 已改为读值，此项成立且已关闭。
- **当前状态（2026-07-28 晚复测）**：三条 baseline 在 v2 下**全部得 1.000，95% CI 宽度为 0**
  （`.audit/g03-readiness/baseline-v2/summary.json`），于是
  `best_baseline + 5pp = 1.05` 落在单位区间之外，`feasible_on_unit_interval: false`。
- **判断**：这不是"基线太强"。连 `no_rag`——无检索、无工具、只读 packet 的削弱基线——
  也拿满分，说明分数可被非诊断特征取得。实测确认：只用"哪些 evidence 组非空"
  这一个特征、不读任何数值，Top-3 = 32/32 = 1.000。
  推导见 [EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md) 第 0 节。

因此 G03 的准入前提改为：**先消除组存在性泄漏、使三条 baseline 分化，再重跑并据以固定 5pp 的参照物。**
直接排除某条 baseline、把 1.05 截断为 1.0、或降低 5pp，都是未经授权的门槛弱化，
`docs/runbooks/G03_BASELINE_READINESS.md:51-53` 已明确禁止。

## Iteration 划分

划分原则来自 G02 的教训（见 [G02.md](G02.md) 第二节）：
**按语义失效范围划分，不按治理动作类型划分。** 每个 iteration 有独立的 checkpoint，
一个 iteration 失败不使其他 iteration 的观测失效。

### I-G03-01：Typed State 与 reducer（S→M，3-4d）

**交付**：版本化 typed state、显式 delta、reducer、所有权边界，
**外加 [CROSS_GATE_INTERFACES.md](../CROSS_GATE_INTERFACES.md) 的五条跨 Gate 接口规格**。

规模从 S 上调到 M（+1d），因为五条接口规格在此一次性落地：
`EvidenceRef.locator` 四级定位、`TerminalReason` 九成员枚举、
`ProgressDigest.no_progress_streak`、`IntentPhase` 三段式、
`ToolDefinition.mcp_exposed` + `side_effect_free`。它们全部是契约层字段，
集中改一次只需重新编译 `contracts/generated/contracts-v1.1.0.json` 一次，
分散到各 iteration 反而更贵。**这五条不落地会导致 G04/G05/G06 返工改 G03 核心结构。**

**为什么第一**：`REQ-AGT-001` 是后续一切的地基。立项报告 §6.2 点名反模式
"全局可变字典充当状态"，这是面试中"你的状态怎么管的"这一问题的唯一正面答案。

**Eval 与通过标准**：
- schema 与 reducer 测试拒绝非法、过期、跨 owner 的 state mutation — **零容忍**
- 并发 reducer 应用产生确定性结果，10 个并发 delta 顺序无关 — 通过率 100%
- state 版本单调递增，回退请求被拒 — 零容忍

**负例义务**：必须有一个 fixture 尝试跨 owner 写入并被拒绝。没有负例的零容忍项不算验证
（这是 G02 V-G02-002 那类 `n=1` 项的教训）。

### I-G03-02：六个只读工具与契约（M，4-5d）

**交付**：metrics / logs / traces / k8s-state / config-diff / change-events 六个工具，
typed schema、真实后端、错误码、超时、可观测性。

**为什么是六个**：L3 门槛 3 要求 ≥6 个领域工具。这六个恰好覆盖 G02 实验室已有的全部证据源，
不需要新建数据面。

**Eval 与通过标准**：
- 每个工具的 schema 校验、超时、错误码、span 导出各有契约测试 — 6×4 = 24 项全通过
- `tool_schema_validity` **由实际调用成功率产生，不再硬编码 `1.0`**
  （现状见 [EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md) 第三节）— ≥0.99。
  **必须同时接入产品侧 gateway 的两个失败码**（`INVALID_STRUCTURED_OUTPUT`
  与 `INVALID_TOOL_ARGUMENTS`），而不是只统计 `validate_result`：
  两者衡量不同层——模型是否产出合法 JSON，与工具参数是否符合子 schema。
  详见 [MODEL_LAYER_REVIEW.md](../MODEL_LAYER_REVIEW.md) 缺口 1
- **让 `RESULT_SCHEMA` 生效或删除它。** `g02_baselines.py:45-70` 是一份带
  `additionalProperties: False` 的完整 JSON Schema，全仓库仅定义处一个引用，
  从未传给任何 validator；实际生效的是更宽松的手写 `validate_result:314-354`。
  倾向于让它生效——严格的那份反而没被用，是真实的可维护性缺陷
- 工具调用全部出现在 Trace 中，无 orphan span — 零容忍
- `/v1/tools` 返回真实 catalog 而非 `[]`

**这一项同时偿还 G00 的 `REQ-DEV-001` 缺口**：Contract 测试类在这里第一次有真实内容。

### I-G03-03：Agent loop 与终止守卫（M，3-4d）

**交付**：观察→假设→取证→诊断的多步 loop，按步数、时间、模型调用、token、成本、重试、
重复度、证据枯竭八个独立守卫终止。

**为什么关键**：`REQ-AGT-002`。立项报告 §0.1 一票否决项含"没有卡循环控制"。
八个守卫必须**各自独立可触发**，否则无法证明。

**Eval 与通过标准**：
- 八个守卫各有一个 chaos case 单独触发，且保留 typed terminal reason — 8/8，零容忍
- `dead_no_progress_loop` **首次真正被计算**（G02 中它只存在于 registry，从未计算）— <0.01
- 任务跨越 ≥5 个有意义步骤（L3 门槛 2）— 中位步数 ≥5

**这一项让两条空转的 quality floor 之一开始生效。**

### I-G03-04：Evidence 与 EvidenceRef 追溯（M，3-4d）

**交付**：Evidence、Hypothesis、ProbePlan、ChangeEvent 四类结构，
每个关键结论携带可核验 EvidenceRef。

**Eval 与通过标准**：
- 关键结论 100% 回溯到 EvidenceRef — **冻结标准，零容忍**
- Trace 一致性测试拒绝 orphan claim、缺失因果、敏感原始载荷 — 零容忍
- `evidence_precision` **在有干扰项的前提下**计算。G02 的 ground truth 是全部 observation ID
  的全集，任何子集都得 1.0（`g02_baselines.py:551-558`）。G03 必须引入
  `required_evidence` 与 `distractor_evidence`，引用干扰项即扣分 — ≥0.90

**这一项让第三条空转 floor 开始生效**，且是 `REQ-OBS-001` 首次真正满足的时刻。

### I-G03-05：Worker 与 SSE 崩溃恢复（M，3d）

**交付**：checkpoint 前后崩溃注入、幂等恢复、SSE 断线续传。

**Eval 与通过标准**：
- checkpoint 前后各注入崩溃，state 恢复且已提交副作用不重复 — **冻结标准，零容忍**
- SSE 断线后从 `Last-Event-ID` 续传，无丢失无重复 — 零容忍
- **接走 DEBT-G01-004**：stage-level wall-time 对账。G03 是第一个存在真实 Agent 阶段的 Gate，
  瀑布图对账是自然产物（理由见 [G01.md](G01.md) 第三节）

只读 Gate 里"已提交副作用"指的是 checkpoint 与事件发布，不是外部写——外部写在 G05。

### I-G03-06：预算与成本（S，2d）

**交付**：per-task token 与金额预算，成本归因到每个成功任务。

**Eval 与通过标准**：
- 预算耗尽时安全终止并保留 typed reason — 零容忍
- 成本报告与 provider usage 对账一致 — 差异 <1%
- **Prompt、模型、参数与 Schema 版本写入每次 Trace**（立项报告 §6.5 `:459` 的明确要求，
  当前 `prompt_version` / `prompt_digest` 在 `src/faultwitness/` 零命中）。
  它与成本归因共享同一个 span 属性写入点，合并做的边际成本接近零；
  且它是 replay adapter 的 `prompt_digest` 键**唯一可能的生产侧来源**——
  没有它，"重放"无法证明用的是同一个 prompt。详见
  [MODEL_LAYER_REVIEW.md](../MODEL_LAYER_REVIEW.md) 缺口 2
- **sanitizer 兼容**：属性命名必须迁就 `_DENIED_KEY_PARTS` 的子串匹配
  （它含 `token`，所以用 `model.usage.input_units` 而非 `model.tokens.input`）。
  **不得为迁就指标命名而放宽 denylist。**

### I-G03-07：Incident Console 最小闭环（S，2-3d）

**交付**：从 intake 到可读诊断报告的最小界面。

**Eval 与通过标准**：
- 一条 E2E case 走完全部状态并产生可核验最终产物
- 演示脚本可在 clean 环境执行（L3 门槛 10）

界面做到"能演示、能截图讲清闭环"即可。按 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md)，
产品界面不在任何 JD 主题的高频区，不值得投入。

### I-G03-08：Gate 评测与 baseline 对照（M，3d）

**交付**：在**去泄漏并已分化**的 baseline 上跑 validation split，产出对照报告。

**Eval 与通过标准**：
- Validation E2E ≥ best baseline + **5pp** — 冻结标准。
  参照物取前置依赖第 4 项重跑后的值；在三条 baseline 分化之前本项不可开工
- 报告包含样本数、公式、置信区间、原始聚合（对抗 §0.1"拿不出测试集、计算公式、样本数"）
- `fault_family_success` ≥0.55 —— 该 floor 已在 metric v2 复测中首次真实计算
  （四个 family 聚合），G03 只需维持而非首次实现
- 两条 N/A floor 在本 Gate 履行证明义务：`tool_schema_validity` 由
  `g03.tool_contract_matrix` 计算，`dead_no_progress_loop` 由
  `g03.termination_guard_matrix` 计算。这是 G02 遗留的两条显式缺口的偿还点

### I-G03-09：五份选型 ADR（S，2d）

**第二轮增补。** 依据见
[INTERVIEW_DEFENSE_COVERAGE.md](../INTERVIEW_DEFENSE_COVERAGE.md) 采纳 1：
报告 §19.1 的 ADR 最低清单十二条里**八条没有对应 ADR**，
仓库现有 15 份全是架构不变量、基础设施选型、治理机制与 G02 实验协议，
没有一份是"为什么这样选"的路线决策。

本 iteration 写其中五份——它们的决策**都在 G03 本体内做出**：

| ADR | 主题 | 被否决的备选 |
|---|---|---|
| 为什么是 Agent，不是 Workflow | 事故诊断的分支不可预先枚举 | 确定性 Workflow、规则引擎 |
| 为什么先单 Agent | 单 Orchestrator + 确定性并行 Collectors | 多 Agent 起步 |
| 为什么选该 Orchestrator | LangGraph | LangChain、Dify、自研状态机 |
| 状态与 Checkpoint 存储 | PostgreSQL Checkpoint | Redis、文件、内存 |
| SSE 与断线恢复 | SSE + outbox + 续传游标 | WebSocket、轮询 |

**为什么放在 G03**：这五条决策的实现落点全在 G03（I-01 typed state、
I-03 loop、I-05 checkpoint 与 SSE）。`LangGraph` 在仓库里已出现 13 处
（`FINAL_PLAN.md:35,57,79,142`、`gates/G01/PLAN.md:227` 的
"禁止裸用默认 Saver"），但**没有一处是选型论证**——全是技术栈罗列或实现约束。
§17.1 要求"最终选择必须有 ADR，不能因为'大家都用'而采用"。

**Eval 与通过标准**：
- 每份 ADR 必须含**被否决的备选方案**及否决理由。
  只写"我们选了 X"的 ADR **不计入**——它没有回答追问
- 每份 ADR 进 `docs/adr/INDEX.yaml`，status 为 accepted
- 与 G03 实现一致：ADR 里的决策必须能指向本 Gate 的具体代码或测试

这不是新增能力，是把**已经做过的判断**补上记录，因此规模是 S 而非 M。

### 第 4 项的 metric v3 进展（2026-07-29）

泄漏本身已由 `AMD-0007` 的 metric v3 处置：collector 改为**标签盲**，
六个 evidence 组对所有 label 恒定出现，`build_observation_packet_v3` 不再按标签下标
生成"唯一正确组"。这消除了第 0 节诊断的共线性。7 个门槛数值仍逐字节不变。

但 baseline 分化的实测尚未取得，因为 preflight 的 32-case 冻结重放一直未能完成。
四轮诊断依次暴露**四个仪器/runner 缺陷**，每个都以 AMD-0007 附录形式冻结：

| 轮 | 缺陷 | 类别 | 附录 |
|---|---|---|---|
| 1 | wildcard `max()` 选中已删除 pod 的滞留序列，掩盖当前 pod 内存增长 | 仪器 | collector pod-pinning |
| 2 | 激活 deadline 到期时终端观测未留存，recovery 索引空列表，`IndexError` 掩盖 fault 结果 | 仪器 | terminal fault-sample |
| 3 | fault 窗口从不驱动它所测量的负载，激活取决于环境流量是否恰好落在 deadline 内 | **runner 假阴性** | runner false-negative |
| 4 | 失败路径丢弃全部观测；首失败即中止整轮；cleanup 错误掩盖主因；缺失序列被当作真零 | **证据缺口** | 同上 |
| 5 | 瞬时 scrape 缺口被首见即判败——`cpu_rate` 缺失判败 kafka case，而该谓词根本不读它 | **runner 假阴性** | correction 6 |
| 6 | 前一个 adHighCpu case 的 burn 仍在 2 分钟 `rate()` 回溯窗内，污染后一个 case 的 baseline | **runner 假阴性** | correction 7 |

第 3、4 轮是本轮的核心结论，且性质与前两轮不同：**它不是第三个仪器缺陷，
而是 runner 自身产生的假阴性**。判定性证据是同一 case 在同一
metric-definition digest 下重跑即通过（`SEED-G02-0001` lag 27.0 → 87.0；
case 8、case 15 同样如此）。仓库此前已两次独立诊断出同一根因
（`EVAL-G02-036`、`EVAL-G02-042` 均归类为 "runner-control defect, not an
infrastructure failure"），本轮只是把当时"每 case 激励一次"补齐为"每轮询激励一次"。

第 5 轮是**我自己在第 4 轮的修复中引入的**，值得单独记录，因为它说明这类缺陷有多容易复制：
把"缺失序列不得当作真零"实现成了"首次见到缺失即判败"。诊断扫描第一个 case 立刻回报
`absent Prometheus series: cpu_rate`——而 `kafkaQueueProblems` 的谓词根本不读 `cpu_rate`。
只读探针证实该序列当时存在且健康（值 `0.00146`，ad pod 自 2026-07-25 起 Running，
命名空间内 79 条 cAdvisor CPU 序列），所以那是一次瞬时 scrape 缺口。
修正是把**不可评分**与**失败**分开：窗口在六组齐备前只是不可评分，
按已有的 5 秒间隔轮询等待（等待刻意保持标签盲，否则轮询次数本身会泄漏标签），
只有到该阶段已预注册的观测 deadline 仍缺失才判 `InfrastructureFailure`。
不动任何谓词、deadline、间隔或门槛数值，且这个方向只可能消除假阴性。

### 首次跑完 32 个 case 的结果（2026-07-29 晚）

修完第 5 个缺陷后，诊断扫描**第一次跑完全部 32 个 case**（此前五轮均止于 case 1）：

| 结果 | 数量 | 归因 |
|---|---:|---|
| `pass` | 24 | —— |
| `infra_failed` | 7 | 全部是 SSH 传输故障，集中在两个断连窗口 |
| `metric_fail` | **1** | `SEED-G02-0015`（`adHighCpu`），即上表第 6 个缺陷 |

**整轮只有一个真正的 metric 失败。** 7 个基础设施失败全是 SSH
（`connection_refused` 5 个、`connection_timeout` 2 个），按 AMD-0003 属可归因基础设施故障、
授权无限重试——它们需要重跑，不需要修。

**这段的后半句已被 ADR-0017 推翻，保留原文以存档。** 当时写的“事后探测确认主机恢复”
成立于探测的那一刻，但不成立于结论：那 7 次 SSH 失败可归因于**正在失效的原宿主**，
而该宿主随后彻底无法开机。因此这一轮（24 pass / 7 `infra_failed` / 1 `metric_fail`）
**不是一个可以拿来改进的基准**——CPU 在静默损坏执行，重跑必须换硬件，
旧结果不构成任何比较基准点。教训按 CLAUDE.md 的说法就是过早宣布成功：
`readyz=ok` 之后机器又崩了两次。

第 6 个缺陷的判定证据极其干净：`SEED-G02-0015` 的 `baseline_cpu_max = 2.243332663338218`
与 34 秒前 `SEED-G02-0014` 的最后一个 recovery 采样**逐字节相同**。
ad 的 CPU 查询是 2 分钟 `rate()`，而 `recovery_state` 只要求信号不恶化、
从不要求回到静息，所以**每个** adHighCpu case 结束时 pod 都仍在 2.24–2.45 cores 衰减中。
后一个 case 是否失败只取决于间隔：25 分钟（case 3→11）、12 分钟（11→14）干净，
6 分钟（14→15）被污染。乘上冻结的 5.0 倍数后激活线变成 11.2 cores，而该 pod 饱和在 4 左右。
`emailMemoryLeak` 因为重建 pod 而免疫，`kafkaQueueProblems` 因为不乘倍数而暴露极小——
**adHighCpu 是唯一同时具备"baseline 不重置"与"乘倍数"的标签，所以它是唯一失败的标签。**

修正是要求 control 阶段先观测到静息的 ad pod（≤0.25 cores，5 秒轮询，240 秒 deadline）
再采 baseline；实测静息值是 0.002 cores，阈值远高于静息且远低于任何被污染的读数。
静息 baseline 只会更低，因此**不可能把未激活的故障判成激活**，方向上只能消除假阴性。
`AD_CPU_ACTIVE_MULTIPLIER` 与 `AD_CPU_ACTIVE_MIN_CORES` 一律未动——
为让这个 case 通过而下调倍数正是 runbook 明令禁止的门槛弱化。

**方法论上这一轮验证了诊断模式的价值**：case 23 在断连前 fault oracle 已达 `FAULT_ACTIVE`，
按默认的首失败即中止语义，整轮会停在 case 23，24-32 的信息一概拿不到。
诊断模式以零模型成本一次性给出完整失败谱，并且**八个失败全部可从 journal 单独归因，
无一需要第二次 live 运行**——这正是本轮改造的目标。
此前"约 7%/case、干净通关概率约 10%"的二项估计至此被"具体是什么在失败"取代：
剩下的是一个真实缺陷加 SSH 抖动，不是无法解释的 7%。

**这一轮的方法论修正值得单独记录**：前三轮每次失败只能换来一个数据点，
因为失败路径不留观测、且首失败即中止。排除已修缺陷后，28 次 case 执行里仍有
2 次无法解释的失败（≈7%/case，精确二项 95% CI 约 0.9%–23.5%），
据此估计串行 32-case 一次干净通关的概率仅约 10%（区间 0.02%–75%）——
**样本量根本不支持"再跑一轮就过"的判断**。因此本轮不赌运气，
而是先让每次失败自带归因（第 4 项四个缺口），再以
`--continue-on-case-failure` 诊断模式一次性暴露 32 个 case 的完整失败谱，
零模型成本。诊断模式产物强制标注 `diagnostic_only` 且永不可提升为 readiness 证据。

**明确未做也不打算做的事**：不授权抽样重试（AMD-0003 只对可归因的基础设施故障
授权无限重试，metric failure 仍然 blocking）；不动 7 个门槛数值、六个 adapter、
90 秒激活 deadline、65 秒 fault 间隔、32 case 分母；不动 `fault_state` /
`recovery_state` 的任何谓词；不改 `LOCUST_USERS` 或环境负载配置；
不编辑 `docs/gates/G02/REPORT.md`。

第 1 项落地时的一处偏差值得记录：本审查原稿建议把 `fault_family_success` 也标 N/A，
实施时没有照抄——它由现有 family 归属真实可算，已按四个 family 聚合。原稿那条建议是错的。

case 1-3 全部 `pass`。**其中 case 1 是 correction 6 的首个正面证据**——它正是上一轮

`protected_assets_start` 与 `protected_assets_end` 逐字节相同

| 时刻（CST） | 事件 | 证据 |

但 96 trial/arm × 3 arm 的 live 参照运行给了它足够多的崩溃机会，
所以宿主稳定是 live 运行的前置条件，而非可选项。

### 宿主内核迁移到 5.8（ADR-0016）

5.15 的修复路径已定位（为 5.15 重建 DKMS 模块 + `update-initramfs -c`，
因为现存 `nvidia.ko` 编译于 2025-06-26，早于 16:45 刷新的模块树 14 个月），
但每次验证都要一次重启，而该主板（ASUS TUF GAMING Z790-PLUS WIFI）无 BMC/IPMI、
panic 发生在 sshd 与 frpc 启动之前、GRUB 选择需要物理在场。
故按"先试 5.15、不行则快速转 5.8"的决定迁移到 5.8.0-43，5.15 保留为可修复状态。

[ADR-0016](../../../adr/ADR-0016.md) 讨清 [ADR-0007](../../../adr/ADR-0007.md)
"宿主内核不兼容须另发 OS/VM ADR"这一条款。实现要点：

- `ACCEPTED_KERNEL_SERIES = ("5.15.", "5.8.")` 与 `kernel_series_accepted()`
  收敛原先三处散落的 `startswith("5.15.")`（`bootstrap.py:864`、
  `infra.py:470`、`infra.py:1188`）。
- **两个系列同时接受，而非替换。** 替换会追溯性地使已关闭的 G01 capability
  baseline（`docs/evals/EVAL-G01-001/CAPABILITY_BASELINE.json` 记录
  `5.15.0-139-generic`）失效，而该文件与 `docs/gates/G02/REPORT.md` 同属冻结历史记录。
- 其余 capability 断言一律未动且仍然生效：`cgroup_version == 1`、`cpu_count >= 32`、
  `memory_bytes >= 60 GiB`、`nvidia_available is True`、`"4090" in gpu_model` 等。
  不在两个系列内的内核仍然被拒（测试覆盖 5.4 / 6.8 / 空串）。

迁移的两项代价是实测发现的，不是预估：

1. **板载网卡 `eno1` 在 5.8 上不存在**——该内核没有对应驱动，只有 `enp7s0`
   （`atlantic` 10G）起来。因此宿主在 5.8 上持有的地址不同，
   k3s 所有钉住地址的资产（`bind-address`、`tls-san`、`node-ip`、kubeconfig
   `server`）以及 etcd member peer URL 都必须随内核选择一起改。
2. **NVIDIA DKMS 模块只为 5.15 编译过**，5.8 上 `nvidia_available` 为 False，
   capability baseline 此时失败在 GPU 断言而非内核断言。为 5.8 的 DKMS 构建已发起。

后续 readiness 与参照证据必须记录产出它的内核，避免跨内核静默比较。

### 宿主稳定性与硬件更换（ADR-0017，2026-08-11 起）

ADR-0016 要求记录产出证据的**内核**；ADR-0017 把这条义务扩展到产出证据的**宿主**，
因为原宿主的失效不是软件问题。

原宿主（`pci`，i9-14900K）的失效签名按 CLAUDE.md 的判据是硬件级的：
`/var/lib/systemd/pstore/` 累积 **3112 份崩溃归档**、**95 个互不相同的 `RIP`**，
且出现在 `swapper`/`kswapd` 这类纯内核上下文——集中在一处才是软件 bug，
散落几十处是硬件。它在 5.15 与 5.8 **两个内核上都崩**，排除了内核专属回归的解释。
微码从 `0x123` 推到 `0x12F` 之后仍崩，最终该机**完全不再 POST**。
13/14 代 i9 的 Vmin-shift 退化是已知问题，这也是 CLAUDE.md 里"装机时就确认微码 ≥ `0x12F`"
这条的来历。

替换宿主（`pci-2`，i9-13900K / RTX 4090 / ASUS PRIME Z790-P）有它自己的崩溃史，
在投入使用前已检查：2026-08-12 在一次 `fw-sut` lab 部署中进入崩溃-重启循环，
微码 `0x133`。此后转为稳定——2026-08-25 启动，至 2026-09-05 已连续运行 11 天，
`oops_this_boot=0`、`mce_this_boot=0`。

**结论与仍欠的证明**：这不构成"已确认健康"。Vmin-shift 失效是间歇且负载相关的，
CPU 与 DIMM 的分离**尚未做**。当前立场是：可用于产出证据，但每份产物都必须记录宿主，
且在称其为 sound 之前仍欠 CPU-versus-DIMM 的分离实验。

**对证据可比性的直接后果**：原宿主产出的 readiness 证据与 pci-2 产出的**不可比较**，
因为前者的 CPU 在静默损坏执行。这就是上文 2026-07-29 那一轮
（24 pass / 7 `infra_failed` / 1 `metric_fail`）不构成基准的原因。
落实到工程上，run manifest 自 2026-09-05 起记录 `host_identity`：
宿主 SSH **公钥**的摘要加 runner 内核串。公钥按定义非秘密、跨重启稳定、每台机器唯一；
`known_hosts` 行的首字段是宿主地址，**刻意不进摘要**，
因此产物带有稳定的机器指纹而地址、端口、用户名与任何密钥材料都不落盘。
该字段**不参与** resume 身份校验——runner 内核是环境量，
拿它比对会因与被测量无关的原因拒绝 resume。

## 与其他 Gate 的联动

G03 不是孤立的纵切，它为三个后续 Gate 预留接口。**这些接口必须在 G03 就位，
否则后续 Gate 需要返工改 G03 的结构**：

| 联动 | G03 必须预留 | 服务于 |
|---|---|---|
| `REQ-AGT-003` G03→G05→G06 | checkpoint 恢复的幂等语义，扩展到外部副作用 | G05 动作事务 |
| `REQ-REL-001` G03→G05 | typed error 与降级路径的分类体系 | G05 失败补偿 |
| `REQ-OBS-001` G01→G03 | EvidenceRef 结构可容纳 RAG 的 chunk-level 引用 | G04 citation precision |
| `REQ-TOOL-005` G03→G04 | 工具 catalog 结构支持 MCP 只读子集投射 | G04 MCP 接口 |
| `REQ-PERF-003` G03→G08 | 成本归因粒度到单次模型调用 | G08 优化对照 |
| `REQ-AGT-005` G03→G08 | Verifier 不继承 Planner 结论的接口位 | G08 消融 |
| `REQ-AGT-002` G03→G07 | typed terminal reason 的枚举可扩展 | G07 badcase 分类 |

第三行最关键：**EvidenceRef 如果只能引用 observation ID，G04 的 citation precision
就无法落地**，因为 RAG 引用需要 source/version/section/chunk 四级定位（`REQ-RAG-004`）。
G03 设计 EvidenceRef 时必须把这四级留出来，即使 G03 只用到 observation 一级。
