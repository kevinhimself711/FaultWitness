# G07 设计：完整评测、数据飞轮与泛化

## 本 Gate 的定位

G07 是**简历数字的唯一合法来源**。立项报告 §0.1 有一条一票否决项专门指向它：
"简历写'准确率 90%''Token 降低 60%''响应提速 5 倍'，却拿不出测试集、计算公式、样本数和实验报告。"

§22.3 的项目完成定义里有三条只能由 G07 满足：150+ Case、1000+ 轨迹可复现、
"所有简历指标能由脚本重新生成"。

它承接 3 条 T1 + 6 条 T2。`evaluation_badcase` 主题 JD 68% / 面经 37%——
面经里它主要以**badcase 归因**的形式出现，不是以"你的评测框架长什么样"出现。
这个区别决定了投入重点：**badcase 深度报告比指标数量更值钱。**

## 冻结的退出标准（只能提高）

> 本节的**定性**条款（安全边界、失败语义、零容忍项）保持冻结。
> 其中**引用实测量的数值目标**在该 Gate 首次通过有效性检查的测量之前视为待定，
> 依据 ADR-0018 的同一原则：冻结定义，不冻结未知数。

`FINAL_PLAN.md:310-314`：

1. 达到 G02 冻结质量下限。
2. Judge-human agreement 不低于 **0.80**。
3. 数据、Ground Truth 和失败标签全部可追溯。

第 1 条有一个前提问题：**G02 冻结时 7 条 floor 里 5 条从未真正生效**
（详见 [EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md) 第三节）。
到 G07 时必须全部真正可计算，否则"达到 G02 冻结质量下限"是空话。

好消息是这个偿还是渐进的，且 metric v2（2026-07-28）已提前完成大半：

- `core_e2e` 的门槛表达式 `"max(0.70,best_baseline+0.10)"` **已被代码解析并聚合**
  （本审查早先说它是无解析的字符串，该判断基于较早版本）。
- `fault_family_success` **已按四个 family 真实计算**，不必等 G03-08。
- `evidence_precision` 已有 `required_evidence` / `distractor_evidence` 字段，
  但当前 `required_evidence` 只有一个组且由标签下标推出，与 `core_e2e` 共线——
  真正"可答错"要等组存在性泄漏修完，见
  [EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md) 第 0 节。
- 仍为显式 N/A 的两条各自绑定 G03 证明义务：`tool_schema_validity` →
  `g03.tool_contract_matrix`，`dead_no_progress_loop` → `g03.termination_guard_matrix`。

**到 G07 时只剩这两条 N/A 需要确认已在 G03 兑现**，以及确认
`evidence_precision` 已解除与 `core_e2e` 的共线。

## Iteration 划分

### I-G07-01：160 case 撰写与授权（L，6-8d）

**交付**：160 个均衡 case，覆盖 Easy / Medium / Hard / OOD / Adversarial。

**当前状态**：`CORE-0001..0160` 是 **metadata-only preregistry**，G07 前强制未物化。
这个设计是对的——防止提前看到 case 导致过拟合。

**T2 支撑**（`REQ-EVAL-001`）。150 是 §22.3 的硬要求，不能降。

**Eval 与通过标准**：
- manifest 计数、平衡、来源、split、locked Ground Truth 机器校验通过
- 至少 **24 个误导性最近变更场景**（`FINAL_PLAN.md:304`）——这一条是
  `REQ-ENV-003` 的落点，也是对抗"选最容易的证据"的关键
- Ground Truth 对 Agent runtime 不可达 — 零容忍（继承 G02 的 60 格 access matrix）

### I-G07-02：Split 重设计（M，2-3d）

**这一项是本 Gate 最重要的设计修正。**

现状：`SPLIT_COUNTS = (("dev",4),("validation",2),("locked",2))`
（`src/faultwitness_dev/g02_isolation.py:18`）按**模板**切分。
问题是：**同一事故模板会同时出现在 dev 与 locked 里**，按构造存在泄漏。

立项报告 §8.6 要求按事故模板**和时间**切分。

**Eval 与通过标准**：
- 同一模板不得跨 split 出现 — 零容忍
- 时间维度切分：locked split 的时间窗晚于 dev — 零容忍
- 泄漏检测脚本可重复运行

不修的话，`REQ-EVAL-001` 的 verification 要求"splits 机器校验"就是在校验一个有缺陷的切分。
这也直接影响 G03 的 5pp 主张——如果 validation 与 dev 同模板，5pp 可能来自记忆而非泛化。

### I-G07-03：分层指标注册表（M，3-4d）

**T1 核心**（`REQ-EVAL-002`）。结果、轨迹、工具、检索、记忆、安全、性能、成本八个维度。

**Eval 与通过标准**：
- 指标注册表定义公式、聚合方式、门槛、置信区间、拥有产物 — 每个指标四项齐全
- **`core_e2e` 的门槛表达式必须真正被解析**（偿还 G02 遗留）
- 每个指标有一个"未计算则报错"的守卫（偿还 G02 的 5 条空转 floor）
- **注册表增加 `rationale` 字段**（第二轮增补，+0.5d）：记录该指标的**参数取值理由**。
  最直接的例子是 Recall@10 的 K——它是冻结数值，但现有五项要求
  （公式、聚合、门槛、CI、拥有产物）没有一项解释**为什么 K 取 10**。
  §20 Q52 直接问这个，而报告 `:1495` 要求任何简历指标都能回答"定义、公式"。
  成本极低，见 [INTERVIEW_DEFENSE_COVERAGE.md](../INTERVIEW_DEFENSE_COVERAGE.md)

最后一条是从 G02 学到的最重要的机制教训：`validate_threshold_registry` 只做 dict 相等比较，
能保证数值不漂移但完全不检查指标是否被计算过。**门槛注册表必须同时约束"值"和"来源"。**

### I-G07-04：可复现与重放（M，3d）

**T1 核心**（`REQ-EVAL-003`）。

**Eval 与通过标准**：
- 一条命令重现全部指标，记录不可变输入与输出 digest
- **journal-backed replay adapter**：以 `(trial_id, call_ordinal, prompt_digest)` 为键
  从 journal 回放模型响应，`prompt_digest` 不匹配即报错而非静默穿透到真实 provider

第二条是 `AGENTS.md` badcase triage 前两步（Trace 重放同一任务、固定模型输出隔离随机性）
的实现，目前完全不存在。没有它，badcase 归因只能靠读日志推断。
详见 [EVAL_HARNESS_REVIEW.md](../EVAL_HARNESS_REVIEW.md) 第五节。

### I-G07-05：Judge 校准（M，3-4d）

**T2 支撑，但建议上调到接近 T1**（`REQ-EVAL-004`）。

理由见 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md)：它是
"你怎么知道你的分数是对的"这一追问的**唯一**答案，而现在没有实现路径。

**Eval 与通过标准**：
- Judge-human agreement ≥ **0.80** — 冻结标准
- 报告分歧类别、模型版本、方差（`REQ-EVAL-004` 的 verification 要求四项）
- **盲评**：人工复核者不知道 Judge 的判定
- **确定性 evaluator 优先**（`FINAL_PLAN.md:363`）：能用规则判的不用 Judge
- **同一模型不得同时生成测试、答案并作为唯一 Judge**（`FINAL_PLAN.md:364`）

最后一条在本项目有一个具体约束：模型网关只有一个真实上游（Bailian），
三个模型族（`qwen3.7-plus`、`deepseek-v3.2`、`glm-5.2`）**不是三个独立 provider**。
Judge 与被测必须用不同模型族，且报告里要说明它们共享同一上游——
这个诚实声明比假装有三个独立 provider 更安全。

### I-G07-06：Badcase 分类与深度报告（M，4-5d）

**交付**：13 类 badcase 分类 + 至少 10 份深度报告（`FINAL_PLAN.md:306`）。

**分类口径已修正为 13 类**，依据见 [BADCASE_TAXONOMY.md](../BADCASE_TAXONOMY.md)：
`FINAL_PLAN.md:306` 只写了"七类"这个数字，全仓库从未枚举是哪七类；
立项报告 §13.1 给出的是 13 类，且其中 4 类各自对应本项目专门建设的机制
（独立 Verifier、并发/状态覆盖、策略拒绝、预算超限），压缩掉它们会使机制失去归因证据。

**这是本 Gate 面试价值最高的一项。** `evaluation_badcase` 在面经里主要以归因形式出现，
而"能把失败定位到规划/检索/工具/模型/记忆中的具体环节"是 §0.1 的一票否决项。

**Eval 与通过标准**（较原七类口径**变严**，符合"阈值只能提高"）：
- 13 类覆盖全部失败样本，`other` 兜底类 ≤ **5%**
- **五个可自动判定的类目必须由代码判定，不得人工标注**（参数错误、Tool 自身失败、
  并发/状态覆盖、策略拒绝、预算超限）——防止分类主观化
- 每个类目至少 1 个样本，否则**显式记录该类目不可达及原因**（沿用 floor 的
  `not_applicable` + 证明义务原则）
- 10 份深度报告各定位到**具体环节**并给出可验证的修复假设
- 每份报告可通过 I-04 的 replay adapter 重现
- 深度报告含一个固定小节，按**幻觉五层**（数据/模型/检索/推理/工具）重新聚合同一份
  badcase 数据——这一次聚合同时回答立项报告 §20 第 82 题，无需额外实验

**依赖 G03**：typed terminal reason 的枚举必须可扩展（见 [G03.md](G03.md) 联动表末行）。
**约束**：badcase 分类**不得**向 `TerminalReason` 追加成员——终止方式与失败原因是
两个正交维度，交叉成表，见 [CROSS_GATE_INTERFACES.md](../CROSS_GATE_INTERFACES.md) 规格 2。

### I-G07-07：轨迹累积（S，2d）

**T3 降级**（`REQ-EVAL-006`）：作为 G07 副产物累积，**不单独立项**。

1000+ 条 TrajectoryIR 是 §22.3 的硬要求，但它是 160 case × 多 baseline × 多次重复的
自然产物，不需要专门的采集工程。

**Eval 与通过标准**：
- 轨迹 manifest 证明计数、split 隔离、血缘、隐私、重放兼容性
- 隐私：轨迹中无 secret 无 PII（复用 G06 的 canary 探针）

### I-G07-08：泛化验证（M，3d）

**交付**：Online Boutique 20 个 diagnosis-only case + ITBench-Lite locked eval
（`FINAL_PLAN.md:307-308`）。

**这一项的价值被低估了。** 在一个**没训练过的第二个微服务系统**上测量，
是"你的 Agent 是不是只会你那 32 个 case"这一质疑的唯一答案。
它比 160 个同源 case 更能证明泛化。

**Eval 与通过标准**：
- Online Boutique 20 case 为 diagnosis-only（无写操作，降低环境成本）
- 报告与主环境的性能差距，**允许显著下降**——如实报告比修饰更有说服力
- ITBench-Lite 作为 locked eval，只跑一次

### I-G07-09：Gate 评测（S，2d）

**Eval 与通过标准**：
- 达到 G02 冻结质量下限（7 条 floor **全部真正可计算**）
- 数据、Ground Truth、失败标签全部可追溯 — 冻结标准
- 随机实验至少三次并报告 95% CI（`FINAL_PLAN.md:365`）

## 规模

九个 iteration,约 **29-35 天**（含 I-03 的 `rationale` 字段 +0.5d）。I-01（160 case 撰写）是最大单项,
且它是纯人工工作,无法通过工程手段压缩。

建议 I-01 与其他 iteration 并行推进——case 撰写不依赖代码。

## 明确不做

- **交互式 Dashboard**（`REQ-OBS-003`）。降为静态报告页。observability 面经 24%,
  看板是最贵的表达形式。
- **超过 160 的 case 规模**。160 已满足 §22.3 的 150+ 要求,更多不增加可讲述性。
- **多个外部 benchmark**。Online Boutique + ITBench-Lite 两个足够证明泛化。
