# G10 设计：发布、Dogfooding 与面试资产

## 本 Gate 的定位

G10 不产出新能力,它把前九个 Gate 的产物转成**可被面试官验证的资产**。

`FINAL_PLAN.md:344-359` 的交付里有一项值得单独提出：**私网运行 4-6 周,
至少 3 名使用者和 20 次事故调查或回放**。这是整个项目里唯一的**真实使用证据**,
也是立项报告 §0.1 最后一条（"项目来自开源仓库改名,无法讲清自己的需求、取舍、失败方案"）
的正面对策——有真实用户用过,这条质疑就不成立。

但它也是最难保证的：4-6 周是日历时间,不能靠加班压缩;3 名使用者需要真实的人。
**如果找不到 3 名使用者,应如实降为 dogfooding 自用 + 完整回放记录,并明确说明**,
而不是虚构使用者。§4.4 已经写明"没有这些资源时,不应虚构客户、人工团队和线上准确率"。

## 冻结的最终退出标准（只能提高）

`FINAL_PLAN.md:354-359`：

1. G00-G09 全部通过,**无 P0/P1 缺陷**。
2. 新环境仅按文档即可部署。
3. Claims **100%** 关联代码、测试、Trace、数据和实验。
4. 三条训练管线有真实 **4090 smoke** 证据。

第 3 条是全项目最有价值的一条冻结标准。它把 §0.1 的
"简历写准确率 90% 却拿不出测试集、公式、样本数"从一个警告变成了一个可检查的门。

## Iteration 划分

### I-G10-01：三套面试叙事（M，3-4d）

**交付**：应用开发、Agent Infra、AI 算法三套叙事（`FINAL_PLAN.md:352`）。

**这是本 Gate 最重要的一项,也是本次审查的核心原则最直接的落点。**

立项报告 §1.3 明确说这些 JD 至少分成四类岗位,"一个个人项目不可能在每个方向都达到同样深度",
合理方案是"建设一套共同的生产型 Agent 核心;主攻应用开发作为默认求职叙事;
按目标岗位二选一增加算法优化扩展或 Infra 扩展"。

因此三套叙事的**深度不应相同**：

| 叙事 | 定位 | 承重的 Gate | 深度 |
|---|---|---|---|
| 应用开发 | **默认主叙事** | G03（Agent loop、工具、状态）、G04 阶段 A（RAG）、G05（受控写） | 最深 |
| AI 算法 | 二选一扩展 | G07（评测、badcase 归因）、G09（训练 smoke + 归因报告） | 中等 |
| Agent Infra | 二选一扩展 | G01（Trace、平台）、G06（隔离、lease、沙箱） | 中等,已按分级瘦身 |

**Eval 与通过标准**：
- 每套叙事的每个主张关联到具体的代码、测试、Trace、数据、实验 — **100%**,冻结标准
- 每套叙事能回答立项报告 §20 对应小节的追问（§20.1-§20.11）
- 应用开发叙事可不看稿完成,并能现场定位任一 Trace（§22.3 的完成定义）
- **§19.1 的 ADR 最低清单十二条各有一份 accepted ADR**（第二轮增补）

**第二轮增补两项。** 上面第二条通过标准此前无法验证——本轮逐题反向检索 §20 的 88 题，
发现 9 题无落点（见 [INTERVIEW_DEFENSE_COVERAGE.md](../INTERVIEW_DEFENSE_COVERAGE.md)），
其中 4 条经判据筛选后采纳。落在本 iteration 的是两条：

**（1）§19.1 ADR 清单的验收。** 十二条里八条此前没有对应 ADR
（现有 15 份全是架构不变量、基础设施选型、治理机制与 G02 实验协议）。
八份分散在 G03 I-09（五份）与 G04 I-06b / I-10（各一份），
剩余一份（Memory 写入与冲突已含，Tool/MCP 权限模型由 ADR-0006 覆盖、
模型路由由 ADR-0008、评测与 Judge 由 ADR-0012、部署与扩展由 ADR-0007）在此核验齐全。
**本 iteration 只做验收，不写 ADR**——ADR 应在决策发生的 Gate 里写。

**（2）项目级 Problem Brief（+1d）。** `REQ-BUS-001` 是 **P0 mandatory**，
verification 原文 "A versioned Problem Brief answers every field without invented
customers or traffic"，但仓库里 `problem_brief` 只是单个 fault case 的场景字段
（`g02_baselines.py:238/256/269`），**项目级文档不存在**。
一份 ≤2 页：真实用户、事故类别、基线工作流、频率、失败成本、可伪证的成功判据，
外加一节**"为什么现成产品（Datadog Watchdog、PagerDuty AIOps、自建脚本）不够"**——
`竞品`/`开源方案` 全仓库 0 命中，说明这个判断从未被写下来，而它是 §20.1 的开题问。
**不虚构客户与流量**（§4.4）：用户就是 dogfooding 的自己与 ≤3 名私网使用者，如实写。

### I-G10-02：私网运行与 dogfooding（L，4-6 周日历时间）

**交付**：4-6 周私网运行、≥3 名使用者、≥20 次事故调查或回放。

**Eval 与通过标准**：
- 20 次调查或回放的记录完整,含失败案例
- 使用者反馈记录（不修饰负面反馈）
- 如使用者不足 3 名,**如实降级并说明**,不虚构

这一项应与其他 iteration **并行**：私网运行是日历时间,期间可以做文档与演示脚本。

### I-G10-03：清洁环境部署演练（S，2d）

**T2 支撑**（`REQ-DEV-003`,跨 G02/G10）。

**Eval 与通过标准**：
- clean-clone 按 README 命令执行,无隐藏全局依赖 — 冻结标准
- 新环境仅按文档即可部署 — 冻结标准

按 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md) 的判断,
这一项**只在 G10 做一次**,不需要每个 Gate 重做。

### I-G10-04：Runbook、Threat Model 与三张 Card（S，3d）

**交付**：Runbook、Threat Model、Data Card、Model Card、Eval Card。

**Eval 与通过标准**：
- Threat Model 覆盖注入、越权、数据泄漏、沙箱逃逸四类,各引用对应的 Gate 证据
- 三张 Card 的每个数字可由脚本重新生成（§22.3）

### I-G10-05：五类演示（M，3d）

**交付**：成功、补偿、误导性变更、Worker 恢复、租户隔离五类演示
（`FINAL_PLAN.md:351`）。

**Eval 与通过标准**：
- 五类各有可重复执行的演示脚本
- 正常路径与至少一种失败路径可演示（§22.3）
- 演示不依赖预录制,现场可跑

**这五类的选择很好**,因为它们各自对应一个一票否决项的反面：
补偿↔"工具有写操作却没有回滚"、误导性变更↔"说不清冲突"、
Worker 恢复↔"没有断点恢复"、租户隔离↔"不理解状态、并发、数据库"。

### I-G10-06：AI Coding 度量（S，1-2d）

**建议上调到 P0 支撑档**（`REQ-DEV-004`,现为 P1）。

理由见 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md)：`ai_coding` 是**唯一**
面经覆盖率（39%）高于 JD（27%）的主题,却被定为 P1。这是低估。

**交付**：accepted diff 比例、首过验证率、返工率三个数字,**全部由 git 历史自动生成**。

**Eval 与通过标准**：
- 报告定义与原始聚合,而非只给 AI 生成的百分比（`REQ-DEV-004` 的 verification 要求）
- 三个数字可由脚本从 git 历史重算

成本极低（1-2 天,数据已在 git 里）而追问命中率高——
"你这个项目多少是 AI 写的""你怎么判断 AI 的输出对不对"是面经里的常见问题。

**第二轮增补：从"三个数字"扩为"三个数字 + 一节现有 harness 与防弱化机制说明"（+1d）。**
§20.11 是全部十一节里最薄的一节（六题里四题无交付物），
但[素材其实很充分](../INTERVIEW_DEFENSE_COVERAGE.md)，缺的只是收口：

| §20.11 题 | 现成素材 |
|---|---|
| Q86 止血与复盘 | `docs/engineering/badcases/BC-PROC-0001..0006` 六份可复现过程 badcase + GR-02–GR-12 防复发规则；`BC-PROC-0004` 是"错误处置掩盖了可定位失败"的完整复盘 |
| Q87 防止 AI 弱化测试 | `AGENTS.md:27`（用户指令 never authorizes weaker safety/thresholds）、`PHASES.md:24`、`validate_threshold_registry` 的 dict 相等检查（`g02_baselines.py:111`，由 `tests/g02/test_g02_baselines.py:140` 覆盖）、G07 I-03 的"未计算则报错"守卫 |
| Q88 Harness 组成 | `AGENTS.md` 本身：环境、`verify-fast` 工具、L1/L2/L3 判定层、安全不变量权限、direct debug loop 五项齐全 |

**注意 `AGENTS.md:40` 明确禁止 "add a bespoke harness"**——
本项是**把现有 harness 写清楚**，不是新建一个。这一节的补齐成本几乎全是写作。

> **引用已失效（核实于 2026-09-10）**：`AGENTS.md` 已重写为 60 行，全文不含 harness 或 bespoke
> 字样，第 40 行也不再是该内容，因此这条禁令在 `AGENTS.md` 中不存在。等价禁令仍在
> `docs/blueprint/AMENDMENTS/AMD-0005.md:15` 与 `docs/adr/ADR-0014.md:31-32`（均限于 corrective
> 与 Gate attempt，见其适用性限定）。本项的结论不变：写清楚现有 harness，不新建一个。

### I-G10-07：安全与合规审计（S，2d）

**交付**：`REQ-SEC-003` 的第三段（跨 G01/G06/G10）+ 来源/License/Secret 最终审计。

**Eval 与通过标准**：
- Secret 与 PII canary 在全部出口面被拦截或脱敏 — 零容忍
- **`audit.py` 的完整审计有 CI 前门**（[G00.md](G00.md) 的残留 1 已于 2026-07-28 偿还,
  本项改为验证该前门未在后续 Gate 中被摘除）
- 无绝对本地路径、无 JD/面经原文、License 合规

原风险已消除：`audit.py` 已接回 `verify-fast`,"仓库可公开"这个决定不再建立在
一个没有 CI 保障的检查上。G10 需要断言的是**这条前门到 G10 仍然存在**——
它在 G00 到 G05 之间曾被移除一次,复发是真实可能。

### I-G10-08：locked 回归门（S，2d）

**T2 支撑**（`REQ-EVAL-005`,跨 G07/G10）。

**Eval 与通过标准**：
- CI 检测受保护面变更,并在 core set 回退时阻止合并
- **注意与 governance v2 的关系**：`GOVERNANCE_V2.md` 已把 CI 降为 1 个 advisory job,
  0 个阻塞项。locked 回归门是**唯一**应当重新引入阻塞的检查——
  但它必须只在受保护面变更时触发,不能变回 G02 那种全量阻塞

最后一点很重要。[GOVERNANCE_REVIEW.md](../GOVERNANCE_REVIEW.md) 量化了 G02 的
strict up-to-date + candidate binding 自失效循环的成本。重新引入阻塞检查时,
必须避免同样的结构：**按语义变更范围触发,不按 commit 触发。**

- 三条训练管线有真实 4090 smoke 证据 — 冻结标准

## 与其他 Gate 的联动

G10 引用全部前序 Gate,以下是**双向**的（G10 的要求反过来约束前序设计）：

| 联动 | 反向约束 |
|---|---|
| Claims 100% 可追溯 | 每个 Gate 的报告必须记录足以支撑简历数字的原始聚合,不能只给结论 |
| 新环境仅按文档部署 | 每个 Gate 的部署步骤必须写进 README,不能只存在于开发者记忆里 |
| 三套叙事 | G03/G04/G05 服务应用叙事,G07/G09 服务算法叙事,G01/G06 服务 Infra 叙事——**每个 Gate 要知道自己在为哪套叙事供货** |
| `REQ-SEC-003` 三段式 | G01 建 sanitizer、G06 扩全出口面、G10 最终审计 |
| `REQ-EVAL-005` G07→G10 | locked set 在 G07 冻结,G10 建门 |
| `REQ-DEV-001`/`REQ-DEV-002` G00→G10 | G00 的 ADR 与测试清单在此收口 |

第三行是本次审查全局视角的落点：**Gate 不是独立的,它们各自为一套面试叙事供货。**
按 [REQUIREMENT_COVERAGE.md](../REQUIREMENT_COVERAGE.md) 的分级,
应用叙事的供货 Gate（G03、G04 阶段 A、G05）承接了最多的 T1 核心需求——
这与"主攻应用开发作为默认求职叙事"的定位是一致的,不是巧合。

## 规模

九个 iteration。工程部分约 **20-24 天**（第二轮增补：I-01 的 Problem Brief +1d、
I-06 的 harness 与防弱化说明 +1d）,但 I-02（私网运行）需 **4-6 周日历时间**,
应与其他 iteration 并行。总日历时间约 **6-8 周**。

## 明确不做

- **虚构使用者或使用数据**。找不到 3 名使用者就如实降级。
- **公开演示环境**。`FINAL_PLAN.md:280` 明确"运行环境继续私有"。
- **交互式 Dashboard**（`REQ-OBS-003`）。静态报告页 + 演示脚本足够。
- **FaultWitness 自身的发布灰度**（§20 Q66 的"灰度"半句）。部署（I-03）、监控（G01）、
  动作回滚（G05）、索引回滚（G04 I-05）都有落点，缺的只是自身发布的渐进交付。
  这需要 Argo Rollouts / Flagger 一类 CD 栈，是纯发布工程，与 Agent 能力无关，
  且单节点 K3s 上做灰度没有意义。**驳回**，理由见
  [INTERVIEW_DEFENSE_COVERAGE.md](../INTERVIEW_DEFENSE_COVERAGE.md)。
- **产品级离线运行设计**（§20 Q65 的"离线"半句）。现有
  `prepare_offline_base_images`（`infra.py:642`）是把 pinned image 送进私网节点的
  **bootstrap 手段**，不是产品的离线运行能力。I-03 的部署演练应明确区分
  "离线安装"与"离线运行"，后者记入本节而非含糊带过。
- **恢复 G02 式的全量阻塞 CI**。locked 回归门按语义变更范围触发。
